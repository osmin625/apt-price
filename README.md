# 수원시 아파트 적정 시세 (PoC)

국토교통부 실거래가를 기반으로 아파트 매물의 적정 시세를 산출하는 웹 서비스.
수도권 확장을 염두에 두되, PoC 범위는 **수원시 아파트 매매**로 한정한다.

## 핵심 설계 결정

### 1. 평당가는 전용면적 기준

```
전용 평당가 = 거래금액(만원) ÷ (전용면적㎡ ÷ 3.305785)
```

공급면적이 아니라 **전용면적**을 분모로 쓴다. 같은 집이라도 공급면적 기준보다 25~35% 높은
숫자가 나오지만, 전용률(전용/공급)이 단지마다 70~80%로 제각각이라 공급면적 평당가는
단지 간 비교 기준이 되지 못한다. 국토교통부 실거래가 원본도 전용면적만 제공한다.

공급면적은 매물 입력 시 선택 항목으로만 받아 전용률 계산과 환산 표기에 쓴다.

### 2. 세 가지 비교 축

| 축 | 구간 | 기준 |
|---|---|---|
| **층** | 1층 / 저층 / 중층 / 고층 / 최상층 | 단지 최고층 대비 상대 위치 (~25% 저층, ~65% 중층) |
| **입지** | 초역세권(5분) / 역세권(10분) / 준역세권(15분) / 비역세권 | 최근접 지하철역까지 직선거리 400·800·1200m |
| **컨디션** | 신축(5년) / 준신축(10년) / 10~15 / 15~20 / 20~30 / 30년 초과 | 준공년도 기준 경과 연수 |

단지 최고층은 국토교통부 API가 주지 않으므로 **관측된 최고 거래층**을 추정치로 쓴다.
도보 시간은 직선거리에 보행 경로 보정(×1.25)을 한 뒤 분당 67m로 환산한다.
(분양 광고 관행인 "1분 = 80m"는 실제 보행 속도보다 빠르게 잡힌 값이라 쓰지 않았다.)

여기에 **노선 · 생활권(최근접역) · 단지 규모(세대수)** 필터가 더 붙는다.

| 필터 | 기준 | 비고 |
|---|---|---|
| 지하철 노선 | 큐레이션한 `Station.line` | 1호선 / 수인분당선 / 신분당선 |
| 생활권 | 최근접역 이름 | 노선을 고르면 그 노선 역만 남는다 |
| 단지 규모 | 세대수 300/600/1000/1500 구간 | K-apt 미매칭 단지는 '정보없음' |

노선·역은 카카오가 준 `Complex.station_line`('수도권1호선')이 아니라 **큐레이션한
Station 테이블**을 쓴다. 표기가 달라 필터 값과 화면 표시가 어긋나면 안 되기 때문이다.
필터 선택지도 고정 목록이 아니라 **실제로 단지가 붙어 있는 역**만 내보낸다 —
단지가 없는 역을 띄우면 고르는 순간 빈 화면이 된다.

> **생활권 필터의 한계**: 최근접역 기준이라, 역에서 먼 단지도 어딘가에는 배정된다.
> 예를 들어 우만동 월드메르디앙은 '광교중앙역 생활권'이지만 실제로는 도보 33분이다.
> 생활권으로 좁힐 때는 **입지 등급 필터를 함께** 거는 것이 안전하다.

위 구간은 **시장 분석 / 단지 비교 / 매물 진단** 탭이 쓰는 기술통계 축이다.
역거리를 자르지 않고 연속으로 보는 경로는 아래 6번의 헤도닉 모델이 따로 담당한다.

### 매물 분석 (적정가 진단 + A·B 분해)

한 화면에서 **두 가지 질문**에 답한다. 원래 탭이 갈려 있었는데, 실제로는 같은 매물에
대해 연달아 묻게 되는 질문이라 입력을 두 번 하게 됐다.

| | 묻는 것 | 단지 고유 프리미엄 |
|---|---|---|
| **적정가 진단** | 그 단지 같은 평형 시세 대비 이 호가가 적정한가 | 값에 이미 포함 |
| **요인별 비교** | A와 B 중 요인을 감안하면 어느 쪽이 싼가 | 빼고 펀더멘털만 |

둘은 다른 질문이라 답이 갈릴 수 있다. 재건축 기대가 붙은 단지는 "그 단지 시세로는
적정"인데 "펀더멘털 대비로는 비쌈"이 된다. 갈리는 것 자체가 정보다.

한쪽만 채우면 그쪽 진단만, 양쪽을 채우면 진단 두 장 + 비교까지 나온다.

요인별 비교는 평당가 차이를 **요인별 기여로 쪼갠다**. "A가 두 배 비싼데 왜 싸다는
거냐"에 대한 답이 표에 그대로 나온다.

```
A 자연앤힐스테이트 (이의동, 84.9㎡, 15층, 13.5억)
B 매탄주공5       (매탄동, 84.9㎡, 15층,  6.2억)

  역까지 도보   2.0분 vs 15.5분    +17.1%
  강남까지     35분  vs 58분       +8.1%
  연식        14년  vs 41년       +58.3%
  지하철 노선   신분당선 vs 수인분당선  +28.5%
  ──────────────────────────────────────
  모델 예상 차이                  +157.6%
  실제 호가 차이                  +117.7%
  → A가 15.5% 저렴
```

#### 입력 — 텍스트를 붙여넣으면 자동으로 채워진다

매물 화면의 텍스트를 그대로 붙여넣으면 단지·전용면적·층·호가를 뽑아 채운다.
붙여넣는 순간 돌아가고, 버튼을 한 번 더 누를 필요가 없다.

화면에 보이는 것은 **붙여넣기 칸과 채워진 값 요약**뿐이다. 검색창·필터·목록·입력칸은
'직접 입력' 토글 뒤에 접어 둔다 — 붙여넣기 한 번으로 끝나는 것이 기본 동선인데
입력칸이 전부 펼쳐져 있으면 그쪽이 기본처럼 보인다. 단, **파싱이 단지나 면적을
못 채웠으면 자동으로 펼친다.** 접힌 채로 두면 손댈 곳이 안 보여 막힌다.

```
힐스테이트푸르지오수원 103동
매매 9억
3,360만원/3.3㎡평당가 도움말
알림관심매물
공유하기
아파트88B㎡ (전용59B)8/15층남향
```

화면을 통째로 긁어 와 버튼 문구(`도움말`·`공유하기`)가 섞여도 쓸 줄만 골라 읽는다.
`아파트88B㎡ (전용59B)` 에서 **전용 59㎡** 를 집고(타입 문자 `B` 는 평면 변형이라
면적과 무관하다), `8/15층` 에서 8층·총 15층을, `매매 9억` 에서 90,000만원을 뽑는다.

**평당가 기준이 다른 것도 짚어 준다.** 위 매물에 적힌 평당가는 3,360만원/평인데
이 서비스는 5,043만원/평로 계산한다. 틀린 게 아니라 분모가 다르다 — 네이버는
공급 88㎡, 이 서비스는 **전용 59㎡** 기준이다(이 프로젝트의 출발점이 바로 그것이다).
적힌 평당가와 호가로 분모를 역산해 공급 기준이면 경고로 알려 준다. 50% 차이가
설명 없이 나오면 어느 한쪽이 틀린 줄 알기 때문이다.

다른 표기도 받는다.

```
자연앤힐스테이트 101동
매매 13억 5,000
아파트 · 112.9/84.97㎡, 중층, 남향
```

- **단위는 적힌 대로 읽고, 평은 1평 = 3.305785㎡ 로 환산한다.** 파싱 전에 한 번
  환산해(`normalize_pyeong`) 단위를 통일하므로, `34평/25.7평` 같은 공급/전용 쌍도
  ㎡ 쌍과 똑같이 뒤쪽을 전용으로 잡는다. `30평대`(범위)·`평당가`(단가)는 면적이
  아니므로 건드리지 않고, 숫자와 '평'은 **같은 줄**에서만 잇는다 — 줄을 넘게 두면
  `매매 3억 9,000` 다음 줄의 `평당가` 와 붙어 `000평` → 0평 이 된다.
- **괄호 안 전용은 앞의 공급에서 단위를 물려받는다.** 네이버는 `아파트17평 (전용12)`
  처럼 전용 쪽 단위를 생략하는데, 이때 12는 12㎡ 가 아니라 **12평(39.7㎡)** 이다.
  단위 없는 숫자를 일괄로 ㎡ 취급하면 맞는 평형이 사라져 면적 칸이 빈 채로 남는다.
  `88B㎡ (전용59B)` 는 공급이 ㎡ 라 이 규칙에 걸리지 않고 그대로 ㎡ 로 읽힌다.
- **'전용' 표기가 없는 면적은 공급으로 본다.** 광고의 `34평`·`112㎡`는 거의 항상
  공급면적이다. 그대로 전용에 넣으면 112㎡ 전용을 가진 단지가 아닌 한 "그런 평형 없음"
  으로 비워진다. 그래서 **어느 해석이 맞는지 데이터에 물어본다** — 숫자가 그 단지의
  전용 평형과 바로 맞으면 전용, 아니면 전용률 0.60~0.90 안에 드는 평형을 찾고, 여럿이면
  거래가 가장 많은 쪽을 고른다(`routers/model._resolve_area`). `34평` → 전용 84㎡
  (전용률 75%), `25평` → 전용 60㎡ (73%). 둘 다 아니면 비우고 직접 고르게 한다.
- `전용59B` `112.9/84.97㎡` `34평/25.7평` → 전용면적 ㎡. 한 쌍이면 뒤쪽이 전용이다.
  뽑은 값은 그 단지의 실제 평형으로 맞춘다(59 → 60㎡).
- `8/15층` → 8층. 뒤의 15는 **건물 실제 최고층**이라 층 구간 판정에 쓴다. DB 의
  `max_floor` 는 거래에서 관측된 최고층이라 거래가 적은 단지에서는 실제보다 낮다.
- `129동` → **역까지 도보를 그 동 좌표로 잡는다.** 동이 없으면 단지 중심점을 쓴다.
  수원센트럴아이파크자이는 129동이 19.9분, 104동이 12.4분으로 **단지 안에서만 8.4분**
  벌어진다. 중심점 하나(16.2분)로는 이 차이가 통째로 사라진다.

  동 편차에 단지 간 계수를 그대로 쓰면 안 된다. 단지 간 도보 계수(-1.083%/분)는
  입지 전반을 함께 싣고 있어 동 편차 계수(-0.355%/분, t=-9.7, n=20,211)의 3배다.
  그래서 **단지 중심점까지는 스플라인, 거기서 동까지의 편차는 within 계수**로 나눠
  더한다. 후자는 단지 고정효과와 직교하게 추정된 값이라 학군·브랜드·연식·구 입지가
  전부 통제돼 있다.

  직접 입력 패널의 동 선택은 `GET /api/complexes/{id}/dongs` 가 주는 실제 동 목록에
  동별 도보시간과 시세 프리미엄을 붙여 보여 준다 — 타이핑하면 오타도 나고 그 동이
  얼마나 먼지·비싼지도 모른다. 좌표를 못 잡은 동(전체의 19%)은 중심점으로 떨어진다.

### 동 프리미엄 — 재보니 평형 교란이었다

층 프리미엄은 처음부터 있었는데 동 프리미엄은 없어서, Stage 1 잔차를 단지 안에서
동별로 평균 내 봤다. τ=2.50%, 신호비 48% 라는 그럴듯한 값이 나왔고 수원센트럴아이파크자이
129동은 -8.66%(42건) 가 찍혔다. **전부 틀린 값이었다.**

**무엇이 틀렸나.** 그 단지에서 40㎡ 는 129동·130동에만 있고 나머지 28개 동은 60~103㎡ 뿐이다.
전역 면적 스플라인이 이 단지의 40㎡ 를 10%쯤 비싸게 예측하면 그 오차가 갈 곳은 129·130동의
'동 효과' 밖에 없다. 실거래를 직접 보면 두 동은 **같은 전용 39.77㎡ 유닛이고 평당가 중앙값이
3,076 으로 똑같다**. 동 위치 차이가 아니라 평형 차이를 보고 있었던 것이다.

여기에 수축까지 겹쳐 더 나빠졌다. 129동(42건, 수축 0.83)은 -8.66%, 130동(3건, 수축 0.26)은
-2.30% 가 됐는데, 두 동의 실제 가격은 같다. **6%p 격차가 순전히 표본 수 차이에서 나왔다.**
적정가 진단에서 129동 3,280원/평 vs 130동 3,531원/평 이라는 없는 차이를 만들어 냈다.

**고친 방법.** `(단지 × 평형)` 셀 안에서 잔차를 한 번 더 차감한 뒤 동별로 평균 낸다. 같은
평형을 나눠 갖는 동끼리만 비교되고, 같은 평형이 한 동에만 있으면 **식별 불가**로 빼 버린다
(403개 동). 129동은 -10.33% → **-0.13%**, 130동은 -8.58% → +1.82% 로 둘 다 0 근처가 된다.

**결과: τ = 0.00%.** 검출력을 보정해 보면(참 효과를 심고 되찾는 시뮬레이션)

| 심은 참 τ | 되찾은 값 |
|---|---|
| 1.0% | 0.00% (못 잡음) |
| 1.5% | 0.94% |
| 2.0% | 1.39% |
| 3.0% | 2.53% |

검출 한계는 **τ≈1.2%** 다. 즉 평형을 통제한 동 효과는 그보다 작고, 이 표본으로는
있다/없다를 말할 수 없다. 시장 분석 탭의 '동 위치' 카드는 0짜리 막대 다섯 개 대신
**"검출되지 않았습니다"** 와 그 한계를 적는다 — 0 을 그리면 '동은 가격과 무관' 으로
읽히는데 실제로는 '잴 수 없다' 이기 때문이다.

동 위치가 가격에 미치는 영향 중 이 표본에서 잡히는 경로는 **역까지 도보거리뿐**이다
(`dong_walk_dev`, -0.355%/분, t=-9.7, n=20,211). 그쪽은 위에서 설명한 대로 살아 있다.

> **교훈**: 단지 고정효과만으로는 부족했다. 동과 평형이 붙어 있는 단지에서는 다른 항의
> 오차가 통째로 동 효과로 흘러든다. 잔차 평균으로 무언가를 뽑을 때는 **그 무언가와
> 공선인 것이 무엇인지** 먼저 따져야 한다.

### 요인별 적정가 — 매물 하나를 분해한다

기존 '요인별 기여' 표는 **A−B 상대 차이**만 냈다. 그래서 두 가지가 안 됐다.

- 같은 단지 두 매물(129동 vs 130동)을 넣으면 단지 요인이 전부 0% 라 표가 텅 빈다.
- 한쪽만 넣으면 아예 나오지 않는다.
- 금액이 없다. % 기여만 있고 "그래서 얼마인가" 가 빠져 있다.

`model_view.model_price()` 가 매물 **하나**를 절대값으로 분해한다. α̂_c 는
`전용 84㎡ · 중층 · 최신월` 기준이므로, 거기에 이 매물의 면적·층·동 도보편차를 더해
해당 유닛으로 옮긴다. 출발점을 무엇으로 두느냐에 따라 두 값이 나온다.

| | 출발점 | 답하는 질문 |
|---|---|---|
| **실거래 기준** | 같은 단지·평형 실거래 | 이 단지 이 평형이 실제로 얼마에 팔리나 |
| **요인 기준** | Stage 2 예측 α̂ | 거리·연식·세대수·노선·구만으로 얼마여야 하나 |
| **시장 기준** | 관측 α̂_c | (내부 검산용 — 아래 참조) |

둘의 차이가 그 단지에 붙어 있는 **고유 프리미엄**이다. 학군·브랜드·재건축 기대처럼
측정하지 않은 것이 거기 들어 있다.

#### 면적 곡선 교정 — 안 하면 34% 틀린다

모델은 `α_c + f(면적) + 층` 인데 `f` 는 **전 단지 공통 곡선**이다. 어떤 단지의 40㎡가
84㎡ 대비 얼마나 싼지는 단지마다 다른데 공통 곡선은 그 차이를 못 담는다. 실제로
수원센트럴아이파크자이 40㎡ 에서 모델의 **시장 기준 46,111만원**이 같은 평형
**실거래 기준 40,532만원**보다 14% 높게 나왔다. 교정 없이 내보내면 요인 기준이
5.36억 — 실거래 4.05억짜리 집에 대해 +32% 짜리 숫자가 나간다.

두 값은 같은 질문("이 단지 이 유닛이 지금 얼마에 팔리나")의 답이므로, **어긋난 만큼이
곧 면적 곡선의 이 단지·이 평형 오차**다. 비율로 뽑아 요인 기준에도 먹인다.

    보정계수 = 실거래 기준 평당가 / 모델 시장 기준 평당가

단지 간 펀더멘털(Stage 2)은 건드리지 않고 **단지 안에서의 유닛 환산만** 고친다.
130동 20층: 원값 5.36억 → 교정 **4.74억**(보정 -12.1%). 실거래 비교가 없으면 교정할
수 없으므로 원값을 쓰고 그 사실을 남긴다. 2배 넘게 벌어지면 교정이 아니라 다른 데가
고장 난 것이라 손대지 않는다.

#### 화면

```

같은 단지·평형 56건      펀더멘털만            요인으로 설명 안 되는 부분
호가 -12.4%             호가 -25.1%

  역까지 도보    16.2분        -8.9%
  강남까지 전철  60분          -0.7%
  연식          2년          +46.9%
  세대수        3,432세대      +8.3%
  지하철 노선    수인분당선     -11.7%
```

두 판정이 갈릴 수 있고, **갈리는 것 자체가 정보다**. 이 매물은 실거래 대비 -12%인데
펀더멘털 대비로는 -25%다. 차이는 이 단지가 요인 대비 14.5% 낮게 거래된다는 뜻이다.

A·B 비교의 요인별 기여 표는 그대로 둔다 — 그쪽은 **상대 차이**를 묻는 다른 화면이다.

### 호가 누적 — 실거래가 못 잡는 것

실거래는 **팔린 것만** 남긴다. 값을 못 받는 매도자는 싸게 파는 대신 물건을 거둬들이므로,
거래가 뜸한 구간의 관측 거래가는 **위로 편향**된다(constant-liquidity index 문헌의 고전적
문제다). 내려간 물건은 거래가 아니라 호가에만 있다.

수원센트럴아이파크자이가 그 사례다. 129동과 130동은 **구조가 같은데도** 같은 기간 거래가
42건 대 3건이고, 그 3건은 시점보정하면 129동보다 오히려 **비싸게** 찍힌다(3,405 vs 3,306).
실거래만 보면 "130동에 디스카운트 없음" 이라는 결론이 나오지만, 팔리지 않는 물건이
호가로 얼마에 나와 있는지를 데이터가 통째로 놓치고 있는 것이다.

그래서 **붙여넣기마다 호가를 쌓는다**(`services/quotes.py`). 따로 '저장' 을 누르게 하면
아무도 안 누르므로, 매물 텍스트를 붙여넣는 것만으로 기록된다.

**중복 처리**가 이 기능의 핵심이다.

- 같은 `(단지·동·평형·층·호가)` 가 다시 들어오면 새로 쌓지 않고 `last_seen_at` 과
  `seen_count` 만 올린다. 같은 매물을 몇 번을 붙여넣어도 표본이 부풀지 않는다.
- **가격이 바뀌면 새 행**이 된다. 그 변화가 바로 보고 싶은 신호다 —
  130동 3.55억 → 3.38억 → 3.20억 같은 경로가 그대로 남는다.
- 층·동을 모르면 NULL 이 아니라 `0`/`""` 를 쓴다. SQLite 의 UNIQUE 제약은 NULL 끼리를
  서로 다른 값으로 보기 때문에, NULL 을 두면 중복이 그대로 쌓인다.

집계는 최근 90일 안에 확인된 호가만 본다. 매물은 팔리거나 내려가는데 우리는 내려간 걸
알 방법이 없어서, 시간으로 끊는 수밖에 없다.

적정가 진단 카드에 **실거래 기준값과 나란히** 뜬다. 대체가 아니라 보완이다 — 호가는
희망가와 급매가 섞여 있고 성사 여부를 모른다.

```
적정 시세 4.05억   |  130동 자체 3건 기준 4.16억
같은 평형 누적 호가 (최근 90일 · 4건)
  130동  3건  3.38억  3.20억~3.55억   2,793만원/평
  129동  1건  3.90억                  3,223만원/평
```

두 동의 호가가 430만원/평 벌어져 있는데 실거래로는 그 차이가 안 보인다 — 이 표가 없으면
그 사실 자체를 알 수 없다.

> **한계**: 호가 표본은 사용자가 붙여넣은 것만이라 대표성이 없다. 매물이 내려갔는지
> 팔렸는지도 모른다. 파서가 바뀌어 층·평형 해석이 달라지면 중복 키가 달라져 예전 행이
> 남는다(실제로 `고/23층` 파싱을 고치는 도중 겪었다).

### 적합은 별도 프로세스에서 돈다

적합은 14초쯤 걸리는데 대부분이 numpy/statsmodels 안에서 **GIL 을 쥔 채** 도는 연산이다.
FastAPI 가 동기 엔드포인트를 스레드풀에 넘겨도 GIL 은 풀리지 않아, 적합이 도는 동안
다른 모든 요청이 같이 멈춘다. `services/fit_worker.py` 가 `ProcessPoolExecutor`(워커 1개)
로 이를 분리한다.

| | 적합 | 동시 `/api/complexes` 지연(최대/중앙) | 그동안 처리한 요청 |
|---|---|---|---|
| 인프로세스 | 20.0s | 4.4s / 2.6s | 7회 |
| 별도 프로세스 | 13.6s | 2.2s / 1.9s | 10회 |

무경쟁 기준선이 1.4s 이니 거의 회복된다. 설계 메모:

- 워커는 **자기 세션을 연다**. 세션·커넥션은 프로세스 경계를 넘길 수 없다. 넘기는 것은
  `(months, spec)` 뿐이고 결과는 피클로 돌아온다(119KB, 3ms).
- 같은 키의 동시 요청은 `_inflight` 로 묶어 **한 번만** 계산한다. 안 그러면 탭 두 개만
  열어도 14초짜리 적합이 두 번 돈다.
- 풀은 재사용한다. 윈도우는 spawn 이라 자식이 pandas/statsmodels 를 다시 import 하는 데
  몇 초 걸리는데, 살려 두면 그 비용은 첫 적합 한 번뿐이다(1회차 13.2s → 2회차 9.1s).
- **실패하면 인프로세스로 떨어진다.** 프로세스 생성이 막힌 환경에서도 앱은 돌아야 한다.
  `FIT_IN_PROCESS=1` 로 강제할 수도 있다.
- 시작할 때 백그라운드로 **예열**한다(`FIT_WARM=0` 으로 끔). 첫 사용자가 14초를 기다릴
  이유가 없고, 동 프리미엄처럼 적합이 있어야 붙는 정보가 첫 화면부터 나온다.

탭은 다섯이다. **시장 분석**은 요인별 보정계수 전용, **단지 비교**는 구간 기반 기술통계,
**지도 · 거리 모델**은 연속 거리 모델링 경로, **매물 분석**은 진단과 비교를 한 화면에서 쓴다.

### 시장 분석 = 보정계수만

예전에는 구간별 평당가 분포(층·입지·연식·면적대)와 월별 추이를 같이 깔았는데, 한 화면에
**성질이 다른 두 숫자**가 있으니 계속 헷갈렸다. 구간별 평당가는 다른 요인이 섞인 관측값이고
보정계수는 나머지를 고정한 순효과다. 역에서 먼 단지에 마침 신축이 많으면 '입지별 평당가'는
거리 효과를 거꾸로 보여 준다. 이 탭이 답할 질문은 "무엇이 가격을 얼마나 움직이나" 하나이고
그 답은 보정계수 쪽이므로, 평당가 분포는 걷어내고 보정계수만 남겼다(실제 분포는 단지 비교·
지도 탭에 있다).

필터도 **분석 기간만** 남겼다. 자치구·면적대 같은 필터는 모델 적합 대상을 바꾸지 않아서
(계수는 전체 표본에서 추정된다) 눌러도 아무 일이 없었다.

## 실제 데이터 연결

`scripts/seed_demo.py` 가 만드는 데이터는 **합성 데이터**다. 단지명·법정동·역 정보는 실제
수원시 기준이지만 가격과 거래 건수는 시뮬레이션이므로 실제 시세 판단에 쓰면 안 된다.

실거래가를 쓰려면 `backend/.env` 에 키를 넣는다.

| 키 | 위치 | 발급처 | 없으면 |
|---|---|---|---|
| `MOLIT_SERVICE_KEY` | `backend/.env` | [공공데이터포털 — 국토교통부_아파트 매매 실거래가 **상세** 자료 (15126468)](https://www.data.go.kr/data/15126468/openapi.do) 의 일반 인증키(Decoding) | 합성 데이터로 동작 |
| `KAKAO_REST_KEY` | `backend/.env` | [카카오 개발자센터](https://developers.kakao.com) > 내 애플리케이션 > 앱 키 > REST API 키 | 단지 수집·좌표 조회 불가 |
| `VITE_KAKAO_JS_KEY` | `frontend/.env.local` | 같은 카카오 앱의 **JavaScript 키** (REST 키와 다른 키) | 지도 탭이 설정 안내로 대체 |
| `TMAP_APP_KEY` | `backend/.env` | [SK open API](https://openapi.sk.com) > 보행자 경로안내 | 직선거리×1.25 추정치로 자동 폴백 |

카카오 JS 키를 쓰려면 개발자센터 > 플랫폼 > Web 에 `http://localhost:5173` 과
`http://127.0.0.1:5173` 을 **둘 다** 등록해야 한다. 카카오는 origin 을 완전일치로 검사하고
Vite 는 127.0.0.1 로 프록시한다.

이름이 거의 같은 **국토교통부_아파트 매매 실거래가 자료(15126469)** 를 신청하면 안 된다.
그쪽은 동 정보(`aptDong`)와 계약 해제 여부(`cdealType`)가 빠져 있어, 해제된 거래를
걸러내지 못하고 시세가 위로 왜곡된다.

인증키는 **Encoding / Decoding 두 가지로 발급**되는데 이 프로젝트는 `httpx` 가 쿼리스트링을
직접 인코딩하므로 **Decoding 키**를 넣어야 한다. Encoding 키를 넣으면 이중 인코딩되어
`SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 난다.

활용신청은 자동승인이지만 키가 실제로 활성화되기까지 보통 **수십 분에서 1시간** 걸린다.
바로 호출해서 오류가 나면 조금 기다렸다가 다시 시도할 것. 개발계정 트래픽은 일 10,000건이며,
수원시 4개 구 × 24개월 = 96회 호출이라 넉넉하다.

### API 재호출 방지

한 번 받은 것은 다시 받지 않는다. 스크립트를 여러 번 돌려도 안전하다.

| 스크립트 | 건너뛰는 조건 | 다시 받으려면 |
|---|---|---|
| `geocode` | `Complex.lat` 이 이미 있으면 | `--force` |
| `seed_stations` | 역 좌표가 이미 있으면 | `--force` |
| `route_walk` | `routed_at` 있고 출처가 `tmap` 이면 | `--force` |
| `ingest_trades` | 그 (구, 월) 조합이 이미 적재돼 있으면 | `--refetch-all` |

**국토부만 예외가 있다.** 실거래 신고 기한이 계약 후 30일이라 지난달 데이터도 계속
늘어난다. 그래서 **최근 3개월은 항상 다시 받는다**(`--refetch-recent N` 으로 조절).
덕분에 24개월 재실행이 96회 호출 → 12회, 3~4분 → 12초가 된다.

```bash
cd backend
python -m scripts.ingest_trades --months 24   # 수원시 4개 구 실거래 적재
python -m scripts.geocode                     # 좌표 변환 + 최근접 지하철역 거리
python -m scripts.seed_stations --force       # 역 좌표 채우기
python -m scripts.route_walk                  # 도보 경로 (TMap 키 있으면 실거리)
python -m scripts.geocode_dongs               # 동별 좌표 + 동별 역거리
python -m scripts.ingest_kapt --check         # 세대수 (K-apt 활용신청 필요)
```

**스키마를 바꿨을 때**는 `--recreate-schema` 로 통째로 다시 만드는 대신
`python -m scripts.migrate` 로 빠진 컬럼만 추가한다. 실데이터가 들어 있으면
재생성에 API 호출 수십 분이 다시 들기 때문이다. 컬럼 추가만 하고 타입 변경·삭제는
하지 않으므로, 그런 변경에는 여전히 재생성이 필요하다.

### 세대수 (K-apt)

data.go.kr 은 **계정당 인증키가 하나**라 기존 `MOLIT_SERVICE_KEY` 를 그대로 쓴다.
다만 서비스마다 활용신청은 따로 해야 한다(자동승인).

- [공동주택 기본 정보제공 서비스 (15058453)](https://www.data.go.kr/data/15058453/openapi.do) — 세대수·동수
- [공동주택 단지 목록제공 서비스 (15057332)](https://www.data.go.kr/data/15057332/openapi.do) — 단지코드

`python -m scripts.ingest_kapt --check` 가 신청 상태를 알려준다. 응답 코드로 구분한다 —
**30번은 "경로는 맞는데 미신청"**, 12번은 "경로가 틀림". 이 둘을 구분해야
신청을 더 해야 하는지 코드를 고쳐야 하는지 알 수 있다.

K-apt 에서 밟은 함정 셋. 전부 **오류 없이 조용히 빈 결과**가 되는 종류다.

1. **오퍼레이션 이름 끝의 `4`.** 서비스가 `AptListService4` 면 오퍼레이션도
   `getSigunguAptList4` 다. `getSigunguAptList` 로 부르면 코드 12 가 오는데,
   미신청과 구분이 안 돼 원인을 찾기 어렵다.
2. **응답 모양이 서비스마다 다르다.** 단지목록은 `body.items.item`, 기본정보는
   `body.item` (복수형이 아니다).
3. **세대수가 `1240.0` 처럼 실수로 온다.** `int("1240.0")` 은 ValueError 라
   float 을 거쳐야 한다. 안 그러면 호출은 성공하는데 세대수만 전부 None 이 된다.

단지 매칭은 K-apt 이름에 붙은 **지역 접두어**를 벗겨야 한다
(`정자동 송학아파트` vs 국토부 `송학`). 다만 이름만으로 붙이면 위험해서
**준공년도 교차검증**(K-apt 와 국토부가 독립 보고한 값이 1년 이내)을 함께 건다.
접두어 처리로 매칭이 154 → 264곳으로 늘었다.

### 단지를 늘리기 (카카오 키만 있으면 국토부 키 없이도 가능)

기본 시드의 25곳으로는 2단계 회귀 표본이 부족하다. 특히 강남접근성 항은 유효 클러스터가
4개 수준이라 해석이 어렵다. 카카오로 실제 단지를 수집해 250~300곳으로 늘린다.

```bash
python -m scripts.fetch_complexes --dry-run   # 먼저 눈으로 검수
python -m scripts.fetch_complexes --max 300
python -m scripts.seed_stations --force
python -m scripts.route_walk
python -m scripts.seed_demo                   # 늘어난 단지로 거래 재생성
python -m scripts.validate_model --coverage 40
```

`--dry-run` 을 **반드시 먼저** 돌려 법정동별 단지 수와 제외된 POI 목록을 확인할 것.
키워드 검색에는 상가·관리사무소·중개업소가 섞여 들어오고, 경계 타일은 용인 기흥이나
화성 병점을 끌어온다. 필터가 잡고 있지만 눈으로 한 번 보는 게 싸다.

`ingest_trades` 는 계약 해제건(`cdealType == "O"`)을 제외하고, 동일 거래를
`(단지, 계약일, 전용면적, 층, 거래금액)` 으로 중복 제거한다. 여러 번 돌려도 안전하다.

단지 식별은 단지명 완전일치가 아니라 **정규화 키**(`pricing.name_key`)로 한다. 카카오는
`래미안영통마크원2단지`, 국토부는 `래미안 영통 마크원 2단지` 를 주기 때문이다. 완전일치로
두면 국토부 적재 시 고아 중복 단지가 생기고, 지오코딩·TMap 호출을 태운 행에 거래가 하나도
붙지 않는다. `N차` 는 정규화하되 **제거하지 않는다** — 래미안1차와 2차는 실제로 다른 단지다.

## 알려진 한계

- **매물 호가는 수동 입력**이다. 네이버부동산 등 호가 데이터는 공식 API가 없고 스크래핑은
  이용약관 위반 소지가 있어 PoC에서 제외했다. 대신 사용자가 **텍스트를 붙여넣으면**
  단지·면적·층·호가를 뽑아 채워 준다(위 '매물 비교' 참조). 링크는 지원하지 않는다 —
  긁어오지 않겠다는 결정이기도 하고, 애초에 링크에 매물 정보가 들어 있지 않다.
- 단지 최고층이 실제 최고층이 아니라 관측 최고 거래층이므로, 거래가 적은 단지에서는
  "최상층" 판정이 부정확할 수 있다.
- 도보거리 정밀도에는 **살 수 없는 한계**가 있다. 카카오가 주는 단지 좌표는 중심점 하나인데
  한국 아파트 단지는 폭이 200~400m라 보행 출입구가 중심에서 300m 떨어질 수 있다. TMap 을
  써도 ±150m 는 남는다. TMap 의 가치는 정밀도가 아니라 **체계적 장벽**(경부선·원천리천·
  영동고속도로) 포착이다 — 분산이 아니라 편향 교정이라, R² 급등이 아니라 특정 단지가 크게
  움직이는 것을 기대해야 한다.
- `seed_stations.py` 의 **강남 소요시간은 현재 추정치**다. 실제 길찾기로 검증해 교체해야
  한다. 합성 데이터 단계에서는 시드와 모델이 같은 표를 읽으므로 복원 검증은 값과 무관하게
  성립하지만, 실거래가로 전환할 때는 실측이 필요하다.
- 강남 접근성은 구 고정효과와 상관이 높다. 신분당선 역(광교·상현)이 전부 영통구/이의동에
  몰려 있어 두 변수가 같은 것을 가리키는 구간이 있다. 계수는 보고하되 과신하면 안 된다.
- 단지 수가 적으면(120곳 미만) 강남 항의 유효 클러스터가 4개 수준이라 해석이 어렵다.
  도보 곡선은 그보다 적은 표본에서도 살아남는다.
- 동향·조망·리모델링 여부·학군 등 가격에 영향을 주는 다른 요인은 반영하지 않는다.
  모델 잔차에 이것들이 전부 섞여 있다. 결과는 참고용이며 투자 판단의 근거로 쓸 수 없다.
