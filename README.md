# 경기 남부 아파트 적정 시세

국토교통부 실거래가를 기반으로 아파트 매물의 적정 시세를 산출하는 웹 서비스.
대상은 **수원 생활권**(수원·용인·화성·안양·오산·의왕·군포·과천, 17개 시군구)의
아파트 매매다. 수원 4개 구로 시작해 인접 시로 넓혔다 — 요인별 보정계수를 더 촘촘히
보려면 요인이 실제로 변해야 하는데, 한 도시 안에서는 강남 접근성이 30~65분 구간에
몰려 있어 곡선의 양 끝이 식별되지 않았다.

## 핵심 설계 결정

### 1. 평당가는 전용면적 기준

```
전용 평당가 = 거래금액(만원) ÷ (전용면적㎡ ÷ 3.305785)
```

공급면적이 아니라 **전용면적**을 분모로 쓴다. 같은 집이라도 공급면적 기준보다 25~35% 높은
숫자가 나오지만, 전용률(전용/공급)이 단지마다 70~80%로 제각각이라 공급면적 평당가는
단지 간 비교 기준이 되지 못한다. 국토교통부 실거래가 원본도 전용면적만 제공한다.

공급면적은 매물 입력 시 선택 항목으로만 받아 전용률 계산과 환산 표기에 쓴다.

### 2. 세 가지 비교 축

| 축 | 구간 | 기준 |
|---|---|---|
| **층** | 1층 / 저층 / 중층 / 고층 / 최상층 | 단지 최고층 대비 상대 위치 (~25% 저층, ~65% 중층) |
| **입지** | 초역세권(5분) / 역세권(10분) / 준역세권(15분) / 비역세권 | 최근접 지하철역까지 직선거리 400·800·1200m |
| **컨디션** | 신축(5년) / 준신축(10년) / 10~15 / 15~20 / 20~30 / 30년 초과 | 준공년도 기준 경과 연수 |

단지 최고층은 국토교통부 API가 주지 않으므로 **관측된 최고 거래층**을 추정치로 쓴다.
도보 시간은 직선거리에 보행 경로 보정(×1.25)을 한 뒤 분당 67m로 환산한다.
(분양 광고 관행인 "1분 = 80m"는 실제 보행 속도보다 빠르게 잡힌 값이라 쓰지 않았다.)

여기에 **노선 · 생활권(최근접역) · 단지 규모(세대수)** 필터가 더 붙는다.

| 필터 | 기준 | 비고 |
|---|---|---|
| 지하철 노선 | 큐레이션한 `Station.line` | 1호선 / 수인분당선 / 신분당선 |
| 생활권 | 최근접역 이름 | 노선을 고르면 그 노선 역만 남는다 |
| 단지 규모 | 세대수 300/600/1000/1500 구간 | K-apt 미매칭 단지는 '정보없음' |

노선·역은 카카오가 준 `Complex.station_line`('수도권1호선')이 아니라 **큐레이션한
Station 테이블**을 쓴다. 표기가 달라 필터 값과 화면 표시가 어긋나면 안 되기 때문이다.
필터 선택지도 고정 목록이 아니라 **실제로 단지가 붙어 있는 역**만 내보낸다 —
단지가 없는 역을 띄우면 고르는 순간 빈 화면이 된다.

> **생활권 필터의 한계**: 최근접역 기준이라, 역에서 먼 단지도 어딘가에는 배정된다.
> 예를 들어 우만동 월드메르디앙은 '광교중앙역 생활권'이지만 실제로는 도보 33분이다.
> 생활권으로 좁힐 때는 **입지 등급 필터를 함께** 거는 것이 안전하다.

위 구간은 **시장 분석 / 단지 비교 / 매물 진단** 탭이 쓰는 기술통계 축이다.
역거리를 자르지 않고 연속으로 보는 경로는 아래 6번의 헤도닉 모델이 따로 담당한다.

### 매물 분석 (적정가 진단 + A·B 분해)

한 화면에서 **두 가지 질문**에 답한다. 원래 탭이 갈려 있었는데, 실제로는 같은 매물에
대해 연달아 묻게 되는 질문이라 입력을 두 번 하게 됐다.

| | 묻는 것 | 단지 고유 프리미엄 |
|---|---|---|
| **적정가 진단** | 그 단지 같은 평형 시세 대비 이 호가가 적정한가 | 값에 이미 포함 |
| **요인별 비교** | A와 B 중 요인을 감안하면 어느 쪽이 싼가 | 빼고 펀더멘털만 |

둘은 다른 질문이라 답이 갈릴 수 있다. 재건축 기대가 붙은 단지는 "그 단지 시세로는
적정"인데 "펀더멘털 대비로는 비쌈"이 된다. 갈리는 것 자체가 정보다.

한쪽만 채우면 그쪽 진단만, 양쪽을 채우면 진단 두 장 + 비교까지 나온다.

요인별 비교는 평당가 차이를 **요인별 기여로 쪼갠다**. "A가 두 배 비싼데 왜 싸다는
거냐"에 대한 답이 표에 그대로 나온다.

```
A 자연앤힐스테이트 (이의동, 84.9㎡, 15층, 13.5억)
B 매탄주공5       (매탄동, 84.9㎡, 15층,  6.2억)

  역까지 도보   2.0분 vs 15.5분    +17.1%
  강남까지     35분  vs 58분       +8.1%
  연식        14년  vs 41년       +58.3%
  지하철 노선   신분당선 vs 수인분당선  +28.5%
  ──────────────────────────────────────
  모델 예상 차이                  +157.6%
  실제 호가 차이                  +117.7%
  → A가 15.5% 저렴
```

#### 입력 — 텍스트를 붙여넣으면 자동으로 채워진다

매물 화면의 텍스트를 그대로 붙여넣으면 단지·전용면적·층·호가를 뽑아 채운다.
붙여넣는 순간 돌아가고, 버튼을 한 번 더 누를 필요가 없다.

화면에 보이는 것은 **붙여넣기 칸과 채워진 값 요약**뿐이다. 검색창·필터·목록·입력칸은
'직접 입력' 토글 뒤에 접어 둔다 — 붙여넣기 한 번으로 끝나는 것이 기본 동선인데
입력칸이 전부 펼쳐져 있으면 그쪽이 기본처럼 보인다. 단, **파싱이 단지나 면적을
못 채웠으면 자동으로 펼친다.** 접힌 채로 두면 손댈 곳이 안 보여 막힌다.

```
힐스테이트푸르지오수원 103동
매매 9억
3,360만원/3.3㎡평당가 도움말
알림관심매물
공유하기
아파트88B㎡ (전용59B)8/15층남향
```

화면을 통째로 긁어 와 버튼 문구(`도움말`·`공유하기`)가 섞여도 쓸 줄만 골라 읽는다.
`아파트88B㎡ (전용59B)` 에서 **전용 59㎡** 를 집고(타입 문자 `B` 는 평면 변형이라
면적과 무관하다), `8/15층` 에서 8층·총 15층을, `매매 9억` 에서 90,000만원을 뽑는다.

**평당가 기준이 다른 것도 짚어 준다.** 위 매물에 적힌 평당가는 3,360만원/평인데
이 서비스는 5,043만원/평로 계산한다. 틀린 게 아니라 분모가 다르다 — 네이버는
공급 88㎡, 이 서비스는 **전용 59㎡** 기준이다(이 프로젝트의 출발점이 바로 그것이다).
적힌 평당가와 호가로 분모를 역산해 공급 기준이면 경고로 알려 준다. 50% 차이가
설명 없이 나오면 어느 한쪽이 틀린 줄 알기 때문이다.

다른 표기도 받는다.

```
자연앤힐스테이트 101동
매매 13억 5,000
아파트 · 112.9/84.97㎡, 중층, 남향
```

- **단위는 적힌 대로 읽고, 평은 1평 = 3.305785㎡ 로 환산한다.** 파싱 전에 한 번
  환산해(`normalize_pyeong`) 단위를 통일하므로, `34평/25.7평` 같은 공급/전용 쌍도
  ㎡ 쌍과 똑같이 뒤쪽을 전용으로 잡는다. `30평대`(범위)·`평당가`(단가)는 면적이
  아니므로 건드리지 않고, 숫자와 '평'은 **같은 줄**에서만 잇는다 — 줄을 넘게 두면
  `매매 3억 9,000` 다음 줄의 `평당가` 와 붙어 `000평` → 0평 이 된다.
- **괄호 안 전용은 앞의 공급에서 단위를 물려받는다.** 네이버는 `아파트17평 (전용12)`
  처럼 전용 쪽 단위를 생략하는데, 이때 12는 12㎡ 가 아니라 **12평(39.7㎡)** 이다.
  단위 없는 숫자를 일괄로 ㎡ 취급하면 맞는 평형이 사라져 면적 칸이 빈 채로 남는다.
  `88B㎡ (전용59B)` 는 공급이 ㎡ 라 이 규칙에 걸리지 않고 그대로 ㎡ 로 읽힌다.
- **'전용' 표기가 없는 면적은 공급으로 본다.** 광고의 `34평`·`112㎡`는 거의 항상
  공급면적이다. 그대로 전용에 넣으면 112㎡ 전용을 가진 단지가 아닌 한 "그런 평형 없음"
  으로 비워진다. 그래서 **어느 해석이 맞는지 데이터에 물어본다** — 숫자가 그 단지의
  전용 평형과 바로 맞으면 전용, 아니면 전용률 0.60~0.90 안에 드는 평형을 찾고, 여럿이면
  거래가 가장 많은 쪽을 고른다(`routers/model._resolve_area`). `34평` → 전용 84㎡
  (전용률 75%), `25평` → 전용 60㎡ (73%). 둘 다 아니면 비우고 직접 고르게 한다.
- `전용59B` `112.9/84.97㎡` `34평/25.7평` → 전용면적 ㎡. 한 쌍이면 뒤쪽이 전용이다.
  뽑은 값은 그 단지의 실제 평형으로 맞춘다(59 → 60㎡).
- `8/15층` → 8층. 뒤의 15는 **건물 실제 최고층**이라 층 구간 판정에 쓴다. DB 의
  `max_floor` 는 거래에서 관측된 최고층이라 거래가 적은 단지에서는 실제보다 낮다.
- `129동` → **역까지 도보를 그 동 좌표로 잡는다.** 동이 없으면 단지 중심점을 쓴다.
  수원센트럴아이파크자이는 129동이 19.9분, 104동이 12.4분으로 **단지 안에서만 8.4분**
  벌어진다. 중심점 하나(16.2분)로는 이 차이가 통째로 사라진다.

  동 편차에 단지 간 계수를 그대로 쓰면 안 된다. 단지 간 도보 계수(-1.083%/분)는
  입지 전반을 함께 싣고 있어 동 편차 계수(-0.355%/분, t=-9.7, n=20,211)의 3배다.
  그래서 **단지 중심점까지는 스플라인, 거기서 동까지의 편차는 within 계수**로 나눠
  더한다. 후자는 단지 고정효과와 직교하게 추정된 값이라 학군·브랜드·연식·구 입지가
  전부 통제돼 있다.

  직접 입력 패널의 동 선택은 `GET /api/complexes/{id}/dongs` 가 주는 실제 동 목록에
  동별 도보시간과 시세 프리미엄을 붙여 보여 준다 — 타이핑하면 오타도 나고 그 동이
  얼마나 먼지·비싼지도 모른다. 좌표를 못 잡은 동(전체의 19%)은 중심점으로 떨어진다.

### 동 프리미엄 — 재보니 평형 교란이었다

층 프리미엄은 처음부터 있었는데 동 프리미엄은 없어서, Stage 1 잔차를 단지 안에서
동별로 평균 내 봤다. τ=2.50%, 신호비 48% 라는 그럴듯한 값이 나왔고 수원센트럴아이파크자이
129동은 -8.66%(42건) 가 찍혔다. **전부 틀린 값이었다.**

**무엇이 틀렸나.** 그 단지에서 40㎡ 는 129동·130동에만 있고 나머지 28개 동은 60~103㎡ 뿐이다.
전역 면적 스플라인이 이 단지의 40㎡ 를 10%쯤 비싸게 예측하면 그 오차가 갈 곳은 129·130동의
'동 효과' 밖에 없다. 실거래를 직접 보면 두 동은 **같은 전용 39.77㎡ 유닛이고 평당가 중앙값이
3,076 으로 똑같다**. 동 위치 차이가 아니라 평형 차이를 보고 있었던 것이다.

여기에 수축까지 겹쳐 더 나빠졌다. 129동(42건, 수축 0.83)은 -8.66%, 130동(3건, 수축 0.26)은
-2.30% 가 됐는데, 두 동의 실제 가격은 같다. **6%p 격차가 순전히 표본 수 차이에서 나왔다.**
적정가 진단에서 129동 3,280원/평 vs 130동 3,531원/평 이라는 없는 차이를 만들어 냈다.

**고친 방법.** `(단지 × 평형)` 셀 안에서 잔차를 한 번 더 차감한 뒤 동별로 평균 낸다. 같은
평형을 나눠 갖는 동끼리만 비교되고, 같은 평형이 한 동에만 있으면 **식별 불가**로 빼 버린다
(403개 동). 129동은 -10.33% → **-0.13%**, 130동은 -8.58% → +1.82% 로 둘 다 0 근처가 된다.

**결과: τ = 0.00%.** 검출력을 보정해 보면(참 효과를 심고 되찾는 시뮬레이션)

| 심은 참 τ | 되찾은 값 |
|---|---|
| 1.0% | 0.00% (못 잡음) |
| 1.5% | 0.94% |
| 2.0% | 1.39% |
| 3.0% | 2.53% |

검출 한계는 **τ≈1.2%** 다. 즉 평형을 통제한 동 효과는 그보다 작고, 이 표본으로는
있다/없다를 말할 수 없다. 시장 분석 탭의 '동 위치' 카드는 0짜리 막대 다섯 개 대신
**"검출되지 않았습니다"** 와 그 한계를 적는다 — 0 을 그리면 '동은 가격과 무관' 으로
읽히는데 실제로는 '잴 수 없다' 이기 때문이다.

동 위치가 가격에 미치는 영향 중 이 표본에서 잡히는 경로는 **역까지 도보거리뿐**이다
(`dong_walk_dev`, -0.355%/분, t=-9.7, n=20,211). 그쪽은 위에서 설명한 대로 살아 있다.

> **교훈**: 단지 고정효과만으로는 부족했다. 동과 평형이 붙어 있는 단지에서는 다른 항의
> 오차가 통째로 동 효과로 흘러든다. 잔차 평균으로 무언가를 뽑을 때는 **그 무언가와
> 공선인 것이 무엇인지** 먼저 따져야 한다.

### 요인별 적정가 — 매물 하나를 분해한다

기존 '요인별 기여' 표는 **A−B 상대 차이**만 냈다. 그래서 두 가지가 안 됐다.

- 같은 단지 두 매물(129동 vs 130동)을 넣으면 단지 요인이 전부 0% 라 표가 텅 빈다.
- 한쪽만 넣으면 아예 나오지 않는다.
- 금액이 없다. % 기여만 있고 "그래서 얼마인가" 가 빠져 있다.

`model_view.model_price()` 가 매물 **하나**를 절대값으로 분해한다. α̂_c 는
`전용 84㎡ · 중층 · 최신월` 기준이므로, 거기에 이 매물의 면적·층·동 도보편차를 더해
해당 유닛으로 옮긴다. 출발점을 무엇으로 두느냐에 따라 두 값이 나온다.

| | 출발점 | 답하는 질문 |
|---|---|---|
| **실거래 기준** | 같은 단지·평형 실거래 | 이 단지 이 평형이 실제로 얼마에 팔리나 |
| **요인 기준** | Stage 2 예측 α̂ | 거리·연식·세대수·노선·구만으로 얼마여야 하나 |
| **시장 기준** | 관측 α̂_c | (내부 검산용 — 아래 참조) |

둘의 차이가 그 단지에 붙어 있는 **고유 프리미엄**이다. 학군·브랜드·재건축 기대처럼
측정하지 않은 것이 거기 들어 있다.

#### 면적 곡선 교정 — 안 하면 34% 틀린다

모델은 `α_c + f(면적) + 층` 인데 `f` 는 **전 단지 공통 곡선**이다. 어떤 단지의 40㎡가
84㎡ 대비 얼마나 싼지는 단지마다 다른데 공통 곡선은 그 차이를 못 담는다. 실제로
수원센트럴아이파크자이 40㎡ 에서 모델의 **시장 기준 46,111만원**이 같은 평형
**실거래 기준 40,532만원**보다 14% 높게 나왔다. 교정 없이 내보내면 요인 기준이
5.36억 — 실거래 4.05억짜리 집에 대해 +32% 짜리 숫자가 나간다.

두 값은 같은 질문("이 단지 이 유닛이 지금 얼마에 팔리나")의 답이므로, **어긋난 만큼이
곧 면적 곡선의 이 단지·이 평형 오차**다. 비율로 뽑아 요인 기준에도 먹인다.

    보정계수 = 실거래 기준 평당가 / 모델 시장 기준 평당가

단지 간 펀더멘털(Stage 2)은 건드리지 않고 **단지 안에서의 유닛 환산만** 고친다.
130동 20층: 원값 5.36억 → 교정 **4.74억**(보정 -12.1%). 실거래 비교가 없으면 교정할
수 없으므로 원값을 쓰고 그 사실을 남긴다. 2배 넘게 벌어지면 교정이 아니라 다른 데가
고장 난 것이라 손대지 않는다.

#### 화면

```
실거래 기준 4.05억      요인 기준 4.74억      단지 고유 프리미엄 -14.5%
같은 단지·평형 56건      펀더멘털만            요인으로 설명 안 되는 부분
호가 -12.4%             호가 -25.1%

단지 — 어디에 있는 아파트인가
  역까지 도보    16.2분        -8.9%
  강남까지 전철  60분          -0.7%
  연식          2년          +46.9%
  세대수        3,432세대      +8.3%
  지하철 노선    수인분당선     -11.7%
유닛 — 그 안에서 어느 집인가
  전용 40㎡                  -17.8%
  고층                        +0.7%
  130동 도보 20.8분 (단지 평균 16.7분)  -1.6%
```

두 판정이 갈릴 수 있고, **갈리는 것 자체가 정보다**. 이 매물은 실거래 대비 -12%인데
펀더멘털 대비로는 -25%다. 차이는 이 단지가 요인 대비 14.5% 낮게 거래된다는 뜻이다.

A·B 비교의 요인별 기여 표는 그대로 둔다 — 그쪽은 **상대 차이**를 묻는 다른 화면이다.

### 호가 누적 — 실거래가 못 잡는 것

실거래는 **팔린 것만** 남긴다. 값을 못 받는 매도자는 싸게 파는 대신 물건을 거둬들이므로,
거래가 뜸한 구간의 관측 거래가는 **위로 편향**된다(constant-liquidity index 문헌의 고전적
문제다). 내려간 물건은 거래가 아니라 호가에만 있다.

수원센트럴아이파크자이가 그 사례다. 129동과 130동은 **구조가 같은데도** 같은 기간 거래가
42건 대 3건이고, 그 3건은 시점보정하면 129동보다 오히려 **비싸게** 찍힌다(3,405 vs 3,306).
실거래만 보면 "130동에 디스카운트 없음" 이라는 결론이 나오지만, 팔리지 않는 물건이
호가로 얼마에 나와 있는지를 데이터가 통째로 놓치고 있는 것이다.

그래서 **붙여넣기마다 호가를 쌓는다**(`services/quotes.py`). 따로 '저장' 을 누르게 하면
아무도 안 누르므로, 매물 텍스트를 붙여넣는 것만으로 기록된다.

**중복 처리**가 이 기능의 핵심이다.

- 같은 `(단지·동·평형·층·호가)` 가 다시 들어오면 새로 쌓지 않고 `last_seen_at` 과
  `seen_count` 만 올린다. 같은 매물을 몇 번을 붙여넣어도 표본이 부풀지 않는다.
- **가격이 바뀌면 새 행**이 된다. 그 변화가 바로 보고 싶은 신호다 —
  130동 3.55억 → 3.38억 → 3.20억 같은 경로가 그대로 남는다.
- 층·동을 모르면 NULL 이 아니라 `0`/`""` 를 쓴다. SQLite 의 UNIQUE 제약은 NULL 끼리를
  서로 다른 값으로 보기 때문에, NULL 을 두면 중복이 그대로 쌓인다.

집계는 최근 90일 안에 확인된 호가만 본다. 매물은 팔리거나 내려가는데 우리는 내려간 걸
알 방법이 없어서, 시간으로 끊는 수밖에 없다.

### 한 줄 = 한 (단지·동·평형·층대)

순위표가 한 층대 매물로 도배되면 아무것도 안 보인다. 실제로 130동 40㎡ 고층대에만
매물이 여덟 건 올라와 있었다. 그렇다고 합쳐 버리면 실재하는 매물이 사라진다.
그래서 **접는다** — 대표 한 줄만 표에 두고, 몇 건인지 배지로 밝히고, 전부는 호버로
펼친다. 숨기는 게 아니라 한 단계 뒤로 미루는 것이다.

대표는 **가장 최근 확인된 것**, 같은 날이면 **가장 싼 것**이다. 사는 쪽이 실제로 보는
값이고, 무엇보다 결정적이라 새로고침해도 순서가 흔들리지 않는다.

#### 확인일자를 버리지 않는다

각 매물에는 `집주인확인매물 2026.09.23` 같은 **확인일자**가 붙어 있다. 처음에는 이 줄을
중개사명·홍보문구와 함께 노이즈로 버렸는데, 그러면 안 됐다. 우리가 언제 봤는지
(`first_seen_at`)는 한 번에 붙여넣은 매물이 전부 같아서, 목록 안에서 시점을 가르는 데
쓸 수 없다. 매물이 언제 시점의 것인지 말해 주는 단서는 이 날짜뿐이다.

읽어 보니 한 번에 붙여넣은 46건의 확인일자가 `2026-08-28 ~ 2026-09-23` 에 걸쳐 있었다.
이제 순위표에 **확인** 열로 뜨고, '확인일자' 필터가 실제로 동작한다(최근 7일 47줄 /
전체 58줄). 날짜를 못 읽은 매물은 거르지 않고 남긴다 — 읽기 실패를 '오래된 매물' 로
바꿔 조용히 숨기면 안 된다.

#### 같은 집이 값을 바꾼 경우는 따로 가른다

가격이 바뀌면 새 행이 되므로, 한 집이 3.8억 → 3.55억 으로 내리면 두 행이 된다. 이건
접는 게 아니라 **잇는 것**이고, `▼ 6.6%` 배지로 변동을 표시해야 한다.

문제는 '같은 집' 을 알아보는 일이다. 목록에 **호는 나오지 않는다**. 층을 `고층` 으로만
밝힌 매물은 그 구간의 대표층(총 23층이면 19층)으로 채워지므로, `(단지·동·평형·층)` 이
같다고 해서 같은 집이라는 보장이 없다. 확인일자도 답이 못 된다 — 네이버는 **지금 올라와
있는 매물만** 보여 주므로 그 날짜는 '마지막으로 확인된 날' 이지 '언제까지 있었나' 가
아니다. 실제로 130동 고층대 다섯 건 중 네 건이 `09-21` 같은 날이었다.

그래서 **생존 구간**으로 가른다. 한 집의 호가가 바뀌면 옛 호가는 목록에서 사라지므로
`last_seen_at` 이 그 시점에 멈춘다. 반대로 함께 올라와 있는 매물들은 같은 목록에 있으므로
`last_seen_at` 이 나란히 갱신된다. 구간 `[first_seen, last_seen]` 이 **겹치지 않고 이어질
때만** 같은 집의 연속된 호가로 본다. 구간 분할(interval partitioning)과 같은 문제로,
겹치는 구간의 최대 개수가 곧 유닛 수다.

```
잇는다 (같은 집)                  접는다 (동시 매물)
3.8억  09-26 ~ 09-28              3.8억  09-26 ~ 09-30
3.55억 10-01 ~ 10-03              3.55억 09-26 ~ 09-30
→ 3.55억 ▼6.6% (이력 2건)         → 3.55억 [2건] 호버로 펼침
```

이어붙일 후보가 여럿일 때 사슬 **개수**는 어느 쪽을 골라도 같지만(구간 분할의 성질)
어느 호가가 어느 호가의 다음인지는 달라진다. 사라진 직후에 나타난 쪽이 이어졌을
가능성이 높으므로 가장 늦게 비워진 사슬에 붙이고, 후보가 둘 이상이었으면 배지에 `?` 를
붙여 **경로가 추정임을 밝힌다**. 추측을 사실처럼 보여 주지 않기 위해서다.

같은 이유로 현재 호가 집계(`summary`)도 유닛마다 최신 행만 쓴다. 값을 내린 집의 옛
호가는 이미 없는 가격인데, 그것을 중앙값에 함께 넣으면 분포가 위로 끌린다 — 하필 이
데이터를 쌓는 이유(내려간 값 포착)와 정반대 방향이다.

> 생존 구간의 시간 여유는 600초다. 두 방향의 오류는 값이 다르다 — 여유가 **짧아서**
> 동시 매물을 가격 변동으로 오인하면 없는 이력을 만든다. 여유가 **길어서** 실제 변동을
> 못 잡으면 그냥 접힌 두 건으로 보일 뿐이다. 그래서 길게 잡았다.

> **한계**: 접는 단위가 `(단지·동·평형·층)` 이라 같은 층의 서로 다른 호는 한 줄에 접힌다.
> 목록에 호가 나오지 않는 한 이 이상은 알 수 없다. 접힌 건수와 각각의 호가·확인일자를
> 호버로 전부 보여 주는 것이 이 한계에 대한 답이다.

### 순위 계산이 16.7초에서 1.1초로

대상을 넓히자 매물 순위 페이지가 눈에 띄게 느려졌다. 프로파일러가 답을 바로 줬다.

| | 이전 | 이후 |
|---|---|---|
| 순위 계산(매물 56건) | 16.7s | **1.1s** |
| `model_price` | 14.5s | 0.02s |
| `load_points` | 2.8s | 0.21s |

두 가지였고 **둘 다 지역을 넓히기 전에도 있던 낭비**다. 수원만 볼 때는 규모가
4분의 1이라 드러나지 않았을 뿐이다.

**1. 매물마다 단지 전체를 훑었다.** `model_price` 가 단지 하나를 꺼내려고 이렇게 했다.

```python
rows = {int(r["complex_id"]): r for _, r in fit["alpha"].iterrows()}
```

단지 2,018곳을 도는 데다 `iterrows()` 는 행마다 Series 를 새로 만든다. 매물 56건이면
113,008번이다. 조회표는 적합이 바뀌지 않는 한 그대로이므로, 적합 dict 에 매달아
한 번만 만든다(`model_view.fit_index`).

**2. 열 몇 개 쓰자고 ORM 객체를 만들었다.** `load_points` 가 `select(Trade, Complex)`
로 엔티티를 통째로 읽었는데, 실제로 쓰는 것은 열 열세 개뿐이다. 한 구의 24개월치가
3만 행을 넘으면서 ORM 인스턴스 생성만 31,602회였다. 컬럼만 읽도록 바꿨다.

빠르게 만든 것이 **같은 답을 내는지**는 눈이 아니라 비교가 답한다. 매물 69건 전부에
대해 캐싱 전후 결과를 통째로 비교했고(차이 0건), `load_points` 는 필터 조합 10가지를
옛 구현과 대조했다(전부 일치).

### 적합은 별도 프로세스에서 돈다

적합은 14초쯤 걸리는데 대부분이 numpy/statsmodels 안에서 **GIL 을 쥔 채** 도는 연산이다.
FastAPI 가 동기 엔드포인트를 스레드풀에 넘겨도 GIL 은 풀리지 않아, 적합이 도는 동안
다른 모든 요청이 같이 멈춘다. `services/fit_worker.py` 가 `ProcessPoolExecutor`(워커 1개)
로 이를 분리한다.

| | 적합 | 동시 `/api/complexes` 지연(최대/중앙) | 그동안 처리한 요청 |
|---|---|---|---|
| 인프로세스 | 20.0s | 4.4s / 2.6s | 7회 |
| 별도 프로세스 | 13.6s | 2.2s / 1.9s | 10회 |

무경쟁 기준선이 1.4s 이니 거의 회복된다. 설계 메모:

- 워커는 **자기 세션을 연다**. 세션·커넥션은 프로세스 경계를 넘길 수 없다. 넘기는 것은
  `(months, spec)` 뿐이고 결과는 피클로 돌아온다(119KB, 3ms).
- 같은 키의 동시 요청은 `_inflight` 로 묶어 **한 번만** 계산한다. 안 그러면 탭 두 개만
  열어도 14초짜리 적합이 두 번 돈다.
- 풀은 재사용한다. 윈도우는 spawn 이라 자식이 pandas/statsmodels 를 다시 import 하는 데
  몇 초 걸리는데, 살려 두면 그 비용은 첫 적합 한 번뿐이다(1회차 13.2s → 2회차 9.1s).
- **실패하면 인프로세스로 떨어진다.** 프로세스 생성이 막힌 환경에서도 앱은 돌아야 한다.
  `FIT_IN_PROCESS=1` 로 강제할 수도 있다.
- **워커는 워커를 만들지 않는다.** 이 판정을 모듈 전역(`_IS_WORKER`)으로 두었다가 한 번
  뚫렸다. 그 값은 `app.services.fit_worker` 라는 **모듈 객체**에 붙어 있어서, 워커가 같은
  모듈을 다른 경로로 한 번 더 import 하면 전역이 둘이 되고 `run()` 이 읽는 쪽은 여전히
  False 다. 실제로 앱(18008) → 워커(4356) → **또 워커(3336)** 가 잡혔고, 3336 의
  커맨드라인은 `spawn_main(parent_pid=4356)` 이었다. 워커가 워커에 적합을 맡기고 기다리는
  동안 서버 전체가 응답을 멈췄다. 지금은 `multiprocessing.parent_process()` 로 **프로세스
  단위**로 판정한다 — 메인에서만 None 이라 모듈 정체성과 무관하게 흔들리지 않는다.
- 시작할 때 백그라운드로 **예열**한다(`FIT_WARM=0` 으로 끔). 첫 사용자가 14초를 기다릴
  이유가 없고, 동 프리미엄처럼 적합이 있어야 붙는 정보가 첫 화면부터 나온다.

탭은 다섯이다. **시장 분석**은 요인별 보정계수 전용, **단지 비교**는 구간 기반 기술통계,
**지도 · 거리 모델**은 연속 거리 모델링 경로, **매물 분석**은 진단과 비교를 한 화면에서 쓴다.

### 시장 분석 = 보정계수만

예전에는 구간별 평당가 분포(층·입지·연식·면적대)와 월별 추이를 같이 깔았는데, 한 화면에
**성질이 다른 두 숫자**가 있으니 계속 헷갈렸다. 구간별 평당가는 다른 요인이 섞인 관측값이고
보정계수는 나머지를 고정한 순효과다. 역에서 먼 단지에 마침 신축이 많으면 '입지별 평당가'는
거리 효과를 거꾸로 보여 준다. 이 탭이 답할 질문은 "무엇이 가격을 얼마나 움직이나" 하나이고
그 답은 보정계수 쪽이므로, 평당가 분포는 걷어내고 보정계수만 남겼다(실제 분포는 단지 비교·
지도 탭에 있다).

필터도 **분석 기간만** 남겼다. 자치구·면적대 같은 필터는 모델 적합 대상을 바꾸지 않아서
(계수는 전체 표본에서 추정된다) 눌러도 아무 일이 없었다.

### 헤도닉 회귀란 무엇이고 왜 쓰나

아파트는 **동질재가 아니다**. 쌀 1kg 은 어디서 사든 같은 물건이라 '쌀값'이 존재하지만,
아파트는 면적·층·역거리·연식·세대수가 다 다른 **묶음상품**이라 단일한 '아파트값'이 없다.
그래서 "역에서 5분 더 가까운 것의 값"을 직접 관측할 방법이 없다. 그것만 따로 팔지 않기
때문이다.

헤도닉(hedonic) 회귀는 이 문제를 뒤집어 푼다. **묶음의 값이 속성 구성에 따라 어떻게
달라지는지**를 보고 각 속성의 **암묵가격(implicit price)** 을 역산한다. Court(1939) 가
자동차에 처음 썼고 Griliches(1961) 가 물가지수에 도입했으며, Rosen(1974) 이 균형 이론으로
정식화했다. 지금은 통계청·BLS 의 품질조정 물가지수, 환경가치 평가(소음·대기질이 집값을
얼마나 깎는가), 노동경제학의 보상임금격차 등에 표준으로 쓰인다.

**주의할 해석 문제가 하나 있다.** Rosen 의 틀에서 헤도닉 가격함수는 매수자의 입찰함수와
매도자의 제안함수가 만나 생기는 **포락선(envelope)** 이다. 수요곡선도 공급곡선도 아니다.
따라서 "도보 1분당 -1.08%" 는 **균형에서 관측되는 암묵가격**이지, 소비자가 역세권에
지불할 의향(WTP)이 아니다. 시장이 바뀌면 이 값도 바뀐다.

**주택 가격지수의 다른 계열과 비교.** 반복매매(repeat-sales, Bailey-Muth-Nourse 1963 →
Case-Shiller 1987)는 **같은 집이 두 번 팔린 것만** 써서 관측되지 않는 특성을 완벽히
통제한다. 대신 한 번만 팔린 집을 통째로 버리고, 그 사이 리모델링한 것을 가격 상승으로
오인한다. 헤도닉은 모든 거래를 쓰지만 관측 가능한 속성에만 의존한다.

이 프로젝트는 **둘의 중간**이다. 단지 고정효과가 "같은 단지가 여러 번 팔린" 구조를 이용해
관측되지 않는 단지 특성(학군·브랜드·조망)을 흡수하고, Stage 2 가 단지 **사이**의
횡단면 기울기를 따로 추정한다. 반복매매만큼 엄격하지 않지만 표본을 버리지 않는다.

### 왜 로그를 씌우나

종속변수를 $\log P$ 로 두는 이유는 네 가지이고, 첫째가 가장 중요하다.

**1. 곱셈을 덧셈으로 바꾼다.** 집값의 요인 효과는 금액이 아니라 **비율**로 움직인다.
"역세권 프리미엄 5천만원"은 3억짜리와 20억짜리에 같이 붙을 리 없다. 5% 라야 자연스럽다.
그래서 참모형은 곱셈 구조다.

$$
P \;=\; A \cdot \underbrace{e^{\beta W}}_{\text{역거리}} \cdot \underbrace{e^{\phi_b}}_{\text{층}} \cdot \underbrace{e^{\mu_m}}_{\text{시점}} \cdot \eta
$$

양변에 로그를 씌우면 곱이 합이 되어 **선형모형에 그대로 들어간다**.

$$
\log P \;=\; \log A + \beta W + \phi_b + \mu_m + \log \eta
$$

회귀는 선형결합밖에 못 다루므로, 로그가 없으면 이 구조를 표현할 수 없다. 금액 단위로
회귀하면 "역 1분당 -320만원" 같은 값이 나오는데, 이건 강남 아파트와 외곽 아파트에
같은 금액을 빼는 셈이라 둘 다 틀린다.

**2. 계수가 곧 퍼센트다.** $\partial \log P / \partial x = \beta$ 는 **준탄력성**이고,
$\beta$ 가 작을 때 $e^{\beta}-1 \approx \beta$ 다. 도보 계수 $-0.01088$ 은
$e^{-0.01088}-1 = -1.082\%$ — 코드가 굳이 $e^\beta-1$ 로 환산하는 이유다
(작은 값에서는 차이가 미미하지만 연식처럼 큰 계수에서는 벌어진다).

**3. 이분산을 완화한다.** 금액 단위에서는 비싼 집일수록 분산도 크다
($\operatorname{Var} \propto$ 수준$^2$). 로그는 이를 압축해 등분산 가정에 가깝게 만든다.
OLS 는 이분산에서도 불편(unbiased)이지만 효율을 잃고 표준오차가 틀어진다.

**4. 분포를 대칭으로 만든다.** 집값 분포는 오른쪽으로 길게 늘어진다. 로그를 씌우면
대략 정규에 가까워져 OLS 의 소표본 추론이 잘 맞는다. 하한 0 이 $-\infty$ 로 열리므로
예측값이 음수가 되지도 않는다.

**되돌릴 때의 함정 — 재변환 편의(retransformation bias).** Jensen 부등식 때문에
$\mathbb{E}[P] \neq \exp(\mathbb{E}[\log P])$ 다. 로그평균을 지수로 되돌리면 **기하평균**이
나오고, 로그정규 가정에서 이는 **중앙값**에 해당한다. 산술평균을 원하면
$\exp(\hat\mu + \hat\sigma^2/2)$ 나 Duan(1983) 의 smearing 추정량으로 보정해야 한다.

이 프로젝트는 **보정하지 않는다.** 원하는 것이 애초에 중앙값 성격의 대푯값이고,
비교표본 쪽도 중앙값을 쓰므로 두 경로가 같은 기준에 놓인다. 산술평균으로 보정하면
오히려 두 추정기가 서로 다른 것을 재게 된다. 의도된 선택이다.

### Stage 1 — 거래 단위, 단지 고정효과

거래 $i$ 가 단지 $c(i)$ 에 속할 때

$$
\log P_i \;=\; \alpha_{c(i)} \;+\; g(a_i) \;+\; \sum_{b}\phi_b \mathbb{1}[B_i = b] \;+\; \sum_{m}\mu_m \mathbb{1}[M_i = m] \;+\; \delta\, d_i \;+\; \varepsilon_i
$$

| 기호 | 뜻 | 기준값 |
|---|---|---|
| $P_i$ | **전용면적** 기준 평당가 = 거래금액 ÷ (전용㎡ ÷ 3.305785) | |
| $a_i$ | $\log(\text{전용면적}_i / 84)$ | 84㎡ 에서 0 |
| $B_i$ | 층 구간 (1층·저층·중층·고층·최상층) | 중층, $\phi_{\text{중층}} \equiv 0$ |
| $M_i$ | 계약월 | 최신월, $\mu_{\text{latest}} \equiv 0$ |
| $d_i$ | 동 도보편차 | 아래 |

**동 도보편차**가 이 설계의 핵심 장치다.

$$
d_i \;=\; w^{\text{dong}}_i \;-\; \overline{w^{\text{dong}}}_{c(i)}
$$

단지 평균을 뺐으므로 **단지 더미와 직교**한다. 따라서 $\delta$ 는 오직 "같은 단지 안에서
역에 가까운 동 vs 먼 동" 비교로만 추정된다. 학군·브랜드·관리상태·구 입지가 전부 단지
더미에 흡수되므로 교란이 원천적으로 없다 — 이 데이터로 얻을 수 있는 가장 깨끗한 식별이다.
추정값은 $\hat\delta = -0.00356$ (분당 $-0.355\%$, $t=-9.72$, $n=20{,}211$).

기준점 설정 때문에 $\hat\alpha_c$ 는 곧 **그 단지의 전용 84㎡ · 중층 · 최신월 로그 평당가**다.
추정은 OLS + HC1.

**고정효과가 사는 것과 파는 것.** 단지 더미는 단지 단위로 시간불변인 **모든** 요인을
흡수한다 — 학군, 브랜드, 조망, 시공 품질, 관리 상태, 동네 분위기. 관측하지 못한 것까지
포함해서다. 누락변수 편의가 원천적으로 사라지므로 이 안에서 추정한 층·면적·동 효과는
믿을 만하다(within estimator).

대신 대가가 있다. **단지 안에서 변하지 않는 것은 아무것도 식별할 수 없다.** 역거리·연식·
세대수·노선은 단지마다 값이 하나뿐이라 단지 더미와 완전공선이다. 그래서 Stage 2 가 따로
필요하다. 두 단계는 임의의 분업이 아니라 고정효과가 남긴 구멍을 메우는 구조다.

### 제한 3차 스플라인 (RCS)

$g(\cdot)$ 과 Stage 2 의 연속 요인은 형태를 미리 정하지 않는다. 매듭
$t_1 < \cdots < t_k$ 에 대해 Harrell 기저 (`pricing.rcs_basis`):

$$
X_1 = x, \qquad
X_{j+1} = \frac{(x-t_j)_+^3 \;-\; (x-t_{k-1})_+^3\dfrac{t_k-t_j}{t_k-t_{k-1}} \;+\; (x-t_k)_+^3\dfrac{t_{k-1}-t_j}{t_k-t_{k-1}}}{(t_k-t_1)^2}
$$

$j = 1,\dots,k-2$, $(u)_+ = \max(u,0)$. 매듭 $k$ 개 → 열 $k-1$ 개.

**왜 '제한'인가** — 양 끝 매듭 바깥에서 2·3차항이 상쇄되어 **선형으로 제한**된다. 일반 3차
스플라인은 데이터가 없는 꼬리에서 폭주하는데, 이건 도보 35분처럼 표본이 희박한 구간에서도
얌전하다. 분모 $(t_k-t_1)^2$ 은 스케일 정규화다.

매듭은 Harrell 권장 분위수에 놓는다. 3개면 $p_{10}, p_{50}, p_{90}$, 4개면
$p_5, p_{35}, p_{65}, p_{95}$. 데이터가 몰린 곳에 매듭을 촘촘히 두는 셈이다.

**다항식 대신 스플라인을 쓰는 이유는 국소성이다.** $x^2, x^3$ 같은 항은 **전역 기저**라
한쪽 끝의 관측치 하나가 곡선 전체 모양을 비튼다. 차수를 올려 유연성을 얻으려 하면
Runge 현상으로 꼬리가 진동한다. 스플라인 기저는 해당 매듭 구간에서만 크게 반응하므로
한 구간의 데이터가 다른 구간을 흔들지 않는다.

**선형성 검정** — 첫 열이 $x$ 자신이므로, 나머지를 함께 0 으로 두는 Wald 검정이 곧
"이 요인은 직선인가" 검정이 된다.

$$
H_0:\ \beta_{\text{nl},1} = \cdots = \beta_{\text{nl},k-2} = 0
$$

이 검정이 사전 가정을 절반쯤 뒤집었다 — 도보거리 $p=0.90$(직선), 강남 접근성 $p=0.052$,
연식 $p<0.001$(휨).

### Stage 2 — 단지 단위, 가중최소제곱

$$
\hat\alpha_c \;=\; \beta_0 + f_W(W_c) + f_G(G_c) + f_A(A_c) + f_H(\log H_c) + \sum_\ell \lambda_\ell \mathbb{1}[\text{노선}_c=\ell] + \sum_g \gamma_g \mathbb{1}[\text{구}_c=g] + u_c
$$

$W$=도보분, $G$=강남 소요분, $A$=연식, $H$=세대수. $f_\bullet$ 는 전부 RCS.

**왜 Stage 1 의 추정값을 종속변수로 쓰나.** $W_c, A_c, H_c$ 는 단지 안에서 상수다. 거래
단위 회귀에 그대로 넣으면 같은 정보를 거래 수만큼 반복해 세는 셈이 된다. Moulton(1990) 이
지적한 문제이고, 표준오차가 얼마나 틀리는지는 **설계효과**로 계산된다.

$$
\frac{\mathrm{se}_{\text{올바른}}}{\mathrm{se}_{\text{OLS}}} \;\approx\; \sqrt{1 + (\bar n - 1)\rho}
$$

$\bar n$ 은 군집당 평균 관측 수, $\rho$ 는 오차의 급내상관이다. 이 데이터는 거래 28,451 건
단지 497 곳이라 $\bar n = 57.2$ 다.

| 급내상관 $\rho$ | 설계효과 |
|---|---|
| 0.05 | 1.95배 |
| 0.10 | 2.57배 |
| 0.20 | 3.50배 |
| 0.30 | 4.23배 |

같은 단지 거래끼리 닮았으므로 $\rho$ 가 0 일 리 없다. **t 값이 2~4배 부풀고**, 유의하지
않은 것이 유의해 보인다. 군집 표준오차로 사후 보정할 수도 있지만, 단지를 하나의 관측치로
접으면 문제 자체가 생기지 않는다.

**생성된 종속변수(generated regressand)는 왜 안전한가.** $\hat\alpha_c$ 는 참값이 아니라
추정값이라 오차를 품는다. **설명변수**에 측정오차가 있으면 계수가 0 쪽으로 끌려가는
감쇠 편의가 생기지만, **종속변수**의 측정오차는 다르다. 오차항에 합쳐질 뿐이라 계수는
여전히 불편(unbiased)이고 분산만 커진다. 2단계 설계가 성립하는 근거가 여기 있다.
커진 분산은 아래 가중치가 처리한다.

대신 $\hat\alpha_c$ 는 **추정된 종속변수**라 오차가 두 겹이다.

$$
\hat\alpha_c = \alpha_c + \eta_c, \qquad \operatorname{Var}(\hat\alpha_c \mid \alpha_c) = \mathrm{se}^2_c
$$

여기에 참값 자체의 설명 안 되는 분산 $\tau^2 = \operatorname{Var}(u_c)$ 가 더해진다.
둘을 합친 것이 가중치의 역수다.

$$
\omega_c \;=\; \frac{1}{\mathrm{se}^2_c + \tau^2}
$$

거래 3건짜리 단지($\mathrm{se}$ 큼)는 자동으로 덜 세어진다. $\tau^2$ 이 없으면 표본이 많은
단지 몇 곳이 회귀를 지배한다.

$\tau^2$ 추정은 적률법인데 **한 단계 더** 간다.

$$
\hat\tau^2 \;=\; \max\!\left(0,\ \frac{\sum_c \hat e_c^2}{n-k} \;-\; \overline{\mathrm{se}^2_c}\right)
$$

$\hat e_c$ 는 1차 OLS 잔차다. 그냥 $\operatorname{Var}(\hat\alpha) - \overline{\mathrm{se}^2}$
로 두면 **모델이 설명한 변동까지** $\tau^2$ 에 들어간다. 잔차에서 빼야 설명되지 않은 부분만
남는다.

공분산은 단지 250곳 미만이면 **HC3**, 아니면 HC1. 둘 다 White 의 이분산 강건 추정량
계열인데 잔차 보정 방식이 다르다 — HC1 은 자유도만 $n/(n-k)$ 로 조정하고, HC3 은 각
관측치의 지렛대값 $h_i$ 를 써 $\hat e_i^2/(1-h_i)^2$ 로 나눠 **잭나이프에 가깝다**.
MacKinnon-White(1985) 가 소표본에서 HC3 을 권한 이유다.

취향이 아니라 재서 고른 것이다. 시드 복원 검증에서 HC1 의 신뢰구간 포함률이 **72.5%** 로
명목 95% 에 한참 못 미쳤고, HC3 으로 바꾸자 **97.5%** 가 됐다.

식별 불가도 잡는다. $\operatorname{rank}(X) <$ 열 수면 예외를 던진다(단지 25곳에 법정동
더미 17개를 넣는 경우). 의미 없는 숫자를 내놓느니 "못 푼다"고 말한다.

**단지 잔차**는 경험적 베이즈로 축소한다.

$$
\tilde u_c \;=\; \hat u_c \cdot \frac{\tau^2}{\tau^2 + \mathrm{se}^2_c}
$$

이것은 정규-정규 계층모형 $u_c \sim N(0,\tau^2)$, $\hat u_c \mid u_c \sim N(u_c, \mathrm{se}^2_c)$
의 **사후평균**이다. 신호 대 잡음 비율만큼만 믿는다는 뜻으로, 표본이 적은 단지일수록
0(전체 평균) 쪽으로 당겨진다. James-Stein 이 보인 대로 이런 축소추정량은 개별 추정값을
그대로 쓰는 것보다 전체 제곱오차가 작다.

축소 없이 정렬하면 상위권이 전부 거래 3건짜리 단지로 채워진다. 실제로 동 프리미엄에서
이 함정을 만났다 — 거래 3건짜리 동이 '이 단지에서 가장 싼 동'으로 올라왔다.

### 비교표본 방식 (comparable sales)

회귀가 **아니다**. 모수도 없고 함수 형태 가정도 없다. "비슷한 것이 얼마에 팔렸나"를 직접 센다.

**표본 사다리** — 위에서부터 3건 이상이면 멈춘다.

$$
S \;=\; \begin{cases}
\{p : |\text{면적}_p - a| \le 1.5,\ c_p = c\} & |\cdot| \ge 3 \
\{p : \text{면적대}_p = \text{면적대}(a),\ c_p = c\} & |\cdot| \ge 3 \
\{p : c_p = c\} & |\cdot| \ge 3 \
\text{유사 입지·연식·면적대의 다른 단지} & \text{그 외}
\end{cases}
$$

좁을수록 좋지만 비면 쓸모없다는 절충이다. 어느 단을 썼는지 `basis` 로 화면에 그대로 적는다.

**시점 보정 — 구성 편향 제거.** 월별 중앙 평당가를 그냥 쓰면 비싼 단지가 몰린 달이 시장
상승으로 잘못 읽힌다. 그래서 각 거래를 **자기 (단지, 평형) 중앙값으로 나눈 상대 평당가**로
지수를 만든다.

$$
r_i \;=\; \frac{P_i}{\operatorname{med}\{P_j : (c_j, \text{평형}_j) = (c_i, \text{평형}_i)\}},
\qquad
I_m \;=\; \frac{\operatorname{med}\{r_i : M_i = m\}}{\operatorname{med}\{r_i : M_i = m_{\text{latest}}\}}
$$

분모 기준 그룹은 3건 이상일 때만 만들고, 표본 5건 미만인 달은 직전 달 지수를 이어받아
튀는 값을 막는다. 시점 보정 평당가는 $\tilde P_i = P_i / I_{M_i}$.

이 구조는 물가지수에서 **품목 구성 변화를 통제하는 방식**과 같다. 매칭 모형(matched-model)
지수처럼 '같은 것끼리' 비교하도록 만든 상대값을 집계하므로, 그 달에 어떤 단지가 거래됐는지가
지수에 새지 않는다. 헤도닉 쪽의 월 더미 $\mu_m$ 도 같은 일을 하는데, 그쪽은 회귀가
단지·면적·층을 동시에 통제해 준다는 점이 다르다. **두 경로가 서로의 검산이 된다.**

**층 보정 — 같은 방식 한 번 더.**

$$
F_b \;=\; \operatorname{med}\left\{ \frac{\tilde P_i}{\operatorname{med}\{\tilde P_j : (c_j,\text{평형}_j)=(c_i,\text{평형}_i)\}} \;:\; B_i = b \right\}
$$

(단지, 평형) 그룹 4건 이상, 구간별 5건 이상일 때만 낸다. 단지 효과와 평형 효과가 제거된
**순수 층 프리미엄**이다.

**최종 조립.**

$$
\text{base} \;=\; \operatorname{med}\left\{ \frac{\tilde P_i}{F_{B_i} \cdot D_{\text{dong}_i}} : i \in S \right\},
\qquad
\widehat{\text{적정}} \;=\; \text{base} \times F_{b^*} \times D_{d^*} \times \text{평}
$$

**중립화 후 재적용**이 핵심이다. 표본은 여러 층·여러 동에서 오므로, 각 거래에서 자기 층·동
효과를 **나눈 뒤** 대상 매물의 효과를 곱한다. 나누지 않고 곱하기만 하면 기준선에 이미 섞인
효과를 두 번 센다. ($D$ 는 동 계수인데 현재 $\tau=0$ 이라 실질적으로 1이다.)

범위는 $p_{25}, p_{75}$ 에 같은 보정을 걸어 낸다.

### 왜 중앙값 기반 비모수인가

**비모수(nonparametric)** = 모집단 분포에 유한 개의 모수를 가정하지 않는다는 뜻이다.
"오차가 정규분포" 같은 전제 없이 순위 통계량만 쓰므로, 가정이 틀려서 결과가 틀리는 경로가
없다. 대신 가정을 안 쓰는 만큼 같은 표본에서 뽑아내는 정보가 적다 — 전형적인 맞교환이다.

**붕괴점(breakdown point).** 추정량이 무너지기까지 견디는 오염 비율이다. 평균의 붕괴점은
$1/n$ — 관측치 **하나**만 무한대로 보내면 평균도 무한대가 된다. 중앙값은 $50\%$ 로,
이론적 최대값이다. 절반이 오염돼야 무너진다.

영향함수(influence function)로 보면 더 분명하다. 평균은 관측치 값에 **비례해** 끌려가지만
(IF $\propto x - \mu$, 유계가 아님), 중앙값의 영향함수는 $\pm 1/(2f(m))$ 로 **유계**다.
아무리 멀리 떨어진 값이라도 밀어낼 수 있는 한계가 정해져 있다.

부동산 실거래에는 이런 것이 실제로 섞인다.

- 특수관계인 거래(증여성 저가 거래)
- 계약 해제 전 신고(걸러내지만 완벽하지 않다)
- 급매 / 경매 낙찰
- 층·향이 극단적인 한 채

거래 10건짜리 단지에서 한 건이 3배 비싸면 평균은 **+20%** 움직이고 중앙값은 **0%** 움직인다.

**대가 — 점근상대효율(ARE).** 오차가 정말 정규분포라면 중앙값의 점근분산은
$\dfrac{1}{4nf(m)^2} = \dfrac{\pi\sigma^2}{2n}$ 로, 평균의 $\sigma^2/n$ 보다 $\pi/2 \approx 1.57$ 배
크다. 즉 ARE 가 $2/\pi \approx 0.64$ — 같은 정밀도를 얻으려면 표본이 **1.57배** 더 필요하다.

그런데 이 맞교환은 분포에 따라 뒤집힌다. 꼬리가 두꺼워질수록 중앙값이 유리해지고,
Laplace 분포에서는 중앙값이 오히려 평균보다 효율적이다. 실거래가는 정규보다 꼬리가 두껍다
— 특수관계인 거래, 급매, 경매가 섞이기 때문이다. 그래서 명목상 36% 손해라는 계산은
**최악의 경우**이고 실제 손해는 더 작다.

그리고 이 프로젝트에서 중요한 것은 효율이 아니라 **판정이 뒤집히지 않는 것**이다.
거래 10건짜리 단지에서 한 건 때문에 '적정'이 '저평가'로 바뀌면 효율 36% 는 의미가 없다.

### 역할 분담

| | 헤도닉 회귀 | 비교표본 |
|---|---|---|
| 가정 | 로그선형 + 스플라인, 오차 등분산 | 없음 |
| 이상치 | 민감(OLS 는 제곱 손실) | 강건 |
| 외삽 | 가능(표본 없는 조건도 예측) | 불가능 |
| 단지 프리미엄 | 분리해 냄 | 값에 포함 |
| 필요 표본 | 단지 전체 | 그 단지 3건 |

**그래서 둘 다 쓴다.** 헤도닉은 "조건만 보면 얼마여야 하나", 비교표본은 "실제로 얼마에
팔리나". 둘의 차이가 그 단지에 붙어 있는 값이다.

다만 비교표본을 **검산 장치로도** 쓴다. 모델의 면적 곡선은 전 단지 공통이라 특정 단지·평형
에서 어긋나는데, 같은 질문("이 단지 이 유닛이 지금 얼마")에 두 방법이 다른 답을 내면 그
비율이 곧 곡선의 국소 오차다. 실제로 40㎡ 에서 14% 어긋나 그만큼 교정한다
(위 '요인별 적정가' 참조).

## 실제 데이터 연결

`scripts/seed_demo.py` 가 만드는 데이터는 **합성 데이터**다. 단지명·법정동·역 정보는 실제
수원시 기준이지만 가격과 거래 건수는 시뮬레이션이므로 실제 시세 판단에 쓰면 안 된다.

실거래가를 쓰려면 `backend/.env` 에 키를 넣는다.

| 키 | 위치 | 발급처 | 없으면 |
|---|---|---|---|
| `MOLIT_SERVICE_KEY` | `backend/.env` | [공공데이터포털 — 국토교통부_아파트 매매 실거래가 **상세** 자료 (15126468)](https://www.data.go.kr/data/15126468/openapi.do) 의 일반 인증키(Decoding) | 합성 데이터로 동작 |
| `KAKAO_REST_KEY` | `backend/.env` | [카카오 개발자센터](https://developers.kakao.com) > 내 애플리케이션 > 앱 키 > REST API 키 | 단지 수집·좌표 조회 불가 |
| `VITE_KAKAO_JS_KEY` | `frontend/.env.local` | 같은 카카오 앱의 **JavaScript 키** (REST 키와 다른 키) | 지도 탭이 설정 안내로 대체 |
| `TMAP_APP_KEY` | `backend/.env` | [SK open API](https://openapi.sk.com) > 보행자 경로안내 | 직선거리×1.25 추정치로 자동 폴백 |

카카오 JS 키를 쓰려면 개발자센터 > 플랫폼 > Web 에 `http://localhost:5173` 과
`http://127.0.0.1:5173` 을 **둘 다** 등록해야 한다. 카카오는 origin 을 완전일치로 검사하고
Vite 는 127.0.0.1 로 프록시한다.

이름이 거의 같은 **국토교통부_아파트 매매 실거래가 자료(15126469)** 를 신청하면 안 된다.
그쪽은 동 정보(`aptDong`)와 계약 해제 여부(`cdealType`)가 빠져 있어, 해제된 거래를
걸러내지 못하고 시세가 위로 왜곡된다.

인증키는 **Encoding / Decoding 두 가지로 발급**되는데 이 프로젝트는 `httpx` 가 쿼리스트링을
직접 인코딩하므로 **Decoding 키**를 넣어야 한다. Encoding 키를 넣으면 이중 인코딩되어
`SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 난다.

활용신청은 자동승인이지만 키가 실제로 활성화되기까지 보통 **수십 분에서 1시간** 걸린다.
바로 호출해서 오류가 나면 조금 기다렸다가 다시 시도할 것. 개발계정 트래픽은 일 10,000건이며,
17개 시군구 × 24개월 = 408회 호출이라 넉넉하다(구·월당 약 0.5초).

### API 재호출 방지

한 번 받은 것은 다시 받지 않는다. 스크립트를 여러 번 돌려도 안전하다.

| 스크립트 | 건너뛰는 조건 | 다시 받으려면 |
|---|---|---|
| `geocode` | `Complex.lat` 이 이미 있으면 | `--force` |
| `seed_stations` | 역 좌표가 이미 있으면 | `--force` |
| `route_walk` | `routed_at` 있고 출처가 `tmap` 이면 | `--force` |
| `ingest_trades` | 그 (구, 월) 조합이 이미 적재돼 있으면 | `--refetch-all` |

**국토부만 예외가 있다.** 실거래 신고 기한이 계약 후 30일이라 지난달 데이터도 계속
늘어난다. 그래서 **최근 3개월은 항상 다시 받는다**(`--refetch-recent N` 으로 조절).
덕분에 24개월 재실행이 96회 호출 → 12회, 3~4분 → 12초가 된다.

```bash
cd backend
python -m scripts.ingest_trades --months 24   # DISTRICTS 전체(17개 구) 실거래 적재
python -m scripts.geocode                     # 좌표 변환 + 최근접 지하철역 거리
python -m scripts.seed_stations --force       # 역 좌표 채우기
python -m scripts.route_walk                  # 도보 경로 (TMap 키 있으면 실거리)
python -m scripts.geocode_dongs               # 동별 좌표 + 동별 역거리
python -m scripts.ingest_kapt --check         # 세대수 (K-apt 활용신청 필요)
```

**스키마를 바꿨을 때**는 `--recreate-schema` 로 통째로 다시 만드는 대신
`python -m scripts.migrate` 로 빠진 컬럼만 추가한다. 실데이터가 들어 있으면
재생성에 API 호출 수십 분이 다시 들기 때문이다. 컬럼 추가만 하고 타입 변경·삭제는
하지 않으므로, 그런 변경에는 여전히 재생성이 필요하다.

### 세대수 (K-apt)

data.go.kr 은 **계정당 인증키가 하나**라 기존 `MOLIT_SERVICE_KEY` 를 그대로 쓴다.
다만 서비스마다 활용신청은 따로 해야 한다(자동승인).

- [공동주택 기본 정보제공 서비스 (15058453)](https://www.data.go.kr/data/15058453/openapi.do) — 세대수·동수
- [공동주택 단지 목록제공 서비스 (15057332)](https://www.data.go.kr/data/15057332/openapi.do) — 단지코드

`python -m scripts.ingest_kapt --check` 가 신청 상태를 알려준다. 응답 코드로 구분한다 —
**30번은 "경로는 맞는데 미신청"**, 12번은 "경로가 틀림". 이 둘을 구분해야
신청을 더 해야 하는지 코드를 고쳐야 하는지 알 수 있다.

K-apt 에서 밟은 함정 셋. 전부 **오류 없이 조용히 빈 결과**가 되는 종류다.

1. **오퍼레이션 이름 끝의 `4`.** 서비스가 `AptListService4` 면 오퍼레이션도
   `getSigunguAptList4` 다. `getSigunguAptList` 로 부르면 코드 12 가 오는데,
   미신청과 구분이 안 돼 원인을 찾기 어렵다.
2. **응답 모양이 서비스마다 다르다.** 단지목록은 `body.items.item`, 기본정보는
   `body.item` (복수형이 아니다).
3. **세대수가 `1240.0` 처럼 실수로 온다.** `int("1240.0")` 은 ValueError 라
   float 을 거쳐야 한다. 안 그러면 호출은 성공하는데 세대수만 전부 None 이 된다.

단지 매칭은 K-apt 이름에 붙은 **지역 접두어**를 벗겨야 한다
(`정자동 송학아파트` vs 국토부 `송학`). 다만 이름만으로 붙이면 위험해서
**준공년도 교차검증**(K-apt 와 국토부가 독립 보고한 값이 1년 이내)을 함께 건다.
접두어 처리로 매칭이 154 → 264곳으로 늘었다.

### 단지를 늘리기 (카카오 키만 있으면 국토부 키 없이도 가능)

기본 시드의 25곳으로는 2단계 회귀 표본이 부족하다. 특히 강남접근성 항은 유효 클러스터가
4개 수준이라 해석이 어렵다. 카카오로 실제 단지를 수집해 250~300곳으로 늘린다.

```bash
python -m scripts.fetch_complexes --dry-run   # 먼저 눈으로 검수
python -m scripts.fetch_complexes --max 300
python -m scripts.seed_stations --force
python -m scripts.route_walk
python -m scripts.seed_demo                   # 늘어난 단지로 거래 재생성
python -m scripts.validate_model --coverage 40
```

`--dry-run` 을 **반드시 먼저** 돌려 법정동별 단지 수와 제외된 POI 목록을 확인할 것.
키워드 검색에는 상가·관리사무소·중개업소가 섞여 들어오고, 경계 타일은 용인 기흥이나
화성 병점을 끌어온다. 필터가 잡고 있지만 눈으로 한 번 보는 게 싸다.

`ingest_trades` 는 계약 해제건(`cdealType == "O"`)을 제외하고, 동일 거래를
`(단지, 계약일, 전용면적, 층, 거래금액)` 으로 중복 제거한다. 여러 번 돌려도 안전하다.

단지 식별은 단지명 완전일치가 아니라 **정규화 키**(`pricing.name_key`)로 한다. 카카오는
`래미안영통마크원2단지`, 국토부는 `래미안 영통 마크원 2단지` 를 주기 때문이다. 완전일치로
두면 국토부 적재 시 고아 중복 단지가 생기고, 지오코딩·TMap 호출을 태운 행에 거래가 하나도
붙지 않는다. `N차` 는 정규화하되 **제거하지 않는다** — 래미안1차와 2차는 실제로 다른 단지다.

### 거래된 적 없는 평형

붙여넣은 면적은 그 단지에 **실제로 거래된 평형**에 맞춘다(`_resolve_area`). 네이버가
전용 평을 버림해 쓰거나 광고가 공급면적을 적는 일이 잦아서인데, 셋 다 실패하면
면적을 지워 버렸다. 그러면 화면에는 "전용면적 또는 가격을 읽지 못했습니다" 가 뜬다.

그런데 맞는 평형이 없다는 것이 **면적을 잘못 읽었다는 뜻은 아니다.** 수원성중흥
S-클래스는 실거래가 1건뿐이고 그마저 84.66㎡인데, 매물에는 `전용75.97` 이라고 분명히
적혀 있었다. 값은 제대로 읽었고 그 평형이 아직 거래되지 않았을 뿐이다. 그런데도
'못 읽었다' 고 말하니 사용자는 붙여넣기가 깨진 줄 알게 된다.

그래서 **명시된 값은 살린다.** 비교할 거래가 없다는 사실은 평가 단계가 따로 알려 준다.
반대로 평 표기처럼 값 자체가 추정인 경우에는 지운다 — 그때는 정말 잘못 읽었을 수 있다.

이때 적정가는 역거리·연식·면적대가 비슷한 **다른 단지** 거래로 낸다. 안내 문구가
"같은 평형 다른 동의 시세로 대신했다" 고 말하고 있었는데, 표본 28건 중 27건이 다른
단지였으므로 틀린 설명이었다. 표본의 절반 이상이 단지 밖에서 왔으면 그렇게 말한다.

### 두 글자 단지명

붙여넣은 텍스트에서 단지를 찾을 때는 본문 전체에서 정규화 키를 부분일치로 찾는데,
여기에 `len >= 3` 조건이 있었다. `현대`·`대우` 같은 두 글자를 본문에서 찾으면
'현대건설 시공' 같은 홍보문구에 걸리기 때문이다.

그런데 그 조건 때문에 **두 글자 단지는 영원히 못 찾는다.** `임광`(수원 매탄동,
1,320세대)이 그렇고, 2,469곳 중 **346곳(14%)** 이 여기 해당한다. 가격·층·면적·동·
확인일자는 전부 제대로 읽히는데 단지만 비어서, 목록 전체가 통째로 평가되지 않았다.

그래서 길이 제한을 푸는 대신 **찾는 자리를 좁혔다.** 단지명은 목록의 첫 줄에 있고
그 줄은 '임광 8동' 처럼 이름과 동뿐이다. 거기서 동을 떼고 남은 것과 **정확히 같을
때만** 인정한다. 홍보문구는 첫 줄이 아니므로 걸리지 않는다.

같은 이름이 여러 곳이면(`현대` 는 장안구에만 네 곳) 자동 선택하지 않고 후보로만
올린다. 두 글자는 구별 정보가 거의 없어서, 찍으면 틀릴 확률이 높다.

## 알려진 한계

- **매물 호가는 수동 입력**이다. 네이버부동산 등 호가 데이터는 공식 API가 없고 스크래핑은
  이용약관 위반 소지가 있어 PoC에서 제외했다. 대신 사용자가 **텍스트를 붙여넣으면**
  단지·면적·층·호가를 뽑아 채워 준다(위 '매물 비교' 참조). 링크는 지원하지 않는다 —
  긁어오지 않겠다는 결정이기도 하고, 애초에 링크에 매물 정보가 들어 있지 않다.
- 단지 최고층이 실제 최고층이 아니라 관측 최고 거래층이므로, 거래가 적은 단지에서는
  "최상층" 판정이 부정확할 수 있다.
- 도보거리 정밀도에는 **살 수 없는 한계**가 있다. 카카오가 주는 단지 좌표는 중심점 하나인데
  한국 아파트 단지는 폭이 200~400m라 보행 출입구가 중심에서 300m 떨어질 수 있다. TMap 을
  써도 ±150m 는 남는다. TMap 의 가치는 정밀도가 아니라 **체계적 장벽**(경부선·원천리천·
  영동고속도로) 포착이다 — 분산이 아니라 편향 교정이라, R² 급등이 아니라 특정 단지가 크게
  움직이는 것을 기대해야 한다.
- `seed_stations.py` 의 **강남 소요시간은 현재 추정치**다. 실제 길찾기로 검증해 교체해야
  한다. 합성 데이터 단계에서는 시드와 모델이 같은 표를 읽으므로 복원 검증은 값과 무관하게
  성립하지만, 실거래가로 전환할 때는 실측이 필요하다.
- 강남 접근성은 구 고정효과와 상관이 높다. 신분당선 역(광교·상현)이 전부 영통구/이의동에
  몰려 있어 두 변수가 같은 것을 가리키는 구간이 있다. 계수는 보고하되 과신하면 안 된다.
- 단지 수가 적으면(120곳 미만) 강남 항의 유효 클러스터가 4개 수준이라 해석이 어렵다.
  도보 곡선은 그보다 적은 표본에서도 살아남는다.
- 동향·조망·리모델링 여부·학군 등 가격에 영향을 주는 다른 요인은 반영하지 않는다.
  모델 잔차에 이것들이 전부 섞여 있다. 결과는 참고용이며 투자 판단의 근거로 쓸 수 없다.

## 대상 지역을 넓히기

`app/clients/molit.py` 의 `DISTRICTS` 에 시군구 코드를 더하면 그대로 확장된다.
분석 로직에 특정 도시 전용 가정은 없다.

### 코드를 기억으로 적지 않는다

처음에 화성시를 `41590` 으로 적었다가 실거래 **0건**을 받았다. 화성시가 구로 나뉘면서
코드가 41591(만세구)·41593(효행구)·41595(병점구)·41597(동탄구) 로 갈린 것이었다.
틀린 코드는 오류가 아니라 **0건으로 조용히 지나간다** — 결과만 봐서는 알 수 없다.

그래서 13개 코드를 전부 확인하고 적었다. 코드마다 실거래를 한 달치 받아 법정동을 꺼낸 뒤,
카카오 주소 API 의 `b_code` 앞 5자리가 그 코드와 맞는지 대조했다. 코드를 추가할 때도
같은 방식으로 확인할 것.

### 역 테이블이 약한 고리다

강남 소요시간은 공개 대중교통 길찾기 API 를 쓰지 않아 **수기 표**다(`scripts/seed_stations.py`).
표가 21개에서 67개로 커지면서 세 종류의 오류가 드러났고, 전부 검사로 잡았다.

| 검사 | 잡아낸 것 |
|---|---|
| 노선 단조성 (`check_monotone`) | 성균관대역이 화서역보다 강남에 가까운데 4분 느리게 적혀 있었다 |
| 이름 대조 (`station_name_matches`) | 운동장·송담대역 → **용인중앙시장역** 개명, GTX-A '용인역' → 실제로는 **구성역** |
| 좌표 검증 | **영덕역은 존재하지 않는 역**이었다. 카카오가 청명역 좌표를 그대로 돌려줬고(좌표 완전 일치), 강남 43분으로 청명역(48분)보다 5분 빠르게 잡혀 단지 65곳이 여기에 붙어 있었다 |

세 검사 모두 매 실행마다 돈다. 수기 표는 커지면 반드시 어긋나므로, 어긋남을 사람이
발견하기를 기다리면 안 된다.

> 강남접근성 계수는 이 표만큼만 정확하다. **다른 요인(면적·층·도보·연식·세대수·동 위치)은
> 실거래에서 직접 추정되므로 이 한계의 영향을 받지 않는다.** 실측이 필요하면 ODsay 같은
> 대중교통 길찾기 API 를 붙여 이 표를 대체하면 된다.

### 매듭 수는 표본이 정한다

요인 곡선을 얼마나 촘촘히 볼 수 있는지는 표본이 정한다(`hedonic.knots_for`). Stage 2 의
관측치는 **단지 수**라, 수원만 볼 때 497곳에서는 매듭 4개가 상한이었다. 경기 남부로
넓혀 2,000곳을 넘으면서 7개까지 쓸 수 있게 됐다 — 요인당 열이 3개에서 6개로 늘어난다.

| 단지 수 | 매듭 | 근거 |
|---|---|---|
| < 250 | 4 | 표본이 작으면 Harrell 권고 하한 |
| < 700 | 5 | |
| < 1,500 | 6 | |
| ≥ 1,500 | 7 | 요인 4개 × 6열 + FE 20여 열 = 45열, 관측당 30배 |

화면의 곡선 범위도 코드에 박지 않고 적합이 돌려준 관측 분포(`var_range`, p1~p99)에서
가져온다. 박아 두면 지역을 넓혔을 때 곡선이 데이터 없는 구간까지 그려지거나 있는 구간을
잘라 먹는다.
