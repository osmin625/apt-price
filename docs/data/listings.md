# 붙여넣은 매물 — 우리 단지에 맞추고 메모를 읽는다

붙여넣은 매물 텍스트를 **우리 데이터에 잇는** 규칙과 그 함정. 글자를 읽는 것
(`services/listing_parse.py`)은 코드 주석이 사례와 함께 들고 있고, 여기는 읽은 값을
어느 단지·어느 평형으로 볼지(`services/listing_match.py`), 중개사 메모를 어떻게 읽는지
(`services/memo_tags.py`), 한 번에 얼마나 붙여넣을 수 있는지를 다룬다. 읽힌 매물이
화면에서 어떻게 값이 매겨지고 줄 서는지는 [호가 다루기](../screens/quotes.md) 에 있다.

[데이터 파이프라인](pipeline.md) 에서 나왔다. 그 문서는 공공 API 에서 **우리가 모으는**
데이터를 다루는데, 붙여넣은 매물을 맞추는 이야기가 섞여 500줄이 넘었다.

판단의 기준은 하나다 — **합치는 것보다 못 합치는 게 낫다.** 잘못 붙이면 남의 거래가
섞여 시세가 통째로 망가지지만, 안 붙이면 줄이 하나 비는 것뿐이다.

## 단지·평형에 맞추기

### 거래된 적 없는 평형

붙여넣은 면적은 그 단지에 **실제로 거래된 평형**에 맞춘다(`_resolve_area`). 네이버가
전용 평을 버림해 쓰거나 광고가 공급면적을 적는 일이 잦아서인데, 셋 다 실패하면
면적을 지워 버렸다. 그러면 화면에는 "전용면적 또는 가격을 읽지 못했습니다" 가 뜬다.

그런데 맞는 평형이 없다는 것이 **면적을 잘못 읽었다는 뜻은 아니다.** 수원성중흥
S-클래스는 실거래가 1건뿐이고 그마저 84.66㎡인데, 매물에는 `전용75.97` 이라고 분명히
적혀 있었다. 값은 제대로 읽었고 그 평형이 아직 거래되지 않았을 뿐이다. 그런데도
'못 읽었다' 고 말하니 사용자는 붙여넣기가 깨진 줄 알게 된다.

그래서 **명시된 값은 살린다.** 비교할 거래가 없다는 사실은 평가 단계가 따로 알려 준다.
반대로 평 표기처럼 값 자체가 추정인 경우에는 지운다 — 그때는 정말 잘못 읽었을 수 있다.

이때 적정가는 역거리·연식·면적대가 비슷한 **다른 단지** 거래로 낸다. 안내 문구가
"같은 평형 다른 동의 시세로 대신했다" 고 말하고 있었는데, 표본 28건 중 27건이 다른
단지였으므로 틀린 설명이었다. 표본의 절반 이상이 단지 밖에서 왔으면 그렇게 말한다.

### 시공사 합동 단지 — 네이버는 묶고 국토부는 쪼갠다

네이버 매물에 `신성,신안,쌍용,진흥 543동` 이라고 적힌 단지가 국토부 실거래에는 없다.
시공사 네 곳이 함께 지은 단지라 **국토부는 시공사마다 따로 기록**하기 때문이다.

```
카카오    신성신안쌍용진흥아파트 (수원 영통구 영통동 963-2)
국토부    신나무실신성 · 신나무실신안 · 신나무실쌍용 · 신나무실진흥  (각 60여 건)
```

이름으로는 1:N 이라 고를 수 없다. 그런데 **동 번호는 겹치지 않는다.** 실거래에 찍힌
동을 세어 보면 시공사마다 구간이 나뉘어 있다.

| 단지 | 실거래에 찍힌 동 |
|---|---|
| 신나무실신성 | 521 ~ 524 |
| 신나무실신안 | 531 ~ 534 |
| 신나무실쌍용 | 541 ~ 544 |
| 신나무실진흥 | 551 ~ 554 |

그래서 543동은 쌍용, 534동은 신안으로 **유일하게** 정해진다
(`listing_match._resolve_by_dong`).

**이름 조각과 동 번호가 둘 다 맞을 때만** 고른다. `쌍용` 은 전국에 흔한 이름이라
조각 하나로 고르면 엉뚱한 단지가 걸린다. 그리고 조각이 하나뿐이거나(쪼개진 이름이
아니다), 동이 없거나, 그 동의 거래가 없으면 **손대지 않는다** — 둘 이상 남을 때도
고르지 않고 후보로만 둔다. 찍는 것보다 낫다.

### 두 글자 단지명

붙여넣은 텍스트에서 단지를 찾을 때는 본문 전체에서 정규화 키를 부분일치로 찾는데,
여기에 `len >= 3` 조건이 있었다. `현대`·`대우` 같은 두 글자를 본문에서 찾으면
'현대건설 시공' 같은 홍보문구에 걸리기 때문이다.

그런데 그 조건 때문에 **두 글자 단지는 영원히 못 찾는다.** `임광`(수원 매탄동,
1,320세대)이 그렇고, 2,469곳 중 **346곳(14%)** 이 여기 해당한다. 가격·층·면적·동·
확인일자는 전부 제대로 읽히는데 단지만 비어서, 목록 전체가 통째로 평가되지 않았다.

그래서 길이 제한을 푸는 대신 **찾는 자리를 좁혔다.** 단지명은 목록의 첫 줄에 있고
그 줄은 '임광 8동' 처럼 이름과 동뿐이다. 거기서 동을 떼고 남은 것과 **정확히 같을
때만** 인정한다. 홍보문구는 첫 줄이 아니므로 걸리지 않는다.

같은 이름이 여러 곳이면(`현대` 는 장안구에만 네 곳) 자동 선택하지 않고 후보로만
올린다. 두 글자는 구별 정보가 거의 없어서, 찍으면 틀릴 확률이 높다.

## 단지명 매칭에서 동 번호를 먼저 뗀다

첫 줄은 `성원 102동` 처럼 **단지명 + 동**이다. 정규화하면 `성원102동` 이 되는데,
여기서 DB 이름을 부분일치로 찾으면 **동 번호가 이름의 일부로 먹힌다.**

```
성원 102동          -> 성원102동      ⊃ `성원1`(안양 만안구)   ← 남의 시
신나무실5단지주공 514동  -> ...주공514동   ⊃ `주공5`(과천시)       ← 남의 시
주공 103동          -> 주공103동      ⊃ `주공10`(과천시)
인정프린스 102동      -> 인정프린스102동  ⊃ `인정프린스1`(용인 처인구)
```

실제로 겪었다. 수원 매교역 근처 매물 **11건이 안양 성원1 에 붙어 저장됐고**(메모에
'매교역세권' 이 적혀 있었다), 영통 신나무실 34건은 과천 주공5 로 가서 "비교 실거래
없음" 으로 버려졌다. 버려진 쪽은 시끄럽기라도 했지만 붙은 쪽은 **조용히 틀렸다** —
남의 동네 거래가 시세 계산에 섞인다.

이름이 숫자로 끝나는 단지가 2,469곳 중 **187곳**이다. 동 번호는 거의 항상 숫자로
시작하므로, 안 떼면 이 187곳이 전부 덫이다.

### 전수로 대조했다

`scripts/verify_name_match.py` 가 DB 의 모든 단지로 `"{이름} {동}동"` 줄을 만들어
떼기 전/후를 비교한다. 정답은 **출처 단지**다.

```
단지 2,469곳 · 이름이 숫자로 끝나는 곳 187곳
같은 답 9,367건
[고쳐짐] 오답/거절 -> 제 단지        35건
[오답을 거절로]                    63건   (성원·삼익 등 두 글자 이름)
[깨짐] 제 단지였는데 틀려짐           0건   <- 이것이 0 이어야 한다
```

처음에는 1번 규칙(부분일치)만 떼어 재서 "깨진 것 78건" 이라는 **틀린 숫자**를 봤다.
1번이 비면 2번(두 글자 정확일치)이 받는데 그걸 안 태웠기 때문이다. 검증은 실제로
쓰는 경로(`parse_listing`)로 해야 한다.

### 덜 붙는 쪽으로 갔다

고친 뒤 같은 붙여넣기(82건)에서 읽히는 줄이 19 → 8로 줄었다. 성원 11건이 **오답에서
거절로** 바뀌었기 때문이다. 이 저장소의 '합치는 것보다 못 합치는 게 낫다' 그대로다 —
잘못 붙이면 남의 거래가 섞여 시세가 통째로 망가지지만, 안 붙이면 줄이 하나 비는 것뿐이다.

거절된 매물은 **사용자가 고른다.** 일괄 붙여넣기의 `skipped` 에 후보가 실리고, 화면이
이름 단위로 고르게 한다(`components/UnresolvedPicker.jsx`). 고른 '이름 → 단지' 는 서버가
이름 매칭보다 먼저 쓴다(`BulkRequest.name_map`).

## 중개사 메모 — 울타리가 있어서 추측하지 않아도 된다

붙여넣은 목록에서 매물마다 붙는 한 줄 메모를 같이 읽는다. **따옴표만 있는 줄이
여닫는다.**

```
아파트17평 (전용12)3/25층남서향
"
달리는 황소 입주가능,시에2대 지동사거리 접근 좋아 대중교통용이
"
집주인확인매물 2026.09.23
황소단지내공인중개사사무소
```

이 울타리가 있어서 '어느 줄이 메모인가' 를 길이나 어휘로 추측할 필요가 없다.
추측했다면 중개사명(`황소단지내공인중개사사무소`)이나 `매물 보러가기` 같은 버튼
글자를 섞었을 것이고, 그건 조용히 틀린다. 울타리 문자는 **U+0022** 로 확인했다
(실제 붙여넣기에서 짧은 기호 줄 66개가 전부 `0x22` 였고, 66 = 메모 33건 × 2).

여는 따옴표만 있고 닫는 것이 없으면 **버린다.** 덩어리 끝까지 읽으면 다음 매물의
단지명·가격까지 메모로 들어간다.

메모가 없는 카드도 많다. 중개사 여러 곳이 올린 매물은 접혀서 "중개사 4곳에서
등록했어요" 만 나온다 — 실측 46건 중 메모가 붙은 것은 33건이었다.

규칙은 북마클릿(`tools/bookmarklet.js` 의 `memoOf`)과 백엔드
(`listing_parse.parse_memo`)에 **같이** 있다. 한쪽을 고치면 양쪽을 고칠 것.

### 원문을 저장하고, 키워드는 읽을 때 뽑는다

`Quote.memo` 에 원문을 그대로 둔다. 저장할 때 키워드로 바꿔 두면 사전을 고쳐도 옛
행은 옛 태그를 달고 있다. 이 사전은 **측정으로 키우는 것을 전제로** 만들었으므로
언제든 다시 뽑을 수 있어야 한다.

같은 (단지·동·평형·층·호가)를 중개사 여러 곳이 올리면 메모도 여럿이다. 덮어쓰지
않고 줄바꿈으로 덧붙인다 — 한 곳만 '급매' 라고 적었어도 그건 사실이고, 덮어쓰면
나중에 들어온 것이 앞의 것을 조용히 지운다. `ranking.merge_duplicates` 에서도
합집합을 쓴다.

### 사전은 실제 메모 50건을 재서 만들었다

추측으로 적지 않았다. 규칙 18개가 **전부** 한 번 이상 걸렸고, 50건 중 48건이 태그를
하나 이상 받았다. 못 받은 둘은 "맘에 쏙드는 집, 신혼부부추천" 과 "임대놓기좋은
원룸.깔끔.주차장.엘레베이터" 로, 가격에 걸리는 말이 없다.

재면서 잡은 오탐 둘.

- `협의\s*가` 로 '가격 협의' 를 잡으려 했더니 **'입주협의가'** 가 걸렸다. 입주 날짜
  얘기지 가격 얘기가 아니다. 뗀 대신 '할인' 을 더해 "확정가500할인됨" 을 얻었다.
- `에\s*2` 로 '에어컨 2대'(`시에2대`·`에2`)를 잡으면 **'전세 2억에 2억9천'** 같은
  금액 표현이 걸린다. 숫자 뒤에 억/만/천/% 가 오면 뺀다.

적중 상위: 시스템에어컨 22 · 전망 16 · 즉시입주 14 · 세안고 11 · 입주협의 11 ·
올수리 9 · 분양권P 5 · 투자 5 · 채광 5.

`RULES` 의 **순서가 곧 표시 우선순위**다. 비고 칸이 좁아 앞의 셋만 배지로 나가므로
가격에 걸리는 것(급매·세안고·분양권P·조정가능)이 앞에 와야 한다.

### 사전을 늘릴 때는 다시 잰다

    python -m scripts.memo_report              # 쌓인 메모에 사전을 다시 재 본다
    python -m scripts.memo_report --min 3      # 3번 이상 나왔는데 아직 규칙 없는 낱말

이 스크립트가 답하는 것 셋 — 규칙마다 지금 몇 건이 걸리나(0건이면 지울 것이거나
패턴이 어긋난 것), 태그를 못 받은 메모는 무엇인가, 자주 나오는데 아직 아무 규칙에도
안 걸리는 낱말은 무엇인가. **눈으로 보고 늘리지 말 것.** 늘렸으면 다시 돌려 적중
수를 주석에 남긴다.

## 한 번에 몇 건까지 옮길 수 있나 — 재 봤다

사슬에 한계가 여럿인데 **백엔드 입력 길이가 가장 먼저 걸린다.**

| 한계 | 값 | 매물 환산 |
|---|---|---|
| `BulkRequest.text` max_length | 200,000자 | **약 2,100건** (북마클릿) · 약 1,550건 (드래그 복사 원문) |
| sessionStorage (북마클릿 버퍼) | 브라우저 5MB 안팎 | 약 26,000건 — 한참 멀다 |
| 클립보드 | 사실상 없음 | — |

한 건당 길이(실측 46장): 메모 있는 카드 99자 · 없는 카드 70자 · 구분자 포함 평균
**92.5자**. 북마클릿이 단지명·가격·면적층·날짜·메모만 남기므로, 드래그 복사한
원문(129자/건)보다 짧다.

처리 시간도 쟀다. **1,058건(13.7만 자)이 4.0초**다. 322건은 1.3초, 46건은 0.4초.

### 넘겼을 때 조용하지 않게

20만 자를 넘기면 422 가 온다. 그런데 FastAPI 의 422 `detail` 은 문자열이 아니라
**배열**이라, 그대로 Error 에 넣으면 화면에 `[object Object]` 만 떴다. 서버는
"String should have at most 200000 characters" 라는 쓸 만한 말을 보내고 있었는데
화면이 버린 것이다.

`api.js` 의 `detailText()` 가 배열이면 `msg` 들을 모아 한 줄로 만든다. **한계에
부딪히는 것 자체는 괜찮다 — 왜 막혔는지 모르는 것이 문제다.**
