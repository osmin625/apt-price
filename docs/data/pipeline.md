# 데이터 파이프라인

공공 API 에서 실거래·단지·역·입지를 가져와 채우는 과정과, 그 과정에서 조용히
틀어지는 자리들. 대상 지역을 넓히는 방법도 여기에 있다.

한국부동산원 공표 통계(가격 분석 탭)는 성격이 달라 [공표 통계](reb.md) 로 뺐다 —
우리가 거래를 모아 만드는 값이 아니라 **남이 계산해 공표한 값**이다.
붙여넣은 매물을 우리 단지·평형에 맞추는 규칙과 중개사 메모는 [붙여넣은 매물](listings.md)
에 있다 — 모으는 데이터가 아니라 사용자가 가져온 텍스트다.

## 키 발급과 적재

`scripts/seed_demo.py` 가 만드는 데이터는 **합성 데이터**다. 단지명·법정동·역 정보는 실제
수원시 기준이지만 가격과 거래 건수는 시뮬레이션이므로 실제 시세 판단에 쓰면 안 된다.

실거래가를 쓰려면 `backend/.env` 에 키를 넣는다.

| 키 | 위치 | 발급처 | 없으면 |
|---|---|---|---|
| `MOLIT_SERVICE_KEY` | `backend/.env` | [공공데이터포털 — 국토교통부_아파트 매매 실거래가 **상세** 자료 (15126468)](https://www.data.go.kr/data/15126468/openapi.do) 의 일반 인증키(Decoding) | 합성 데이터로 동작 |
| `KAKAO_REST_KEY` | `backend/.env` | [카카오 개발자센터](https://developers.kakao.com) > 내 애플리케이션 > 앱 키 > REST API 키 | 단지 수집·좌표 조회 불가 |
| `VITE_KAKAO_JS_KEY` | `frontend/.env.local` | 같은 카카오 앱의 **JavaScript 키** (REST 키와 다른 키) | 지도 탭이 설정 안내로 대체 |
| `TMAP_APP_KEY` | `backend/.env` | [SK open API](https://openapi.sk.com) > 보행자 경로안내 | 직선거리×1.25 추정치로 자동 폴백 |

카카오 JS 키를 쓰려면 개발자센터 > 플랫폼 > Web 에 `http://localhost:5173` 과
`http://127.0.0.1:5173` 을 **둘 다** 등록해야 한다. 카카오는 origin 을 완전일치로 검사하고
Vite 는 127.0.0.1 로 프록시한다.

이름이 거의 같은 **국토교통부_아파트 매매 실거래가 자료(15126469)** 를 신청하면 안 된다.
그쪽은 동 정보(`aptDong`)와 계약 해제 여부(`cdealType`)가 빠져 있어, 해제된 거래를
걸러내지 못하고 시세가 위로 왜곡된다.

인증키는 **Encoding / Decoding 두 가지로 발급**되는데 이 프로젝트는 `httpx` 가 쿼리스트링을
직접 인코딩하므로 **Decoding 키**를 넣어야 한다. Encoding 키를 넣으면 이중 인코딩되어
`SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 난다.

활용신청은 자동승인이지만 키가 실제로 활성화되기까지 보통 **수십 분에서 1시간** 걸린다.
바로 호출해서 오류가 나면 조금 기다렸다가 다시 시도할 것. 개발계정 트래픽은 일 10,000건이며,
17개 시군구 × 24개월 = 408회 호출이라 넉넉하다(구·월당 약 0.5초).

### API 재호출 방지

한 번 받은 것은 다시 받지 않는다. 스크립트를 여러 번 돌려도 안전하다.

| 스크립트 | 건너뛰는 조건 | 다시 받으려면 |
|---|---|---|
| `geocode` | `Complex.lat` 이 이미 있으면 | `--force` |
| `seed_stations` | 역 좌표가 이미 있으면 | `--force` |
| `route_walk` | `routed_at` 있고 출처가 `tmap` 이면 | `--force` |
| `ingest_trades` | 그 (구, 월) 조합이 이미 적재돼 있으면 | `--refetch-all` |

**국토부만 예외가 있다.** 실거래 신고 기한이 계약 후 30일이라 지난달 데이터도 계속
늘어난다. 그래서 **최근 3개월은 항상 다시 받는다**(`--refetch-recent N` 으로 조절).
덕분에 24개월 재실행이 96회 호출 → 12회, 3~4분 → 12초가 된다.

```bash
cd backend
python -m scripts.ingest_trades --months 24   # DISTRICTS 전체(17개 구) 실거래 적재
python -m scripts.geocode                     # 좌표 변환 + 최근접 지하철역 거리
python -m scripts.seed_stations --force       # 역 좌표 채우기
python -m scripts.route_walk                  # 도보 경로 (TMap 키 있으면 실거리)
python -m scripts.geocode_dongs               # 동별 좌표 + 동별 역거리
python -m scripts.ingest_kapt --check         # 세대수 (K-apt 활용신청 필요)
```

**스키마를 바꿨을 때**는 `--recreate-schema` 로 통째로 다시 만드는 대신
`python -m scripts.migrate` 로 빠진 컬럼만 추가한다. 실데이터가 들어 있으면
재생성에 API 호출 수십 분이 다시 들기 때문이다. 컬럼 추가만 하고 타입 변경·삭제는
하지 않으므로, 그런 변경에는 여전히 재생성이 필요하다.

### 세대수 (K-apt)

data.go.kr 은 **계정당 인증키가 하나**라 기존 `MOLIT_SERVICE_KEY` 를 그대로 쓴다.
다만 서비스마다 활용신청은 따로 해야 한다(자동승인).

- [공동주택 기본 정보제공 서비스 (15058453)](https://www.data.go.kr/data/15058453/openapi.do) — 세대수·동수
- [공동주택 단지 목록제공 서비스 (15057332)](https://www.data.go.kr/data/15057332/openapi.do) — 단지코드

`python -m scripts.ingest_kapt --check` 가 신청 상태를 알려준다. 응답 코드로 구분한다 —
**30번은 "경로는 맞는데 미신청"**, 12번은 "경로가 틀림". 이 둘을 구분해야
신청을 더 해야 하는지 코드를 고쳐야 하는지 알 수 있다.

K-apt 에서 밟은 함정 셋. 전부 **오류 없이 조용히 빈 결과**가 되는 종류다.

1. **오퍼레이션 이름 끝의 `4`.** 서비스가 `AptListService4` 면 오퍼레이션도
   `getSigunguAptList4` 다. `getSigunguAptList` 로 부르면 코드 12 가 오는데,
   미신청과 구분이 안 돼 원인을 찾기 어렵다.
2. **응답 모양이 서비스마다 다르다.** 단지목록은 `body.items.item`, 기본정보는
   `body.item` (복수형이 아니다).
3. **세대수가 `1240.0` 처럼 실수로 온다.** `int("1240.0")` 은 ValueError 라
   float 을 거쳐야 한다. 안 그러면 호출은 성공하는데 세대수만 전부 None 이 된다.

단지 매칭은 K-apt 이름에 붙은 **지역 접두어**를 벗겨야 한다
(`정자동 송학아파트` vs 국토부 `송학`). 다만 이름만으로 붙이면 위험해서
**준공년도 교차검증**(K-apt 와 국토부가 독립 보고한 값이 1년 이내)을 함께 건다.
접두어 처리로 매칭이 154 → 264곳으로 늘었다.

### 단지를 늘리기 (카카오 키만 있으면 국토부 키 없이도 가능)

기본 시드의 25곳으로는 2단계 회귀 표본이 부족하다. 특히 강남접근성 항은 유효 클러스터가
4개 수준이라 해석이 어렵다. 카카오로 실제 단지를 수집해 250~300곳으로 늘린다.

```bash
python -m scripts.fetch_complexes --dry-run   # 먼저 눈으로 검수
python -m scripts.fetch_complexes --max 300
python -m scripts.seed_stations --force
python -m scripts.route_walk
python -m scripts.seed_demo                   # 늘어난 단지로 거래 재생성
python -m scripts.validate_model --coverage 40
```

`--dry-run` 을 **반드시 먼저** 돌려 법정동별 단지 수와 제외된 POI 목록을 확인할 것.
키워드 검색에는 상가·관리사무소·중개업소가 섞여 들어오고, 경계 타일은 용인 기흥이나
화성 병점을 끌어온다. 필터가 잡고 있지만 눈으로 한 번 보는 게 싸다.

`ingest_trades` 는 계약 해제건(`cdealType == "O"`)을 제외하고, 동일 거래를
`(단지, 계약일, 전용면적, 층, 거래금액)` 으로 중복 제거한다. 여러 번 돌려도 안전하다.

단지 식별은 단지명 완전일치가 아니라 **정규화 키**(`pricing.name_key`)로 한다. 카카오는
`래미안영통마크원2단지`, 국토부는 `래미안 영통 마크원 2단지` 를 주기 때문이다. 완전일치로
두면 국토부 적재 시 고아 중복 단지가 생기고, 지오코딩·TMap 호출을 태운 행에 거래가 하나도
붙지 않는다. `N차` 는 정규화하되 **제거하지 않는다** — 래미안1차와 2차는 실제로 다른 단지다.

## 대상 지역을 넓히기

`app/clients/molit.py` 의 `DISTRICTS` 에 시군구 코드를 더하면 그대로 확장된다.
분석 로직에 특정 도시 전용 가정은 없다.

### 코드를 기억으로 적지 않는다

처음에 화성시를 `41590` 으로 적었다가 실거래 **0건**을 받았다. 화성시가 구로 나뉘면서
코드가 41591(만세구)·41593(효행구)·41595(병점구)·41597(동탄구) 로 갈린 것이었다.
틀린 코드는 오류가 아니라 **0건으로 조용히 지나간다** — 결과만 봐서는 알 수 없다.

그래서 13개 코드를 전부 확인하고 적었다. 코드마다 실거래를 한 달치 받아 법정동을 꺼낸 뒤,
카카오 주소 API 의 `b_code` 앞 5자리가 그 코드와 맞는지 대조했다. 코드를 추가할 때도
같은 방식으로 확인할 것.

### 역 테이블이 약한 고리다

강남 소요시간은 공개 대중교통 길찾기 API 를 쓰지 않아 **수기 표**다(`scripts/seed_stations.py`).
표가 21개에서 67개로 커지면서 세 종류의 오류가 드러났고, 전부 검사로 잡았다.

| 검사 | 잡아낸 것 |
|---|---|
| 노선 단조성 (`check_monotone`) | 성균관대역이 화서역보다 강남에 가까운데 4분 느리게 적혀 있었다 |
| 이름 대조 (`station_name_matches`) | 운동장·송담대역 → **용인중앙시장역** 개명, GTX-A '용인역' → 실제로는 **구성역** |
| 좌표 검증 | **영덕역은 존재하지 않는 역**이었다. 카카오가 청명역 좌표를 그대로 돌려줬고(좌표 완전 일치), 강남 43분으로 청명역(48분)보다 5분 빠르게 잡혀 단지 65곳이 여기에 붙어 있었다 |

세 검사 모두 매 실행마다 돈다. 수기 표는 커지면 반드시 어긋나므로, 어긋남을 사람이
발견하기를 기다리면 안 된다.

> 강남접근성 계수는 이 표만큼만 정확하다. **다른 요인(면적·층·도보·연식·세대수·동 위치)은
> 실거래에서 직접 추정되므로 이 한계의 영향을 받지 않는다.** 실측이 필요하면 ODsay 같은
> 대중교통 길찾기 API 를 붙여 이 표를 대체하면 된다.

### 매듭 수는 표본이 정한다

요인 곡선을 얼마나 촘촘히 볼 수 있는지는 표본이 정한다(`hedonic.knots_for`). Stage 2 의
관측치는 **단지 수**라, 수원만 볼 때 497곳에서는 매듭 4개가 상한이었다. 경기 남부로
넓혀 2,000곳을 넘으면서 7개까지 쓸 수 있게 됐다 — 요인당 열이 3개에서 6개로 늘어난다.

| 단지 수 | 매듭 | 근거 |
|---|---|---|
| < 250 | 4 | 표본이 작으면 Harrell 권고 하한 |
| < 700 | 5 | |
| < 1,500 | 6 | |
| ≥ 1,500 | 7 | 요인 4개 × 6열 + FE 20여 열 = 45열, 관측당 30배 |

화면의 곡선 범위도 코드에 박지 않고 적합이 돌려준 관측 분포(`var_range`, p1~p99)에서
가져온다. 박아 두면 지역을 넓혔을 때 곡선이 데이터 없는 구간까지 그려지거나 있는 구간을
잘라 먹는다.

## 거래 유형 (중개거래 / 직거래)

국토부 상세 자료의 `dealingGbn` 이다. 전체의 **2.9%** 가 직거래다.

### 왜 가려야 하나

직거래는 **같은 단지·같은 전용면적·같은 시점 안에서도 13.9% 싸다**(회귀 추정,
SE 0.44%p, p≈0). 증여성 거래나 친족 간 이전이 섞여 있어서다. 구성 효과가 아니라는
것은 따로 확인했다 — 같은 칸 안에서 둘 다 있는 190칸 중 **171칸이 음수**였다.

비중이 작아 보이지만 **몰린 단지가 있다.** 거래 3건 이상인 단지 중 직거래가 과반인
곳이 13곳이고, 95%인 단지도 있었다. 그런 단지는 시세가 통째로 내려가 '저평가' 순위
상위에 가짜로 올라온다.

### 두 경로를 다르게 다룬다

- **회귀(Stage 1)**: 더미로 넣는다. 빼지 않는다. α̂_c = mean_c(y − Zβ̂) 이므로
  더미를 넣으면 직거래 행에서 할인분이 되돌아와, α̂_c 가 '전부 중개거래였다면'
  수준이 된다. 빼 버리면 그 거래의 층·면적·시점 정보까지 같이 버린다.
- **비교표본(중앙값)**: 뺀다. 중앙값은 통제할 방법이 없고, 이 경로가 답하는 질문은
  "비슷한 집이 **실제로 얼마에 팔리나**" 라 증여성 거래는 답이 아니다.

### 이미 적재한 거래를 채우는 길

`dealingGbn` 을 나중에 받기 시작했다. 그런데 `ingest_trades` 는 같은 거래가 다시
오면 **건너뛴다.** 그대로 두면 재적재를 돌려도 기존 11.7만 행은 영영 빈 채로 남고,
전부 지우고 다시 받는 것은 몇 시간짜리다.

그래서 중복일 때 **비어 있는 값만 채운다.** 가격·면적처럼 이미 있는 값은 건드리지
않는다 — 덮어쓰기 시작하면 이 스크립트가 '적재' 가 아니라 '동기화' 가 되고, 국토부가
값을 고쳤을 때 조용히 과거가 바뀐다.

**`--refetch-all` 이 필요하다.** 이미 받은 (구, 월) 조합은 캐시로 건너뛰고 최근
3개월만 다시 받기 때문이다. 이걸 모르고 `--months 25` 만 주면 3개월치 6,758건만
채워지는데, 요약은 그냥 "적재 완료" 라고 찍힌다. 행 수를 직접 세어 보고 알았다.

    python -m scripts.ingest_trades --months 25 --refetch-all   # 11.7만 건 ~13분

### SQL 삼치논리 — 조용히 빠진다

`deal_type != '직거래'` 로 거르면 **NULL 인 행이 조용히 빠진다.** 적재 전 거래
111건이 그랬다. `coalesce(deal_type, '') != '직거래'` 를 쓴다. (SQLite 의 UNIQUE 가
NULL 끼리를 서로 다른 값으로 보는 것과 같은 계열의 함정이다.)

### 적재 후에 해제된 거래는 남는다 — 세기는 한다

API 가 더 이상 돌려주지 않는 거래가 **111건**(0.09%) 있다. 적재한 뒤에 계약이 해제된
건들로 보인다(`cdealType == "O"` 는 받는 시점에만 걸러진다).

**지우지는 않는다.** API 가 일시적으로 비면 멀쩡한 거래를 통째로 날리게 된다 — 공공
API 가 그러는 것을 이 저장소에서 이미 겪었다(K-apt 일시 오류로 시군구 6곳이 빠졌다).
대신 재조회할 때마다 **센다.** 문제는 크기가 아니라 조용히 자란다는 것이라, 적재
요약에 숫자가 찍히기만 해도 된다. 응답이 비어 있는 달은 세지 않는다 — 그 경우
'전부 해제됐다' 가 아니라 '못 받았다' 일 가능성이 높다.

비율이 커지면 그때 '최근 N개월은 해제분을 반영해 지운다' 를 넣는다.


## 단지 주변 입지 (소상공인 상가정보 + 카카오)

`complex_amenities` 에 단지당 한 줄. 적재는 `scripts/ingest_amenity.py`, 전체
2,469곳이 **약 15분**이다(실측: 소상공인 2,924회 · 카카오 6,296회 · 실패 0).

### 왜 출처가 둘인가

가게는 **소상공인시장진흥공단 상가(상권)정보**에서 받는다. 학교는 상가가 아니라
거기 없으므로 카카오 카테고리 검색(`SC4`)으로 받는다.

처음에는 전부 카카오로 하려 했다. 세는 비용이 싸기 때문이다 — `meta.total_count` 가
**45개 상한과 무관하게 정확하다.** 반경 1km 학원 335건을 문서는 45개만 주면서 수는
335 로 돌려준다. 그래서 수만 필요하면 `size=1` 로 한 번 부르면 된다.

키워드 검색이 상호명이 아니라 `category_name` 을 본다는 것도 확인했다. 범계역 반경
500m 에서 `query=술집` 이 73건인데 표본 15개가 전부 `음식점 > 술집 > *` 이었고 상호에
'술집' 이 든 것은 1개뿐이었다. 짐작으로 넘기지 않고 **전수로 대조**했다 — FD6 총건수가
45 이하가 되는 좁은 반경에서 음식점을 전부 받아 직접 센 값과 질의 결과가 7개 지점에서
모두 일치했다.

**그런데 유흥을 가를 수가 없다.** 카카오의 '술집' 한 덩어리에는 요리주점·생맥주 같은
생활 상권과 유흥주점이 섞여 있다. 소상공인 쪽은 식품위생법 업종이 그대로 들어온다.

    음식 > 주점 > 요리 주점 / 생맥주 전문 / 일반 유흥 주점 / 무도 유흥 주점

이 구분이 결정적이었다. 모델에 넣어 보니 **섞으면 효과가 사라지고, 갈라야 유흥만
음수로 유의**했다.

### 인증키

`MOLIT_SERVICE_KEY` 를 그대로 쓴다. data.go.kr 일반 인증키는 계정 단위라 하나로 여러
API 를 쓴다. 다만 **활용신청은 API 마다 따로** 해야 하고, 신청 전에는 HTTP 403 에

    "errMsg": "SERVICE_KEY_IS_NOT_REGISTERED_ERROR"  // 등록되지 않은 서비스키

가 온다. **키가 틀린 것이 아니다.** 그래서 클라이언트가 그렇게 안내한다.
신청: https://www.data.go.kr/data/15083033/openapi.do

### 페이징 상한이 1000 이다

`numOfRows` 에 2000 을 줘도 1000 건만 온다(재서 확인했다). 반경 500m 번화가는 2,700건
까지 나오므로 `totalCount` 를 보고 끝까지 넘겨야 한다. 받은 수가 총건수에 못 미치는데
멈추면 **그 단지만 조용히 적게 세어진다** — 오류가 아니라 작은 숫자로 보인다.
`sdsc.stores_in_radius` 는 그 경우 예외를 던진다.

### 조용히 틀리지 않게 하는 것들

- **cx/cy 는 경도/위도 순이다.** 바꿔 넣으면 한국 밖을 찾아 0건이 오는데, 그건 오류가
  아니라 빈 결과다. 적재 전에 좌표가 경기 남부 범위 안인지 전수 검사한다.
- **0건을 성공으로 넘기지 않는다.** 실측 최소가 상가 3건, 중위 511건, 최대 2,981건
  이었다. 0건이면 좌표나 호출이 잘못된 것으로 보고 끝에 모아 보고한다.
- 거리는 API 반경을 믿지 않고 **좌표로 다시 센다.** 위도 37도에서 평면 근사면 충분하다
  (하버사인과 cm 단위 차이).

### 무엇을 저장하고 무엇을 버렸나

저장하는 것은 집계값 네 개다 — 초·중학교 거리, 학원 수(500m), 유흥주점 수(500m).

처음에는 열 가지를 모았다(음식점·소매·의원·숙박·오락·주점·대형마트·고등학교…).
교차검증으로 하나씩 가려 보니 **학교 거리 위에 아무것도 더하지 못했다.** 경과는
[요인](../model/factors.md) 에 있다. 반경 500m 상가 원자료는 단지당 중위 511건이라
2,469곳이면 백만 행이 넘는데, 쓰는 것이 네 개면 다시 받는 쪽이 싸다(전체 15분).

### 갱신

상가는 분기마다 바뀌고 학교는 거의 안 바뀐다. `collected_at` 을 보고 오래된 것부터
돌린다.

    python -m scripts.ingest_amenity --older-than 90

거래 가격은 수시로 들어오지만 이 값은 단지의 성질이라 자주 받을 이유가 없다.
