# 성능

느려진 곳을 어떻게 찾아 무엇을 고쳤는지. 전부 프로파일러로 재고 나서 손댔고,
빠르게 만든 것이 같은 답을 내는지는 매번 비교로 확인했다.

### 순위 계산이 16.7초에서 1.1초로

대상을 넓히자 매물 순위 페이지가 눈에 띄게 느려졌다. 프로파일러가 답을 바로 줬다.

| | 이전 | 이후 |
|---|---|---|
| 순위 계산(매물 56건) | 16.7s | **1.1s** |
| `model_price` | 14.5s | 0.02s |
| `load_points` | 2.8s | 0.21s |

두 가지였고 **둘 다 지역을 넓히기 전에도 있던 낭비**다. 수원만 볼 때는 규모가
4분의 1이라 드러나지 않았을 뿐이다.

**1. 매물마다 단지 전체를 훑었다.** `model_price` 가 단지 하나를 꺼내려고 이렇게 했다.

```python
rows = {int(r["complex_id"]): r for _, r in fit["alpha"].iterrows()}
```

단지 2,018곳을 도는 데다 `iterrows()` 는 행마다 Series 를 새로 만든다. 매물 56건이면
113,008번이다. 조회표는 적합이 바뀌지 않는 한 그대로이므로, 적합 dict 에 매달아
한 번만 만든다(`model_view.fit_index`).

**2. 열 몇 개 쓰자고 ORM 객체를 만들었다.** `load_points` 가 `select(Trade, Complex)`
로 엔티티를 통째로 읽었는데, 실제로 쓰는 것은 열 열세 개뿐이다. 한 구의 24개월치가
3만 행을 넘으면서 ORM 인스턴스 생성만 31,602회였다. 컬럼만 읽도록 바꿨다.

빠르게 만든 것이 **같은 답을 내는지**는 눈이 아니라 비교가 답한다. 매물 69건 전부에
대해 캐싱 전후 결과를 통째로 비교했고(차이 0건), `load_points` 는 필터 조합 10가지를
옛 구현과 대조했다(전부 일치).

### 적합은 별도 프로세스에서 돈다

적합은 14초쯤 걸리는데 대부분이 numpy/statsmodels 안에서 **GIL 을 쥔 채** 도는 연산이다.
FastAPI 가 동기 엔드포인트를 스레드풀에 넘겨도 GIL 은 풀리지 않아, 적합이 도는 동안
다른 모든 요청이 같이 멈춘다. `services/fit_worker.py` 가 `ProcessPoolExecutor`(워커 1개)
로 이를 분리한다.

| | 적합 | 동시 `/api/complexes` 지연(최대/중앙) | 그동안 처리한 요청 |
|---|---|---|---|
| 인프로세스 | 20.0s | 4.4s / 2.6s | 7회 |
| 별도 프로세스 | 13.6s | 2.2s / 1.9s | 10회 |

무경쟁 기준선이 1.4s 이니 거의 회복된다. 설계 메모:

- 워커는 **자기 세션을 연다**. 세션·커넥션은 프로세스 경계를 넘길 수 없다. 넘기는 것은
  `(months, spec)` 뿐이고 결과는 피클로 돌아온다(119KB, 3ms).
- 같은 키의 동시 요청은 `_inflight` 로 묶어 **한 번만** 계산한다. 안 그러면 탭 두 개만
  열어도 14초짜리 적합이 두 번 돈다.
- 풀은 재사용한다. 윈도우는 spawn 이라 자식이 pandas/statsmodels 를 다시 import 하는 데
  몇 초 걸리는데, 살려 두면 그 비용은 첫 적합 한 번뿐이다(1회차 13.2s → 2회차 9.1s).
- **실패하면 인프로세스로 떨어진다.** 프로세스 생성이 막힌 환경에서도 앱은 돌아야 한다.
  `FIT_IN_PROCESS=1` 로 강제할 수도 있다.
- **워커는 워커를 만들지 않는다.** 이 판정을 모듈 전역(`_IS_WORKER`)으로 두었다가 한 번
  뚫렸다. 그 값은 `app.services.fit_worker` 라는 **모듈 객체**에 붙어 있어서, 워커가 같은
  모듈을 다른 경로로 한 번 더 import 하면 전역이 둘이 되고 `run()` 이 읽는 쪽은 여전히
  False 다. 실제로 앱(18008) → 워커(4356) → **또 워커(3336)** 가 잡혔고, 3336 의
  커맨드라인은 `spawn_main(parent_pid=4356)` 이었다. 워커가 워커에 적합을 맡기고 기다리는
  동안 서버 전체가 응답을 멈췄다. 지금은 `multiprocessing.parent_process()` 로 **프로세스
  단위**로 판정한다 — 메인에서만 None 이라 모듈 정체성과 무관하게 흔들리지 않는다.
- 시작할 때 백그라운드로 **예열**한다(`FIT_WARM=0` 으로 끔). 첫 사용자가 14초를 기다릴
  이유가 없고, 동 프리미엄처럼 적합이 있어야 붙는 정보가 첫 화면부터 나온다.

탭은 다섯이다. **시장 분석**은 요인별 보정계수 전용, **단지 비교**는 구간 기반 기술통계,
**지도 · 거리 모델**은 연속 거리 모델링 경로, **매물 분석**은 진단과 비교를 한 화면에서 쓴다.
