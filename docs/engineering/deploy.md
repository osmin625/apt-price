# 배포 — 로컬은 동적, 공개는 정적

모델을 돌리는 것과 결과를 보여 주는 것은 필요한 것이 다르다.

| | 필요한 것 | 어디서 |
|---|---|---|
| 데이터 적재 · 모델 적합 · 매물 붙여넣기 | numpy·pandas·statsmodels, 실거래 11만 건, 수십 초의 계산, DB 쓰기 | 로컬 (동적) |
| 결과 보기 | JSON 한 묶음 | 어디서나 (정적) |

그래서 무거운 쪽은 로컬에 두고, 가벼운 쪽만 정적 사이트로 올린다. 정적 사이트는
백엔드가 없고 파이썬도 필요 없다.

## 흐름

```
로컬 대시보드 (동적)
  적재 · 적합 · 매물 붙여넣기
        │
        │  export_static.py   화면이 부르는 요청을 실제 ASGI 앱으로 실행해
        │                     응답을 JSON 파일로 떨어뜨린다
        │                     (크기는 `python -m scripts.checkup` 이 찍는다)
        ▼
  frontend/public/snapshot/
        │
        │  npm run build:static   VITE_DATA_MODE=static 으로 빌드.
        │                         api.js 가 /api 대신 스냅샷 파일을 읽는다
        ▼
  frontend/dist/
        │
        │  gh-pages 에 고아 커밋 하나로 강제 푸시
        ▼
  정적 사이트
```

한 번에 돌리는 것은 `sync_static.ps1` 이다.

```powershell
.\sync_static.ps1              # 내보내기 + 빌드 + 배포
.\sync_static.ps1 -NoPublish   # 배포 없이 로컬에서 확인만
.\sync_static.ps1 -NoQuotes    # 호가(호가 분석·단지 상세) 제외
```

배포 전 확인:

```powershell
cd frontend; npm run preview:static   # http://localhost:4173/apt-price/
```

## 크기는 문서에 적지 않는다

예전에는 흐름도에 "80개 파일 · 8.2MB" 라고 적어 뒀다. 재 보니 **2,160개 · 38.3MB**
였다. 단지 상세와 도보 경로가 단지 수만큼 늘어난 뒤로 자릿수가 달라졌는데 문서만
그대로였다.

지금 크기는 `python -m scripts.checkup` 이 찍는다. 임계값도 거기 있다 — 넘으면
`[!]` 로 알려 준다.

### 무엇이 무거운가 — 재서 고쳤다

순위 스냅샷 하나가 2.19MB 였고 그중 **47%가 `factor_parts`** 였다. 단지 요인 분해를
매물마다 실어 보냈기 때문인데, **같은 단지면 값이 같다** — 매물 1,018건이 단지
39곳에 몰려 있었다.

단지 몫을 payload 꼭대기의 `complex_parts` 로 한 번만 보내고 행에서는 `complex_id`
로 찾아 쓴다. 행에는 그 집 몫(`unit`)만 남는다.

    순위 스냅샷 24개   31MB → 19MB
    그중 하나         2.19MB → 1.35MB
    factor_parts      1.02MB → 0.19MB (행 0.16 + 단지 분해 0.03)
    전체 dist         38.3MB → 26.4MB

## 정적 사이트에 실리는 것

`App.jsx` 의 `TABS` 에서 `static: true` 인 것만 보인다.

| 탭 | 정적 | 이유 |
|---|---|---|
| 매물 분석 | O | 요인별 보정계수 + 도보거리 상세 창까지 전부 |
| 가격 분석 | O | 한국부동산원 공표 통계. 카드가 있는 지표 × 기간 셋이라 전부 내보낸다(목록은 `macro.METRICS` 에서 뽑는다) |
| 공급 분석 | O | 응답 하나(`/api/supply/overview`). 파라미터가 없다 |
| 거시 분석 | O | 응답 하나. 요인 상관을 서버에서 재서 담는다(88KB) |
| 호가 분석 | O | 단지명을 누르면 단지 상세도 열린다 |
| 지도 | 조건부 | 데이터는 늘 내보낸다. **키 때문에** 기본은 꺼 둔다 — 아래 참조 |
| 분해 모델 | O | `/model/fit` 은 이미 내보내던 것이고, 묶어 보기(`/model/groups`)를 기준 × 기간만큼 더했다(기준 목록은 `model_view.GROUP_BY` 에서 뽑는다) |
| 호가 입력 | **불가** | 붙여넣은 텍스트를 그 자리에서 파싱·평가한다. 미리 파일로 만들 수 없다 |

## 지도 탭 — 데이터가 아니라 키가 문제다

지도가 부르는 넷 중 둘은 다른 화면 때문에 **이미 스냅샷에 있었다.**

| 요청 | 크기 |
|---|---|
| `/map/complexes?months=N` | 1.1MB × 3 (도보거리 상세 창이 이미 쓰고 있었다) |
| `/model/fit?months=N` | 14KB × 3 |
| `/map/stations` | 10KB · 파라미터 없어 한 개 |
| `/map/walk-path/{id}` | 365바이트 × 1,851 ≈ 0.7MB |

그래서 지도를 켜도 **데이터가 늘지 않는다** — 도보 경로는 어차피 내보낸다.
막는 것은 **카카오 JS 키 하나**다.

지도를 띄우려면 키가 번들에 들어가야 한다. `App.jsx` 가 `MapView` 를 정적
import 하므로 `kakaoMap.js` 의 `import.meta.env.VITE_KAKAO_JS_KEY` 가 인라인된다 —
**지도 탭을 숨겨 둔 상태에서도 그랬다.** 실제로 확인했고, 그래서 `.env.static` 에서
비워 뺐다.

JS 키는 원래 클라이언트에 노출되는 키다(카카오 지도를 쓰는 모든 사이트의 소스에
보인다). 노출 자체가 사고는 아니지만, 보호 수단인 도메인 허용목록이 Referer
기반이라 우회가 불가능하지는 않다 — 쿼터를 남이 쓸 수 있다는 뜻이다. 그래서
**기본은 끈 상태**로 두고 켜는 것을 의도적인 행위로 만들었다.

백엔드가 지오코딩에 쓰는 `KAKAO_REST_KEY` 는 **다른 키**이고 `backend/.env` 에만
있다. 정적 번들로는 절대 나가지 않는다.

### 켜는 방법

1. `frontend/.env.static.local` 을 만든다(`.gitignore` 의 `.env*.local` 에 걸려
   커밋되지 않는다). `.local` 이 `.env.static` 보다 우선하므로 둘 다 덮인다.

   ```
   VITE_KAKAO_JS_KEY=<발급받은 JS 키>
   VITE_STATIC_MAP=1
   ```

2. **카카오 개발자센터 > 내 애플리케이션 > 플랫폼 > Web** 에 배포 주소를 등록한다
   (예: `https://osmin625.github.io`). 카카오는 origin 을 완전일치로 검사하므로
   등록하지 않으면 지도 탭만 설정 안내로 바뀐다(나머지 탭은 정상).

   로컬에서 `npm run preview:static` 으로 확인하려면 `http://localhost:4173` 도
   같이 등록해야 한다 — 개발 서버(5173)와 다른 포트다.

3. `.\sync_static.ps1` 로 다시 배포한다.

끄려면 `.env.static.local` 을 지우고 다시 배포한다. 키가 번들에서 빠지고 탭도
사라진다. 다만 **이미 배포된 번들에서 읽힌 키는 되돌려지지 않으므로**, 공개한 뒤
마음이 바뀌면 카카오에서 키를 재발급하는 쪽이 확실하다.

### 도보 경로는 404 가 정상이다

역 정보가 없는 단지는 `/map/walk-path/{id}` 가 404 를 준다. 고장이 아니다 —
프론트도 그때 `null` 로 받아 점선 직선을 그린다. 내보내기는 이 경우를
`allow_404` 로 표시해 **실패로 세지 않는다.** 세면 매 실행이 실패로 끝나고,
그러면 진짜 실패와 구분할 수 없다. `meta.json` 의 `walk_paths_absent` 에 건수가
남는다.

### 두 단계로 내보내는 이유

도보 경로 목록은 **계획 단계에 알 수 없다.** 지도에 뜨는 단지 집합은
`/map/complexes` 가 정하는데(거래가 있고 좌표가 있는 단지), 내보내기 쪽에서 DB 를
다시 질의하면 그 조건을 재구현하는 셈이라 어긋난다. 그래서 1단계에서 내보낸 지도
응답을 **읽어서** 그 id 를 쓴다 — 이미 받아 둔 답이 있으면 다시 묻지 않는다.

**눌리는데 실패하는 것을 두지 않는다.** 삭제 버튼과 새로고침은 정적에서 숨긴다.
그래도 쓰기 요청이 가면 `api.js` 가 405 로 사실을 적는다 — 조용히 실패하지 않는다.

## 파일 이름 규칙 — 양쪽이 같아야 한다

`scripts/export_static.py` 의 `target_of()` 와 `frontend/src/api.js` 의
`snapshotPath()` 는 **같은 규칙**이어야 한다.

```
/api/health                        -> health/default.json
/api/model/factors?months=12       -> model/factors/months=12.json
/api/complexes/14?months=24        -> complexes/14/months=24.json
/api/quotes/ranking?basis=market
    &days=7&months=12              -> quotes/ranking/basis=market~days=7~months=12.json
```

쿼리는 **이름순으로 정렬**한다. 프론트엔드가 파라미터를 넣는 순서는 화면마다
다를 수 있어서, 정렬하지 않으면 같은 요청이 다른 파일을 가리킨다.

한쪽만 바꾸면 화면은 404 를 받고, 그건 **"데이터가 없다" 로 보인다** — 이 저장소가
가장 경계하는 조용한 실패다. 그래서 규칙을 양쪽 주석에 같이 적어 두었다.

내보낼 요청 목록은 `export_static.py` 의 `build_plan()` 하나에만 있다. 화면에
새 필터 조합이 생기면 여기에 넣어야 한다 — 넣지 않으면 그 조합만 404 가 된다.

## 왜 TestClient 인가

서비스 계층을 직접 부르면 라우터가 하는 일(기본값, 검증, 직렬화)을 내보내기 쪽에서
다시 구현해야 하고, 그러면 **정적 사이트와 동적 사이트가 조용히 다른 값을 내기**
시작한다. `TestClient` 는 실제 ASGI 앱을 그대로 호출하므로 같은 코드를 지난다.

응답은 `r.content` 를 **바이트 그대로** 쓴다. 파싱해서 다시 쓰면 그 순간부터
부동소수점 표기나 키 순서가 달라질 수 있다. 다시 만들지 않는 것이 가장 확실하다.

서버를 띄우지 않아도 되니 작업 스케줄러에서 돌리기도 쉽다 — 포트 충돌도, 종료
처리도 없다.

## 왜 고아 커밋으로 강제 푸시하나

스냅샷은 수십 MB 이고 내보낼 때마다 거의 전부 달라진다(적정가가 그 기간 실거래로
다시 계산되므로). 그걸 `gh-pages` 에 쌓으면 이력이 **하루 8MB 씩** 불어난다.
한 달이면 240MB 다.

그래서 매번 `dist` 안에 빈 저장소를 만들어 커밋 하나만 두고 force push 한다.
브랜치에는 항상 커밋이 하나뿐이라 이력이 늘지 않는다. 정적 사이트에 이력이 필요한
경우는 없다 — 필요한 이력은 소스 저장소에 있다.

`.nojekyll` 을 같이 둔다. 없으면 GitHub Pages 가 Jekyll 로 처리하면서 `_` 로
시작하는 파일·디렉터리를 조용히 뺀다. 지금 구조에는 없지만, 나중에 생겼을 때
"파일이 왜 404 지" 로 시간을 버리지 않도록 미리 둔다.

## base 경로

GitHub Pages 는 `https://<user>.github.io/<repo>/` 하위에 올라간다. `base` 를 안
맞추면 빌드 결과가 절대 경로 `/assets/...` 를 가리켜 전부 404 가 된다.

`frontend/.env.static` 의 `VITE_BASE` 로 정한다. 루트 도메인에 올릴 때는 `/` 로
바꾼다. 환경변수를 셸에서 넘기지 않고 파일로 두는 이유는, 윈도우에서 `set` /
`$env:` / npm 스크립트를 섞다 보면 어느 하나에서 조용히 빠지고 그러면 **정적
모드가 아닌 채로 빌드돼** 백엔드를 찾다가 전부 실패하기 때문이다.
`vite build --mode static` 은 이 파일을 확실히 읽는다.

## 올릴 수 있는 상태인지 먼저 본다

`sync_static.ps1` 은 **올리기 전에 셋을 확인하고, 아니면 배포만 건너뛴다.**

| 보는 것 | 왜 |
|---|---|
| 브랜치가 `main` 인가 | 브랜치 작업물이 공개되지 않도록 |
| 커밋되지 않은 변경이 없는가 | 올린 것을 나중에 재현할 수 있도록 |
| `origin/main` 에 다 올라갔는가 | 커밋 메시지에 적는 소스 해시가 떠돌지 않도록 |

**실제로 당해서 넣었다.** 2026-10-12 10:19 배포의 소스가 `6cf9898` 인데, 그것은
거시 분석 탭을 만들다 만 브랜치의 중간 커밋이다 — 하루 한 번 도는 스케줄러가
**그 순간 체크아웃된 작업 트리**를 그대로 올렸다. 이번엔 해가 없었지만(탭이 아직
목록에 없었다) 반쯤 고친 화면이 공개될 수 있는 구조였다.

막는 것은 **공개되는 행위뿐**이다. 내보내기·빌드는 그대로 돈다 — 로컬에서 확인하는
것은 언제나 되어야 한다. 그래서 `-NoPublish` 는 검사를 거치지 않는다.

```powershell
.\sync_static.ps1                  # 전제를 보고, 안 맞으면 배포만 생략
.\sync_static.ps1 -NoPublish       # 검사 없음(어차피 안 올린다)
.\sync_static.ps1 -AllowAnyBranch  # 알고도 올린다
```

**실패가 아니라 생략이라 종료 코드는 0 이다.** 스케줄러에 거짓 실패를 남기면 진짜
실패와 구분할 수 없게 된다(같은 이유로 `Run` 함수가 stderr 를 실패로 세지 않는다).
못 하게 막는 것이 아니라 **의도적인 행위로 만드는 것**이 목적이다.

## 주기 동기화

두 가지가 돈다. 둘 다 작업 스케줄러에 등록하고, 등록 명령은 각 스크립트 맨 아래
주석에 있다.

| 작업 | 언제 | 무엇을 잡나 |
|---|---|---|
| `sync_static.ps1 -Quiet` | 매일 06:30 | 푸시 없이 **데이터만** 바뀐 것(실거래 적재) |
| `deploy_on_push.ps1 -Quiet` | 10분마다 | **main 이 바뀐 것**(PR 머지, main 직접 푸시), 그리고 일일 작업이 빠진 날 |

### 푸시 연동 — hook 이 아니라 감시다

"푸시하면 배포" 를 git hook 으로 하면 **거의 아무것도 못 잡는다.** 이 저장소의
main 은 GitHub 에서 PR 머지로 바뀌고, 머지 버튼은 이 컴퓨터를 지나가지 않는다.
GitHub Actions 로 옮길 수도 없다 — 배포에 실거래 DB(저장소 밖)와 적합이 필요하다.
그래서 `deploy_on_push.ps1` 이 10분마다 `origin/main` 을 받아 보고, 마지막으로
배포한 소스와 다르면 작업 트리를 fast-forward 하고 `sync_static.ps1` 을 돌린다.

- **같으면 아무것도 안 한다.** 로그도 남기지 않는다
- **작업 트리가 main 이 아니거나 더러우면 미룬다.** 이 폴더는 여러 세션이 같이
  쓴다 — 남의 브랜치를 바꾸는 것은 배포가 늦는 것보다 나쁘다
- **'배포 완료 … (소스 <해시>)' 를 봤을 때만 올렸다고 적는다.** 실패하면 한 시간 쉰다
- **마지막 '배포 완료' 가 26시간보다 오래면 main 이 그대로여도 돈다.** 일일 작업이
  죽은 날을 메운다(아래)

미룸을 이유가 바뀔 때만 적는 것, 상태 파일을 `.git` 안에 두는 것, 첫 차례에 상태를
잡는 법은 스크립트 머리 주석에 있다.

### 스케줄러가 띄운 PowerShell 이 죽는다

일일 작업의 마지막 결과가 `3221225477`(0xC0000005)로 남는 날이 있다. 손으로 돌리면
멀쩡하다. 이벤트 로그·WER 보고서·`sync_static.log` 를 대조하니 **스크립트가 한 줄도
돌기 전에** 죽고 있었다.

| 본 곳 | 본 것 |
|---|---|
| `sync_static.log` | 그 실행의 줄이 없다 — 첫 줄 `=== 동기화 시작 ===` 도 못 썼다 |
| WER 적재 모듈 | `clr.dll`(한 건은 `ConsoleHost`)까지. 스크립트 엔진 전이라 node·vite·numpy 와 무관하다 |
| 죽은 자리 | 4건 모두 `ntdll.dll+0x12553a` — 대소문자 무시 문자열 비교가 잘못된 포인터를 읽는다 |
| 언제 | 3건(10-05·10-08·10-15)이 모던 스탠바이에서 깨는 순간(Kernel-Power 507)과 1초 안. `StartWhenAvailable` 이 밀린 06:30 차례를 깨자마자 띄웠다 |

늘 죽지는 않는다(10-10 은 깨고 20초 만에 멀쩡히 돌았다). 세션 0·다른 프로필도
아니다 — 작업은 `Interactive`, 같은 사용자다. Microsoft 것이 아닌 모듈은
`C:\Windows\Teruten\TCube\TModule64.dll`(보안 에이전트의 후킹 DLL) 하나라 가장
의심스럽지만 덤프가 없어 스택으로 확인하지 못했다. **고칠 자리가 저장소 밖이라
메운다** — 위의 26시간 규칙. 메운 날은 `deploy_on_push.log` 에 '마지막 배포가 N시간
전' 으로 남는다.

### 둘이 겹치지 않게

두 작업은 같은 `dist` 와 스냅샷 폴더를 쓴다. 겹치면 한쪽이 지우는 동안 다른 쪽이
빌드해 반쪽 dist 가 올라갈 수 있다. `sync_static.ps1` 이 이름 있는 뮤텍스를 잡고,
이미 잡혀 있으면 기다리지 않고 '겹침' 으로 끝낸다(종료 코드 0). 푸시 연동 쪽은
그것을 실패로 세지 않고 다음 차례에 다시 본다.

로그는 `sync_static.log`·`deploy_on_push.log` 에 쌓인다(`.gitignore` 의 `*.log`). 실패는
종료 코드로도 올라가므로 스케줄러의 마지막 결과에서 보인다 — **내보내기가 반쪽이면
화면에는 아무 표시 없이 옛 값이 남으므로**, 조용히 넘기지 않는 것이 중요하다.

## 공개 범위 — 호가는 실거래가와 성격이 다르다

실거래가는 국토교통부가 공개하는 데이터라 그대로 올려도 된다. **호가는 다르다.**
네이버 부동산에서 붙여넣은 값이고, 이 저장소는 애초에 네이버 자동 수집을 약관
문제로 배제했다. 공개 사이트에 호가를 그대로 싣는 것은 같은 문제를 다른 경로로
들이는 셈이다.

- 저장소가 **private** 이면 무료 플랜에서는 Pages 를 쓸 수 없다(GitHub Pro 필요).
- 저장소를 **public** 으로 바꾸면 사이트도 공개된다 — 호가까지 공개된다.
- 호가를 빼고 올리려면 `.\sync_static.ps1 -NoQuotes`. 매물 분석만 남는데, 그쪽은
  전부 공개 데이터에서 나온 계수다.

`meta.json` 의 `includes_quotes` 로 그 스냅샷에 호가가 들어 있는지 확인할 수 있다.
