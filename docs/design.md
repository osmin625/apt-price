# 설계 결정

화면과 기능을 왜 이렇게 만들었는지. 계산의 수식은 [모델](model.md),
데이터를 어디서 어떻게 가져오는지는 [데이터 파이프라인](data.md) 참조.

## 출발점

### 1. 평당가는 전용면적 기준

```
전용 평당가 = 거래금액(만원) ÷ (전용면적㎡ ÷ 3.305785)
```

공급면적이 아니라 **전용면적**을 분모로 쓴다. 같은 집이라도 공급면적 기준보다 25~35% 높은
숫자가 나오지만, 전용률(전용/공급)이 단지마다 70~80%로 제각각이라 공급면적 평당가는
단지 간 비교 기준이 되지 못한다. 국토교통부 실거래가 원본도 전용면적만 제공한다.

공급면적은 매물 입력 시 선택 항목으로만 받아 전용률 계산과 환산 표기에 쓴다.

### 2. 세 가지 비교 축

| 축 | 구간 | 기준 |
|---|---|---|
| **층** | 1층 / 저층 / 중층 / 고층 / 최상층 | 단지 최고층 대비 상대 위치 (~25% 저층, ~65% 중층) |
| **입지** | 초역세권(5분) / 역세권(10분) / 준역세권(15분) / 비역세권 | 최근접 지하철역까지 직선거리 400·800·1200m |
| **컨디션** | 신축(5년) / 준신축(10년) / 10~15 / 15~20 / 20~30 / 30년 초과 | 준공년도 기준 경과 연수 |

단지 최고층은 국토교통부 API가 주지 않으므로 **관측된 최고 거래층**을 추정치로 쓴다.
도보 시간은 직선거리에 보행 경로 보정(×1.25)을 한 뒤 분당 67m로 환산한다.
(분양 광고 관행인 "1분 = 80m"는 실제 보행 속도보다 빠르게 잡힌 값이라 쓰지 않았다.)

여기에 **노선 · 생활권(최근접역) · 단지 규모(세대수)** 필터가 더 붙는다.

| 필터 | 기준 | 비고 |
|---|---|---|
| 지하철 노선 | 큐레이션한 `Station.line` | 1호선 / 수인분당선 / 신분당선 |
| 생활권 | 최근접역 이름 | 노선을 고르면 그 노선 역만 남는다 |
| 단지 규모 | 세대수 300/600/1000/1500 구간 | K-apt 미매칭 단지는 '정보없음' |

노선·역은 카카오가 준 `Complex.station_line`('수도권1호선')이 아니라 **큐레이션한
Station 테이블**을 쓴다. 표기가 달라 필터 값과 화면 표시가 어긋나면 안 되기 때문이다.
필터 선택지도 고정 목록이 아니라 **실제로 단지가 붙어 있는 역**만 내보낸다 —
단지가 없는 역을 띄우면 고르는 순간 빈 화면이 된다.

> **생활권 필터의 한계**: 최근접역 기준이라, 역에서 먼 단지도 어딘가에는 배정된다.
> 예를 들어 우만동 월드메르디앙은 '광교중앙역 생활권'이지만 실제로는 도보 33분이다.
> 생활권으로 좁힐 때는 **입지 등급 필터를 함께** 거는 것이 안전하다.

위 구간은 **시장 분석 / 단지 상세 / 매물 분석** 탭이 쓰는 기술통계 축이다.
역거리를 자르지 않고 연속으로 보는 경로는 아래 6번의 헤도닉 모델이 따로 담당한다.

### 매물 분석 (적정가 진단 + A·B 분해)

한 화면에서 **두 가지 질문**에 답한다. 원래 탭이 갈려 있었는데, 실제로는 같은 매물에
대해 연달아 묻게 되는 질문이라 입력을 두 번 하게 됐다.

| | 묻는 것 | 단지 고유 프리미엄 |
|---|---|---|
| **적정가 진단** | 그 단지 같은 평형 시세 대비 이 호가가 적정한가 | 값에 이미 포함 |
| **요인별 비교** | A와 B 중 요인을 감안하면 어느 쪽이 싼가 | 빼고 펀더멘털만 |

둘은 다른 질문이라 답이 갈릴 수 있다. 재건축 기대가 붙은 단지는 "그 단지 시세로는
적정"인데 "펀더멘털 대비로는 비쌈"이 된다. 갈리는 것 자체가 정보다.

한쪽만 채우면 그쪽 진단만, 양쪽을 채우면 진단 두 장 + 비교까지 나온다.

요인별 비교는 평당가 차이를 **요인별 기여로 쪼갠다**. "A가 두 배 비싼데 왜 싸다는
거냐"에 대한 답이 표에 그대로 나온다.

```
A 자연앤힐스테이트 (이의동, 84.9㎡, 15층, 13.5억)
B 매탄주공5       (매탄동, 84.9㎡, 15층,  6.2억)

  역까지 도보   2.0분 vs 15.5분    +17.1%
  강남까지     35분  vs 58분       +8.1%
  연식        14년  vs 41년       +58.3%
  지하철 노선   신분당선 vs 수인분당선  +28.5%
  ──────────────────────────────────────
  모델 예상 차이                  +157.6%
  실제 호가 차이                  +117.7%
  → A가 15.5% 저렴
```

#### 입력 — 텍스트를 붙여넣으면 자동으로 채워진다

매물 화면의 텍스트를 그대로 붙여넣으면 단지·전용면적·층·호가를 뽑아 채운다.
붙여넣는 순간 돌아가고, 버튼을 한 번 더 누를 필요가 없다.

화면에 보이는 것은 **붙여넣기 칸과 채워진 값 요약**뿐이다. 검색창·필터·목록·입력칸은
'직접 입력' 토글 뒤에 접어 둔다 — 붙여넣기 한 번으로 끝나는 것이 기본 동선인데
입력칸이 전부 펼쳐져 있으면 그쪽이 기본처럼 보인다. 단, **파싱이 단지나 면적을
못 채웠으면 자동으로 펼친다.** 접힌 채로 두면 손댈 곳이 안 보여 막힌다.

```
힐스테이트푸르지오수원 103동
매매 9억
3,360만원/3.3㎡평당가 도움말
알림관심매물
공유하기
아파트88B㎡ (전용59B)8/15층남향
```

화면을 통째로 긁어 와 버튼 문구(`도움말`·`공유하기`)가 섞여도 쓸 줄만 골라 읽는다.
`아파트88B㎡ (전용59B)` 에서 **전용 59㎡** 를 집고(타입 문자 `B` 는 평면 변형이라
면적과 무관하다), `8/15층` 에서 8층·총 15층을, `매매 9억` 에서 90,000만원을 뽑는다.

**평당가 기준이 다른 것도 짚어 준다.** 위 매물에 적힌 평당가는 3,360만원/평인데
이 서비스는 5,043만원/평로 계산한다. 틀린 게 아니라 분모가 다르다 — 네이버는
공급 88㎡, 이 서비스는 **전용 59㎡** 기준이다(이 프로젝트의 출발점이 바로 그것이다).
적힌 평당가와 호가로 분모를 역산해 공급 기준이면 경고로 알려 준다. 50% 차이가
설명 없이 나오면 어느 한쪽이 틀린 줄 알기 때문이다.

다른 표기도 받는다.

```
자연앤힐스테이트 101동
매매 13억 5,000
아파트 · 112.9/84.97㎡, 중층, 남향
```

- **단위는 적힌 대로 읽고, 평은 1평 = 3.305785㎡ 로 환산한다.** 파싱 전에 한 번
  환산해(`normalize_pyeong`) 단위를 통일하므로, `34평/25.7평` 같은 공급/전용 쌍도
  ㎡ 쌍과 똑같이 뒤쪽을 전용으로 잡는다. `30평대`(범위)·`평당가`(단가)는 면적이
  아니므로 건드리지 않고, 숫자와 '평'은 **같은 줄**에서만 잇는다 — 줄을 넘게 두면
  `매매 3억 9,000` 다음 줄의 `평당가` 와 붙어 `000평` → 0평 이 된다.
- **괄호 안 전용은 앞의 공급에서 단위를 물려받는다.** 네이버는 `아파트17평 (전용12)`
  처럼 전용 쪽 단위를 생략하는데, 이때 12는 12㎡ 가 아니라 **12평(39.7㎡)** 이다.
  단위 없는 숫자를 일괄로 ㎡ 취급하면 맞는 평형이 사라져 면적 칸이 빈 채로 남는다.
  `88B㎡ (전용59B)` 는 공급이 ㎡ 라 이 규칙에 걸리지 않고 그대로 ㎡ 로 읽힌다.
- **'전용' 표기가 없는 면적은 공급으로 본다.** 광고의 `34평`·`112㎡`는 거의 항상
  공급면적이다. 그대로 전용에 넣으면 112㎡ 전용을 가진 단지가 아닌 한 "그런 평형 없음"
  으로 비워진다. 그래서 **어느 해석이 맞는지 데이터에 물어본다** — 숫자가 그 단지의
  전용 평형과 바로 맞으면 전용, 아니면 전용률 0.60~0.90 안에 드는 평형을 찾고, 여럿이면
  거래가 가장 많은 쪽을 고른다(`routers/model._resolve_area`). `34평` → 전용 84㎡
  (전용률 75%), `25평` → 전용 60㎡ (73%). 둘 다 아니면 비우고 직접 고르게 한다.
- `전용59B` `112.9/84.97㎡` `34평/25.7평` → 전용면적 ㎡. 한 쌍이면 뒤쪽이 전용이다.
  뽑은 값은 그 단지의 실제 평형으로 맞춘다(59 → 60㎡).
- `8/15층` → 8층. 뒤의 15는 **건물 실제 최고층**이라 층 구간 판정에 쓴다. DB 의
  `max_floor` 는 거래에서 관측된 최고층이라 거래가 적은 단지에서는 실제보다 낮다.
- `129동` → **역까지 도보를 그 동 좌표로 잡는다.** 동이 없으면 단지 중심점을 쓴다.
  수원센트럴아이파크자이는 129동이 19.9분, 104동이 12.4분으로 **단지 안에서만 8.4분**
  벌어진다. 중심점 하나(16.2분)로는 이 차이가 통째로 사라진다.

  동 편차에 단지 간 계수를 그대로 쓰면 안 된다. 단지 간 도보 계수(-1.083%/분)는
  입지 전반을 함께 싣고 있어 동 편차 계수(-0.355%/분, t=-9.7, n=20,211)의 3배다.
  그래서 **단지 중심점까지는 스플라인, 거기서 동까지의 편차는 within 계수**로 나눠
  더한다. 후자는 단지 고정효과와 직교하게 추정된 값이라 학군·브랜드·연식·구 입지가
  전부 통제돼 있다.

  직접 입력 패널의 동 선택은 `GET /api/complexes/{id}/dongs` 가 주는 실제 동 목록에
  동별 도보시간과 시세 프리미엄을 붙여 보여 준다 — 타이핑하면 오타도 나고 그 동이
  얼마나 먼지·비싼지도 모른다. 좌표를 못 잡은 동(전체의 19%)은 중심점으로 떨어진다.

### 동 프리미엄 — 재보니 평형 교란이었다

층 프리미엄은 처음부터 있었는데 동 프리미엄은 없어서, Stage 1 잔차를 단지 안에서
동별로 평균 내 봤다. τ=2.50%, 신호비 48% 라는 그럴듯한 값이 나왔고 수원센트럴아이파크자이
129동은 -8.66%(42건) 가 찍혔다. **전부 틀린 값이었다.**

**무엇이 틀렸나.** 그 단지에서 40㎡ 는 129동·130동에만 있고 나머지 28개 동은 60~103㎡ 뿐이다.
전역 면적 스플라인이 이 단지의 40㎡ 를 10%쯤 비싸게 예측하면 그 오차가 갈 곳은 129·130동의
'동 효과' 밖에 없다. 실거래를 직접 보면 두 동은 **같은 전용 39.77㎡ 유닛이고 평당가 중앙값이
3,076 으로 똑같다**. 동 위치 차이가 아니라 평형 차이를 보고 있었던 것이다.

여기에 수축까지 겹쳐 더 나빠졌다. 129동(42건, 수축 0.83)은 -8.66%, 130동(3건, 수축 0.26)은
-2.30% 가 됐는데, 두 동의 실제 가격은 같다. **6%p 격차가 순전히 표본 수 차이에서 나왔다.**
적정가 진단에서 129동 3,280원/평 vs 130동 3,531원/평 이라는 없는 차이를 만들어 냈다.

**고친 방법.** `(단지 × 평형)` 셀 안에서 잔차를 한 번 더 차감한 뒤 동별로 평균 낸다. 같은
평형을 나눠 갖는 동끼리만 비교되고, 같은 평형이 한 동에만 있으면 **식별 불가**로 빼 버린다
(403개 동). 129동은 -10.33% → **-0.13%**, 130동은 -8.58% → +1.82% 로 둘 다 0 근처가 된다.

**결과: τ = 0.00%.** 검출력을 보정해 보면(참 효과를 심고 되찾는 시뮬레이션)

| 심은 참 τ | 되찾은 값 |
|---|---|
| 1.0% | 0.00% (못 잡음) |
| 1.5% | 0.94% |
| 2.0% | 1.39% |
| 3.0% | 2.53% |

검출 한계는 **τ≈1.2%** 다. 즉 평형을 통제한 동 효과는 그보다 작고, 이 표본으로는
있다/없다를 말할 수 없다. 시장 분석 탭의 '동 위치' 카드는 0짜리 막대 다섯 개 대신
**"검출되지 않았습니다"** 와 그 한계를 적는다 — 0 을 그리면 '동은 가격과 무관' 으로
읽히는데 실제로는 '잴 수 없다' 이기 때문이다.

동 위치가 가격에 미치는 영향 중 이 표본에서 잡히는 경로는 **역까지 도보거리뿐**이다
(`dong_walk_dev`, -0.355%/분, t=-9.7, n=20,211). 그쪽은 위에서 설명한 대로 살아 있다.

> **교훈**: 단지 고정효과만으로는 부족했다. 동과 평형이 붙어 있는 단지에서는 다른 항의
> 오차가 통째로 동 효과로 흘러든다. 잔차 평균으로 무언가를 뽑을 때는 **그 무언가와
> 공선인 것이 무엇인지** 먼저 따져야 한다.

### 요인별 적정가 — 매물 하나를 분해한다

기존 '요인별 기여' 표는 **A−B 상대 차이**만 냈다. 그래서 두 가지가 안 됐다.

- 같은 단지 두 매물(129동 vs 130동)을 넣으면 단지 요인이 전부 0% 라 표가 텅 빈다.
- 한쪽만 넣으면 아예 나오지 않는다.
- 금액이 없다. % 기여만 있고 "그래서 얼마인가" 가 빠져 있다.

`model_view.model_price()` 가 매물 **하나**를 절대값으로 분해한다. α̂_c 는
`전용 84㎡ · 중층 · 최신월` 기준이므로, 거기에 이 매물의 면적·층·동 도보편차를 더해
해당 유닛으로 옮긴다. 출발점을 무엇으로 두느냐에 따라 두 값이 나온다.

| | 출발점 | 답하는 질문 |
|---|---|---|
| **실거래 기준** | 같은 단지·평형 실거래 | 이 단지 이 평형이 실제로 얼마에 팔리나 |
| **요인 기준** | Stage 2 예측 α̂ | 거리·연식·세대수·노선·구만으로 얼마여야 하나 |
| **시장 기준** | 관측 α̂_c | (내부 검산용 — 아래 참조) |

둘의 차이가 그 단지에 붙어 있는 **고유 프리미엄**이다. 학군·브랜드·재건축 기대처럼
측정하지 않은 것이 거기 들어 있다.

#### 면적 곡선 교정 — 안 하면 34% 틀린다

모델은 `α_c + f(면적) + 층` 인데 `f` 는 **전 단지 공통 곡선**이다. 어떤 단지의 40㎡가
84㎡ 대비 얼마나 싼지는 단지마다 다른데 공통 곡선은 그 차이를 못 담는다. 실제로
수원센트럴아이파크자이 40㎡ 에서 모델의 **시장 기준 46,111만원**이 같은 평형
**실거래 기준 40,532만원**보다 14% 높게 나왔다. 교정 없이 내보내면 요인 기준이
5.36억 — 실거래 4.05억짜리 집에 대해 +32% 짜리 숫자가 나간다.

두 값은 같은 질문("이 단지 이 유닛이 지금 얼마에 팔리나")의 답이므로, **어긋난 만큼이
곧 면적 곡선의 이 단지·이 평형 오차**다. 비율로 뽑아 요인 기준에도 먹인다.

    보정계수 = 실거래 기준 평당가 / 모델 시장 기준 평당가

단지 간 펀더멘털(Stage 2)은 건드리지 않고 **단지 안에서의 유닛 환산만** 고친다.
130동 20층: 원값 5.36억 → 교정 **4.74억**(보정 -12.1%). 실거래 비교가 없으면 교정할
수 없으므로 원값을 쓰고 그 사실을 남긴다. 2배 넘게 벌어지면 교정이 아니라 다른 데가
고장 난 것이라 손대지 않는다.

#### 화면

```
실거래 기준 4.05억      요인 기준 4.74억      단지 고유 프리미엄 -14.5%
같은 단지·평형 56건      펀더멘털만            요인으로 설명 안 되는 부분
호가 -12.4%             호가 -25.1%

단지 — 어디에 있는 아파트인가
  역까지 도보    16.2분        -8.9%
  강남까지 전철  60분          -0.7%
  연식          2년          +46.9%
  세대수        3,432세대      +8.3%
  지하철 노선    수인분당선     -11.7%

```

두 판정이 갈릴 수 있고, **갈리는 것 자체가 정보다**. 이 매물은 실거래 대비 -12%인데
펀더멘털 대비로는 -25%다. 차이는 이 단지가 요인 대비 14.5% 낮게 거래된다는 뜻이다.

A·B 비교의 요인별 기여 표는 그대로 둔다 — 그쪽은 **상대 차이**를 묻는 다른 화면이다.

### 호가 누적 — 실거래가 못 잡는 것

실거래는 **팔린 것만** 남긴다. 값을 못 받는 매도자는 싸게 파는 대신 물건을 거둬들이므로,
거래가 뜸한 구간의 관측 거래가는 **위로 편향**된다(constant-liquidity index 문헌의 고전적
문제다). 내려간 물건은 거래가 아니라 호가에만 있다.

수원센트럴아이파크자이가 그 사례다. 129동과 130동은 **구조가 같은데도** 같은 기간 거래가
42건 대 3건이고, 그 3건은 시점보정하면 129동보다 오히려 **비싸게** 찍힌다(3,405 vs 3,306).
실거래만 보면 "130동에 디스카운트 없음" 이라는 결론이 나오지만, 팔리지 않는 물건이
호가로 얼마에 나와 있는지를 데이터가 통째로 놓치고 있는 것이다.

그래서 **붙여넣기마다 호가를 쌓는다**(`services/quotes.py`). 따로 '저장' 을 누르게 하면
아무도 안 누르므로, 매물 텍스트를 붙여넣는 것만으로 기록된다.

**중복 처리**가 이 기능의 핵심이다.

- 같은 `(단지·동·평형·층·호가)` 가 다시 들어오면 새로 쌓지 않고 `last_seen_at` 과
  `seen_count` 만 올린다. 같은 매물을 몇 번을 붙여넣어도 표본이 부풀지 않는다.
- **가격이 바뀌면 새 행**이 된다. 그 변화가 바로 보고 싶은 신호다 —
  130동 3.55억 → 3.38억 → 3.20억 같은 경로가 그대로 남는다.
- 층·동을 모르면 NULL 이 아니라 `0`/`""` 를 쓴다. SQLite 의 UNIQUE 제약은 NULL 끼리를
  서로 다른 값으로 보기 때문에, NULL 을 두면 중복이 그대로 쌓인다.

집계는 최근 90일 안에 확인된 호가만 본다. 매물은 팔리거나 내려가는데 우리는 내려간 걸
알 방법이 없어서, 시간으로 끊는 수밖에 없다.

### 한 줄 = 한 (단지·동·평형·층대)

순위표가 한 층대 매물로 도배되면 아무것도 안 보인다. 실제로 130동 40㎡ 고층대에만
매물이 여덟 건 올라와 있었다. 그렇다고 합쳐 버리면 실재하는 매물이 사라진다.
그래서 **접는다** — 대표 한 줄만 표에 두고, 몇 건인지 배지로 밝히고, 전부는 호버로
펼친다. 숨기는 게 아니라 한 단계 뒤로 미루는 것이다.

대표는 **가장 최근 확인된 것**, 같은 날이면 **가장 싼 것**이다. 사는 쪽이 실제로 보는
값이고, 무엇보다 결정적이라 새로고침해도 순서가 흔들리지 않는다.

#### 확인일자를 버리지 않는다

각 매물에는 `집주인확인매물 2026.09.23` 같은 **확인일자**가 붙어 있다. 처음에는 이 줄을
중개사명·홍보문구와 함께 노이즈로 버렸는데, 그러면 안 됐다. 우리가 언제 봤는지
(`first_seen_at`)는 한 번에 붙여넣은 매물이 전부 같아서, 목록 안에서 시점을 가르는 데
쓸 수 없다. 매물이 언제 시점의 것인지 말해 주는 단서는 이 날짜뿐이다.

읽어 보니 한 번에 붙여넣은 46건의 확인일자가 `2026-08-28 ~ 2026-09-23` 에 걸쳐 있었다.
이제 순위표에 **확인** 열로 뜨고, '확인일자' 필터가 실제로 동작한다(최근 7일 47줄 /
전체 58줄). 날짜를 못 읽은 매물은 거르지 않고 남긴다 — 읽기 실패를 '오래된 매물' 로
바꿔 조용히 숨기면 안 된다.

#### 같은 집이 값을 바꾼 경우는 따로 가른다

가격이 바뀌면 새 행이 되므로, 한 집이 3.8억 → 3.55억 으로 내리면 두 행이 된다. 이건
접는 게 아니라 **잇는 것**이고, `▼ 6.6%` 배지로 변동을 표시해야 한다.

문제는 '같은 집' 을 알아보는 일이다. 목록에 **호는 나오지 않는다**. 층을 `고층` 으로만
밝힌 매물은 그 구간의 대표층(총 23층이면 19층)으로 채워지므로, `(단지·동·평형·층)` 이
같다고 해서 같은 집이라는 보장이 없다. 확인일자도 답이 못 된다 — 네이버는 **지금 올라와
있는 매물만** 보여 주므로 그 날짜는 '마지막으로 확인된 날' 이지 '언제까지 있었나' 가
아니다. 실제로 130동 고층대 다섯 건 중 네 건이 `09-21` 같은 날이었다.

그래서 **생존 구간**으로 가른다. 한 집의 호가가 바뀌면 옛 호가는 목록에서 사라지므로
`last_seen_at` 이 그 시점에 멈춘다. 반대로 함께 올라와 있는 매물들은 같은 목록에 있으므로
`last_seen_at` 이 나란히 갱신된다. 구간 `[first_seen, last_seen]` 이 **겹치지 않고 이어질
때만** 같은 집의 연속된 호가로 본다. 구간 분할(interval partitioning)과 같은 문제로,
겹치는 구간의 최대 개수가 곧 유닛 수다.

```
잇는다 (같은 집)                  접는다 (동시 매물)
3.8억  09-26 ~ 09-28              3.8억  09-26 ~ 09-30
3.55억 10-01 ~ 10-03              3.55억 09-26 ~ 09-30
→ 3.55억 ▼6.6% (이력 2건)         → 3.55억 [2건] 호버로 펼침
```

이어붙일 후보가 여럿일 때 사슬 **개수**는 어느 쪽을 골라도 같지만(구간 분할의 성질)
어느 호가가 어느 호가의 다음인지는 달라진다. 사라진 직후에 나타난 쪽이 이어졌을
가능성이 높으므로 가장 늦게 비워진 사슬에 붙이고, 후보가 둘 이상이었으면 배지에 `?` 를
붙여 **경로가 추정임을 밝힌다**. 추측을 사실처럼 보여 주지 않기 위해서다.

같은 이유로 현재 호가 집계(`summary`)도 유닛마다 최신 행만 쓴다. 값을 내린 집의 옛
호가는 이미 없는 가격인데, 그것을 중앙값에 함께 넣으면 분포가 위로 끌린다 — 하필 이
데이터를 쌓는 이유(내려간 값 포착)와 정반대 방향이다.

> 생존 구간의 시간 여유는 600초다. 두 방향의 오류는 값이 다르다 — 여유가 **짧아서**
> 동시 매물을 가격 변동으로 오인하면 없는 이력을 만든다. 여유가 **길어서** 실제 변동을
> 못 잡으면 그냥 접힌 두 건으로 보일 뿐이다. 그래서 길게 잡았다.

> **한계**: 접는 단위가 `(단지·동·평형·층)` 이라 같은 층의 서로 다른 호는 한 줄에 접힌다.
> 목록에 호가 나오지 않는 한 이 이상은 알 수 없다. 접힌 건수와 각각의 호가·확인일자를
> 호버로 전부 보여 주는 것이 이 한계에 대한 답이다.

### 분해 모델 탭 — 계수를 읽을 수 있게

'거리 모델' 이라는 이름은 도보거리만 보는 것처럼 들렸다. 실제로는 면적·층·시점·
강남접근성·연식·세대수·노선·구를 함께 분해하므로 **분해 모델**로 바꿨다.

#### 탭이 답할 질문은 하나다

'무엇이 가격을 얼마나 움직이나' 다. 그래서 그 질문에 답하지 않는 것을 덜어냈다.

| 덜어낸 것 | 어디로 |
|---|---|
| 모델 잔차 지도 | 지도 탭. 잔차는 **어디에 뭉쳐 있나**가 핵심이라 지도가 맞다 |
| 도보 산점도 · 같은 단지 안 거리 효과 | 시장 분석의 **도보거리 카드를 펼치면** 나온다 |
| 층 프리미엄 | 삭제. 시장 분석의 층 카드와 같은 값이었다 |

도보거리 둘을 옮긴 이유는 성격이 어긋나서다. 분해 모델은 요인 여덟 개를 **나란히**
보는 탭인데, 거기서 도보거리만 산점도와 전용 분석을 달고 있으면 그 요인만 특별 대우를
받는다. 시장 분석은 요인마다 카드가 하나씩 있으니, 더 보고 싶은 요인의 카드를 펼치는
것이 자연스럽다.

열 때 받아 온다(`components/WalkDetail.jsx`). 시장 분석은 `/model/factors` 만으로
그려지는데 산점도는 적합 전체와 지도용 단지 목록(1.2MB)이 더 필요하고, 대부분의
방문에서는 쓰이지 않는다.

**카드 안에서 펼치지 않고 창으로 띄운다.** 처음에는 카드 아래로 펼쳤는데, 그 카드는
격자의 한 칸이라 폭이 300px 남짓이다. 산점도와 타일 여섯 개를 그 안에 우겨넣으니 읽을
수가 없었고, 한 칸만 길어져 격자 전체가 어그러졌다. **내용이 칸보다 크면 칸을 늘릴 게
아니라 칸 밖으로 꺼내야 한다**(`components/Modal.jsx`).

창은 세 가지를 지킨다.

- 나가는 길을 셋 다 둔다 — `Esc`, 배경 클릭, 닫기 버튼.
- 열 때 창으로 포커스를 옮기고 닫을 때 **누르던 자리로 돌려준다.** 안 그러면 키보드
  사용자가 문서 맨 위로 튕긴다.
- 열려 있는 동안 뒤 배경이 스크롤되지 않는다. 휴대폰에서 특히 거슬린다.

좁은 화면에서는 전체 화면으로 편다. 375px 에서 창을 띄우면 남는 여백이 아깝다.

층 프리미엄은 옮기지 않고 지웠다. 그 카드의 설명이 스스로 "기존 시장분석 탭과 같은
구간" 이라고 적고 있었고, 다른 것은 신뢰구간뿐이었다. 그 신뢰구간은 시장 분석의 층
막대 툴팁에 넣었다 — **옮길 것은 화면이 아니라 빠져 있던 숫자 하나였다.**

> 그러다 버그를 하나 찾았다. `PremiumBars` 툴팁이 `r.factor.toFixed(3)` 를 부르는데,
> 요인별 보정계수에서 온 행(층·노선)에는 `factor` 가 없다. 시장 분석에서 층 막대에
> 호버하면 그 자리에서 터지고 있었다. 있을 때만 쓰도록 고쳤다.

#### 계수표가 44줄이었다

연속 요인은 제한 3차 스플라인으로 적합하므로 요인 하나가 열 여러 개로 흩어진다.
강남 접근성만 해도 `gangnam_min` + `__nl1`~`__nl5` 로 여섯 줄이다. 그런데 그 낱개
계수는 **단독으로 읽을 수 없다** — 기저가 서로 물려 있어 하나만 떼면 뜻이 없다.

그걸 그대로 쏟아 놓으니 정작 읽을 수 있는 값이 묻혔다. **요인 하나에 한 줄**로 묶고
기저는 접었다(44줄 → 27줄). 한 줄에 담는 것은 셋이다.

| 요인 | 읽는 법 | 계수 | p | 형태 |
|---|---|---|---|---|
| 역까지 도보(분) | 1분당 −1.28% | −0.0127 | <0.001 | 선형과 구분 안 됨 · 기저 2개 |
| 강남까지 전철(분) | 1분당 −2.51% | −0.0254 | <0.001 | 비선형 · 기저 5개 |
| 연식(년) | 1년당 −1.64% | −0.0327 | <0.001 | 비선형 · 기저 5개 |
| log(세대수) | 세대수 2배당 +11.28% | 0.1084 | 0.182 | 비선형 · 기저 5개 |

**읽는 법** 열이 핵심이다. 계수는 로그 척도라 그대로는 뜻이 안 들어온다 — 직선인
요인은 `exp(coef)−1` 로 환산하고, 세대수처럼 로그 단위인 것은 '2배당' 으로 읽는다.
범주형(노선·구)도 같은 식으로 '기준 대비 +20.4%' 로 적는다.

구 고정효과 라벨도 고쳤다. `구 FE 41113` 은 읽을 수 없어서 `수원시 권선구` 로 바꿨다.

#### 계수가 어디에 쓰이는지 화면에 적는다

세 탭이 하나의 적합을 공유하지만 그 계수가 모든 숫자에 쓰이지는 않는다는 것을
[위](#세-탭은-같은-모델을-본다)에 적어 뒀는데, **문서에만 있으면 화면을 보는 사람은
끝내 모른다.** 그래서 탭 맨 위에 같은 표를 둔다(`components/CoefUsage.jsx`).

특히 '매물 분석 — 실거래 기준' 만 ○ 로 표시한다. 그 값은 비교표본 중앙값이라 이
계수와 무관하고(동 효과만 빌린다), 그걸 모르면 "같은 모델인데 왜 두 값이 다르지"
에서 멈춘다.

### 단지 비교 탭을 없앴다

단지 목록을 훑어보는 화면이었는데, 대상을 경기 남부로 넓히며 단지가 2,469곳이 되자
**목록을 훑는다는 행위 자체가 성립하지 않게 됐다.** 실제로 쓰는 경로는 하나였다 —
줄을 눌러 그 단지의 상세를 보는 것.

그래서 들어가는 문을 **매물 순위**로 옮겼다. 순위표·카드의 단지명을 누르면 같은 상세가
열린다. 관심 있는 단지는 이미 거기 있으므로, 2,469곳에서 찾아 들어가는 것보다 짧다.
지도와 분해 모델의 점을 눌러도 같은 곳으로 간다.

탭과 함께 `views/ComplexesView.jsx` 와 `App` 의 `FilterBar` 도 지웠다. 필터는 그
화면만 쓰던 것이라, 남은 화면이 쓰는 값은 분석 기간 하나뿐이다.

### 좁은 화면에서는 표 대신 카드

매물 순위표는 열이 열한 개다. 375px 에 넣으면 각 열이 30px 남짓으로 눌려
**단지명이 글자마다 세로로 쪼개졌다** — 수/원/센/트/럴/아/이/파/크/자/이.

표에 `min-width` 를 줘서 가로 스크롤로 만들 수도 있다. 하지만 한 줄을 읽으려고 매번
옆으로 밀어야 하고, 밀면 머리글이 사라져 그 숫자가 무슨 열인지 알 수 없게 된다.

그래서 **정보 구조를 다시 짰다**(`components/RankCards.jsx`). 열을 그대로 눕힌 게
아니라 휴대폰에서 실제로 보는 순서대로 놓는다.

```
1  수원센트럴아이파크자이              저평가
130동 · 40㎡ · 10층 (중층)
3.25억  [2건]                      -20.1%
실거래 4.07억 -20.1%   요인 4.52억 -28.1% ⓘ
확인 09.16                          [삭제]
```

답(호가와 괴리율)을 가장 크게 두고, 근거인 두 기준의 적정가를 그 아래 작게 둔다.
지금 정렬 기준인 쪽은 굵게 — 표의 `is-sort` 와 같은 뜻이다.

중단점은 720px 하나이고 **CSS 와 자바스크립트가 같은 값을 쓴다**(`useNarrow` 의
`matchMedia`). 따로 적으면 언젠가 어긋난다.

#### 손가락에는 호버가 없다

카드로 바꾸고 보니 ⓘ 가 **눌러도 아무 일이 없었다.** `Hint` 가 열리는 경로는
`mouseenter` 와 `focus` 뿐인데, 터치 브라우저는 앞의 것을 흉내만 내고(기기마다 다르다)
뒤의 것은 폼 요소가 아니면 잘 주지 않는다.

그래서 **탭으로 여닫게** 했다. 바깥을 누르면 닫히는 것도 함께 넣었다 — 터치에는
`mouseleave` 가 오지 않으므로 그게 없으면 한 번 연 팝업이 계속 떠 있는다. 데스크톱의
호버는 그대로 두었고, 클릭으로 고정할 수도 있게 됐다.

### 기다릴 때는 경과 시간을 보여 준다

진행 막대를 퍼센트로 채우고 싶지만, **얼마나 걸릴지 시작할 때 알 수 없다.** 적합은
캐시가 있으면 0.02초, 없으면 수 초에서 수십 초다. 그런데도 퍼센트를 그리면 그 숫자는
거짓말이 된다 — 70%에서 멈춰 있는 막대는 아무 정보도 주지 않으면서 곧 끝날 것처럼
보인다.

그래서 **확실히 아는 것만** 보여 준다(`components/Loading.jsx`).

- **경과 시간**을 0.1초 단위로 센다. 사용자가 실제로 알고 싶은 것이고, 우리가 확실히
  아는 유일한 숫자다.
- 막대는 진행률이 아니라 '살아 있다' 는 표시라 끝이 없다. `prefers-reduced-motion`
  에서는 움직이지 않는다.
- **0.4초 안에 끝나면 아예 나타나지 않는다.** 캐시가 있는 대부분의 경우가 여기 해당해서,
  로딩이 있었다는 것조차 모른다. 깜빡이는 표시는 없느니만 못하다.
- **6초를 넘기면** 그제야 이유를 덧붙인다("캐시가 비어 있으면 처음 한 번 오래 걸립니다").
  처음부터 적어 두면 0.02초에 끝나는 대부분의 경우에 괜히 겁을 준다.

#### 문구는 실제로 하는 일을 적는다

처음에는 어느 경우든 "모델을 적합하는 중" 이라고 적었는데, 그건 **대부분의 경우
사실이 아니다.** 적합은 한 번만 계산하고 데이터와 코드가 그대로면 다시 쓴다. 실제로
일어나는 일은 셋 중 하나다.

| 상태 | 실제로 하는 일 | 걸리는 시간 | 문구 |
|---|---|---|---|
| 캐시 없음 | 11만 건으로 회귀를 계산 | 수십 초 | "분해 모델을 계산하는 중" |
| 디스크에 있음 | 저장해 둔 결과를 읽어 온다 | 2초 안팎 | "저장해 둔 분해 모델을 불러오는 중" |
| 메모리에 있음 | 그대로 쓴다 | — | 표시 자체가 안 뜬다 |

걸리는 시간이 한 자릿수 다르고 사용자가 할 일도 다르다 — 앞은 기다려야 하고 뒤는 곧
끝난다. "적합하는 중" 이라고만 적으면 2초짜리도 수십 초처럼 보이고, 반대로 수십 초짜리에
아무 설명이 없으면 멈춘 줄 안다. 이유를 덧붙이는 시점도 다르게 뒀다(계산 4초, 읽기 8초).

**짐작하지 않고 물어본다.** 경과 시간으로 추측할 수도 있지만(2초를 넘겼으면 계산 중이겠지)
그건 이미 기다린 뒤에야 아는 것이고, 처음 몇 초는 틀린 문구를 보여 주게 된다.
`/api/model/status` 가 12ms 에 답하므로 그냥 묻는다(`components/FitLoading.jsx`).

매물 순위도 같은 이유로 고쳤다. "쌓인 매물을 평가하는 중" 은 무엇을 하는지 말해 주지
않는다 — 실제로는 매물마다 같은 단지·같은 평형의 실거래를 모아 시점과 층을 보정한 뒤
중앙값을 낸다. 그대로 적는다.

### 지도는 잔차만 칠한다

지도에 칠할 수 있는 값은 셋이었다 — 보정 평당가, 중앙 평당가, 모델 잔차. 앞의 둘을
없앴다. **평당가를 칠하면 비싼 동네가 비싸게 나올 뿐**이고, 그건 단지 상세의 평형별
표가 더 잘 답한다.

지도에서만 보이는 것은 **요인으로 설명되지 않는 값이 어디에 뭉쳐 있나**이다. 도보거리·
강남접근성·면적·층·연식·구를 모두 통제하고 남은 잔차가 특정 지역에 몰려 있으면, 그
지역에 모델이 모르는 무언가(학군·브랜드·조망·재건축 기대)가 있다는 뜻이다. 그 '뭉침'
은 표로는 안 보이고 지도로만 보인다.

분해 모델 산점도도 지도에서 뺐다. 같은 그래프가 분해 모델 탭에 그대로 있고, 지도 위에
떠 있으면 지도를 가린다.

**등가격 링도 없앴다.** 적합 곡선이 −5%·−10% 를 지나는 도보시간을 관측 보행속도와
우회율로 반경으로 바꿔 그리던 기능인데, 선택한 단지의 최근접역을 중심으로만 그려져서
'지금 이 지도에서 무엇을 알 수 있나' 에 답하지 못했다. 같은 정보는 상세 패널의
'역까지 도보 27.2분' 이 더 정확하게 말해 준다. 백엔드의 `/api/map/rings` 와
`model_view.rings`·`detour_stats` 도 함께 지웠다 — 쓰지 않는 코드는 남겨 두면
다음 사람이 유지해야 할 것으로 오해한다.

### 세 탭은 같은 모델을 본다

시장 분석·매물 분석·분해 모델은 **하나의 적합 객체**를 공유한다
(`peek_fit(24) is get_fit(24)` → True). 하지만 **그 계수가 모든 숫자에 쓰이는 것은
아니다.** 매물 분석에는 회귀를 쓰는 숫자와 안 쓰는 숫자가 나란히 있다.

| 탭 / 숫자 | 회귀 계수를 쓰나 | 무엇으로 내나 |
|---|---|---|
| 분해 모델 | ✅ | Stage 1·2 계수를 그대로 보여 준다 |
| 시장 분석 — 요인별 보정계수 | ✅ | **같은 계수**를 '기준 대비 %' 로 환산 |
| 매물 분석 — **요인 기준** 적정가 | ✅ | 회귀가 예측한 단지 수준(`predicted_alpha`)에서 출발 |
| 매물 분석 — **실거래 기준** 적정가 | ❌ | 비교표본 중앙값(비모수). 동 효과만 회귀에서 빌린다 |

흔들어 보면 갈린다. 회귀가 예측한 단지 수준을 +10% 하면 요인 기준만 움직이고,
회귀가 낸 동 효과를 +10% 하면 실거래 기준만 움직인다.

```
기준                   요인 69,298 · 시장 51,329 · 실거래 52,495
predicted_alpha +10%   요인 76,228 (바뀜) · 시장 51,329 · 실거래 52,495
dong_effects    +10%   요인 69,298 · 시장 51,329 · 실거래 52,996 (바뀜)
```

**층 계수마저 두 경로가 따로 낸다.** 분해 모델은 Stage 1 의 층 더미를, 적정가 진단은
비교표본에서 직접 잰 값을 쓴다. 같은 데이터인데도 값이 다르다.

| 층 | 분해 모델(회귀) | 적정가 진단(표본) |
|---|---|---|
| 1층 | −8.28% | −9.33% |
| 저층 | −2.86% | −2.32% |
| 중층 | 0.00% (기준) | +0.51% |
| 고층 | +0.72% | +1.17% |
| 최상층 | +0.36% | −0.31% |

**의도한 설계다.** 두 방법은 서로 다른 질문에 답하고, 서로의 검산이 된다
([모델 — 역할 분담](model.md) 참조). 회귀는 "펀더멘털 대비 얼마여야 하나", 비교표본은
"그 단지 같은 평형이 실제로 얼마에 팔리나" 를 답한다. 둘이 크게 갈리면 그 차이 자체가
정보다 — 재건축 기대가 낀 단지에서 특히 벌어진다.

#### 다른 것은 모델이 아니라 **기간**이다

적합은 `months` 마다 따로 만들어진다. 분해 모델과 시장 분석은 `get_fit(months)` 로
화면의 기간에 맞는 적합을 계산하지만, 매물 분석과 순위는 `peek_fit()` 으로 **이미
계산된 것만** 쓴다 — 가벼운 조회가 십수 초짜리 적합을 기다리게 할 수는 없어서다.

그런데 예전 `peek_fit()` 은 인자 없이 **캐시의 가장 최근 것**을 돌려줬다. 동 프리미엄
같은 보조 정보에만 쓸 때는 문제가 없었는데, 지금은 여기서 나온 적합이 요인 기준 적정가
전체를 만든다. 그래서 같은 매물을 같은 조건으로 봐도 답이 달라졌다.

```
순위(months=12) · 캐시 최신 24개월 → 요인 적정 7.03억
순위(months=12) · 캐시 최신 12개월 → 요인 적정 7.17억   ← 2% 차이
```

시장 분석 탭에서 기간을 바꾸고 순위표로 돌아오면 숫자가 변하는 셈이었다. 이제
`peek_fit(months=...)` 이 요청한 기간의 적합을 먼저 찾고, 그래도 없으면 종전처럼 가장
최근 것을 쓰되 **어느 기간 것을 썼는지 응답에 싣는다**(`factor_months`). 화면 제목에
'요인 기준은 24개월 적합' 이라고 뜨므로, 값이 왜 그런지 숨지 않는다.

### 시장 분석 = 보정계수만

예전에는 구간별 평당가 분포(층·입지·연식·면적대)와 월별 추이를 같이 깔았는데, 한 화면에
**성질이 다른 두 숫자**가 있으니 계속 헷갈렸다. 구간별 평당가는 다른 요인이 섞인 관측값이고
보정계수는 나머지를 고정한 순효과다. 역에서 먼 단지에 마침 신축이 많으면 '입지별 평당가'는
거리 효과를 거꾸로 보여 준다. 이 탭이 답할 질문은 "무엇이 가격을 얼마나 움직이나" 하나이고
그 답은 보정계수 쪽이므로, 평당가 분포는 걷어내고 보정계수만 남겼다(실제 분포는 단지 상세에
있다).

필터도 **분석 기간만** 남겼다. 자치구·면적대 같은 필터는 모델 적합 대상을 바꾸지 않아서
(계수는 전체 표본에서 추정된다) 눌러도 아무 일이 없었다.

## 매물 비고는 호가가 아니라 유닛에 붙는다

순위표의 한 줄은 호가 하나가 아니라 **접힌 단위**(단지·동·평형·층)다
(`quotes.unit_key()`). 같은 집이 값을 바꿔 다시 올라오면 새 `Quote` 행이 생기고
대표도 그 새 행으로 바뀐다.

그래서 메모를 `quote_id` 에 붙이면 **값이 바뀌는 순간 사라진다.** 적어 둔 사람은
아무 경고도 못 받는다 — 이 저장소가 가장 경계하는 조용한 실패다. `QuoteNote` 는
`unit_key` 와 같은 키를 쓰므로 호가가 바뀌어도, 같은 층대에 새 매물이 올라와도
그 줄의 메모는 남는다.

두 키가 어긋나면 메모가 엉뚱한 줄에 붙으므로 `display_units` 가 `note_key` 를
직접 실어 보낸다. 화면이 키를 다시 조립하지 않는다.

### 입력 중인 글자는 덮지 않되, 줄이 바뀌면 맞춘다

기간·기준을 바꾸면 목록이 새로 온다. 그때 서버 값으로 무조건 덮으면 입력 중이던
글자가 사라진다. 그래서 사용자가 고친 것이 있으면 덮지 않는다.

다만 **줄이 바뀌었으면 무조건 맞춘다.** React 가 같은 자리의 컴포넌트를 다른 행에
재사용할 수 있는데, 그때까지 지키면 남의 줄에 남의 메모가 떠 있게 된다. 못 지키는
것보다 엉뚱한 줄에 붙는 쪽이 훨씬 나쁘다.

저장은 포커스를 뗄 때(또는 Enter) 한 번만 보낸다. 글자마다 보내면 순위표가 수십
줄이라 요청이 쏟아지고, 디바운스로 줄이면 "저장됐나" 를 알 수 없는 구간이 생긴다.
실패해도 입력한 글자는 지우지 않는다.

## '추가' 는 '확인' 과 다르다

순위표에 날짜가 둘이다. **확인**은 매물에 적힌 확인일자(중개사가 확인한 날)이고,
**추가**는 우리가 그 줄을 처음 넣은 날이다. 섞이면 "오래된 매물" 판단이 반대로
간다.

추가 날짜는 그 줄에 접힌 **모든** 호가 중 가장 이른 것이다. 대표 사슬 기준으로
하면 나중에 올라온 매물이 대표가 될 때 날짜가 앞당겨진 것처럼 보인다.

## 민간임대 표시는 동에 붙이고, 비고에는 파생해서 띄운다

민간임대 동은 분양 물건과 성격이 달라 같은 단지·같은 평형이어도 시세가 다르다.
그런데 국토부 실거래가에는 그 구분이 없다. 매물 순위에서 '왜 이 동만 유독 싼가'
를 매번 다시 알아내는 대신, 단지 상세의 **동 정보**에서 한 번 표시해 둔다.

### 비고에 글자를 써 넣지 않는다

표시한 동의 매물에는 비고에 `민간임대` 가 따라붙는다. 다만 `QuoteNote` 에 글자를
**써 넣지 않고** 응답에서 파생한다(`note_auto`). 써 넣으면 두 가지가 깨진다.

- 표시를 끈 뒤에도 글자가 남는다. 지우려면 줄마다 손으로 지워야 한다.
- 사용자가 직접 쓴 메모와 구분되지 않는다. 자동으로 넣은 것을 자동으로 지우려면
  무엇이 자동이었는지 알아야 하는데, 글자만 남으면 알 수 없다.

파생하면 표시를 끄는 순간 배지가 같이 사라지고, 같은 줄에 사용자가 쓴 메모는
그대로 남는다. 실측으로 확인했다 — `로열층` 을 쓴 줄에서 표시를 끄자 배지만
빠지고 `로열층` 은 남았다.

### dong_tags 를 따로 둔다

`complex_dongs` 는 국토부 동 정보와 카카오 좌표로 **다시 채워지는** 테이블이다.
사람이 손으로 표시한 값을 거기 섞으면 적재 한 번에 조용히 날아간다. 들어온
데이터와 사람이 적은 것은 섞지 않는다.

### 동은 버튼 하나씩만

처음에는 동마다 역까지 도보시간·거리·동 효과를 표로 깔았다. 30개 동이면 표가 화면을
반쯤 먹는데, 여기서 실제로 하는 일은 '민간임대인 동을 골라 두는 것' 하나다. 읽을 일이
없는 숫자로 자리를 채우지 않는다. 거리는 지우지 않고 버튼의 `title` 로 내렸다.

### 낙관적 갱신은 함수형으로

버튼은 먼저 움직이고 서버를 부른다. 응답을 기다리면 한 박자 늦어 눌렸는지 알 수 없다.

다만 **다음 상태를 렌더 시점의 값으로 만들면 안 된다.** 연달아 누르면 뒤의 것이 앞의
것을 덮는다. 실측으로 잡았다 — 107·119·130 을 연속으로 누르자 서버에는 셋 다
들어갔는데 화면에는 130 만 켜졌다. 사람 손으로는 사이에 렌더가 끼어 잘 안 드러나지만,
드러날 때는 '눌렀는데 안 켜진다' 로 보인다.

되돌릴 때도 통째로 복원하면 그 사이 켜 둔 다른 동까지 되돌아간다. 실패한 동 하나만
되돌린다.

## A·B 한 건씩 넣던 기능을 뺐다

매물 분석 탭 앞에 매물 두 건을 각각 붙여넣어 적정가를 보고, 둘의 평당가 차이를
요인별로 쪼개는 블록이 있었다. 입력칸이 두 벌(단지 검색·면적·층·호가·붙여넣기)이라
탭에서 자리를 가장 많이 먹었는데, 실제로는 **여러 매물 붙여넣기**로 한 번에 넣고
매물 순위에서 보는 쪽이 쓰기 편했다. 두 건만 견주는 일은 순위표에서 두 줄을 보면
끝난다.

요인별 비교가 답하던 질문("이 차이가 어디서 오나")은 분해 모델 탭의 계수로 같은
답이 나온다. 같은 것을 두 군데서 다르게 보여 주지 않는다.

지운 것: `ComplexPicker`, `PasteBox`, `CompareResult`, `Spec`, `FairVerdict.jsx`.
CompareView 가 957줄에서 205줄로, 번들이 263KB 에서 236KB 로 줄었다.

## 매크로 인사이트 — 4분면이냐 막대냐

매크로 탭은 처음에 17개 시계열을 그려 놓기만 했다. 값은 다 있는데 읽는 일이 통째로
사람 몫이라 "인사이트 없이 값만 보여준다" 는 말을 들었다. 그래서 인사이트 카드를
더했는데, 그릴 때 **두 가지 중 하나를 고른다.**

**4분면 산점도는 두 축을 겹쳐야 보이는 것에 쓴다.** 한 축으로는 구분이 안 되는 것이
있을 때만이다.

| 그림 | 가로 | 세로 | 한 축으로 안 되는 이유 |
|---|---|---|---|
| 지금 어느 국면인가 | 전고점 대비 | 최근 3개월 | 전고점 대비만 보면 '바닥에서 기는 곳' 과 '고점에서 꺾인 곳' 이 섞인다 |
| 그 상승을 전세가 받쳐 줬나 | 12개월 매매 | 전세가율 변화 | 얼마나 올랐나로는 실수요가 따라왔는지 모른다 |
| 거래가 받쳐 준 상승인가 | 12개월 매매 | 거래량 5년 평균 대비 | 가격만으로는 손바뀜된 상승인지 호가만 오른 것인지 모른다 |
| 모델과 어긋나는 곳 | 부동산원 순위 | 모델 계수 순위 | 둘이 **같아야 정상**이고, 벌어진 곳이 볼 곳이다 |

**막대 목록은 값이 하나뿐인 지표에 쓴다.** 표본 두께와 가격 편차가 그렇다. 그럴 때
묻는 것은 "어디가 제일 심한가" 와 "어디까지가 정상 범위인가" 인데, 정렬된 막대에서
바로 읽히고 점으로 흩어 놓으면 오히려 안 읽힌다. 플러스·마이너스가 섞이면
(평균/중위 괴리) 0 을 가운데 두고 좌우로 뻗는다.

`.pbar-*`(요인 패널)를 재사용하지 않고 `.mbar-*` 를 따로 뒀다. 그쪽은 요인 패널의
격자 폭에 맞춰져 있어 한쪽을 고치면 다른 쪽이 조용히 틀어진다. 규칙이 작아서 따로
두는 쪽이 싸다.

### 축소판에서는 이름표를 지운다

카드는 300px 폭이다. 거기에 17개 이름표를 적으면 글자가 겹쳐 아무것도 못 읽는다.
축소판은 **구름의 모양**(산점도)과 **분포의 모양**(막대)만 보여 주고, 자세한 것은
눌러서 띄우는 창에 둔다. 4분면 축소판에서 이름표를 뺀 것과 같은 이유다.

막대 이름표 열은 128px 다. 104px 로 뒀더니 '화성시 만세구'(가장 긴 이름)에 '얇다'
배지가 붙으면서 막대 위로 겹쳐 흘렀다.

### 표본 두께는 그것을 읽는 자리에 같이 띄운다

'지수가 몇 건으로 만들어졌나' 는 독립 카드지만, 그 사실이 실제로 필요한 자리는
**국면 4분면**이다. 과천의 '전고점 대비 -5%' 가 월 33건에서 나왔다는 것은 그 점에
마우스를 올렸을 때 알아야 쓸모가 있다. 그래서 `cycle_phase` 의 각 점에 `vol_pm` 을
붙여 호버에 같이 적는다.

## 시장 분석 + 매크로 = 분석 탭 (미시·거시)

둘은 같은 질문의 두 축이었다. '무엇이 가격을 얼마나 움직이나'(요인별 보정계수)와
'시군구가 서로 어떻게 다르게 움직이나'(공표 통계)는 따로 보면 반쪽이고, **모델과
어긋나는 곳** 차트는 아예 두 탭의 값을 겹쳐야 뜻이 생기는데 그걸 보려면 탭을
오가며 머릿속에서 이어 붙여야 했다.

탭을 나눈 이유는 화면이 좁아서였는데, 재 보니 **가로가 남아 돌았다.** `.app` 이
1240px 이고 격자가 `minmax(300px, 1fr)` 이라 세 칸이 한계였다. 1560px 으로 넓히니
네 칸이 되고(실측), 두 섹션이 한 탭에 들어간다.

### 숨기지 않고 나눈다

섹션을 탭처럼 만들어 한쪽만 보여 줄 수도 있었다. 그러면 **탭이 두 개였던 것과
같아진다** — 이름만 바뀐다. 둘 다 그려 두고 건너뛸 길만 준다. 위쪽 `.section-nav`
는 고르는 것이 아니라 이동이고, 지금 보고 있는 섹션을 `aria-current` 로 표시한다.

'지금 어디' 는 **화면 위쪽 1/3 선을 지난 마지막 섹션**으로 정한다.
IntersectionObserver 의 기본 동작(보이면 켬)으로는 둘 다 걸쳐 있을 때 못 고른다.

### 글줄만 묶는다

폭을 늘린 만큼 문장이 1500px 로 뻗으면 눈이 줄을 잃는다. 숫자·격자는 폭을 다 쓰고
`.card > p`·`.card > .sub` 만 90ch 로 묶는다.

## 중개사 메모에서 키워드를 뽑는다

매물마다 붙는 한 줄 메모("세끼고 피3000 확정가500할인됨 2in0ne 냉장고")를 같이
읽어 **같은 뜻을 한 이름으로** 묶는다. `세끼고`·`세안고`·`전세 안고`·`전세 끼고`
가 전부 다르게 적히므로 원문으로는 걸러 볼 수가 없었다.

### 비고 칸에 **글자를 써 넣지 않는다**

민간임대 표시 때 정한 규칙이 그대로 적용된다. 키워드를 비고 텍스트에 써 넣으면
사용자가 직접 쓴 메모와 섞이고, 사전을 고쳐도 옛 줄은 옛 글자를 달고 있다.
배지로 띄우고 원문은 그 자리에 두는 쪽이 맞다.

### 민간임대 배지와 **다른 모양**이다

민간임대는 사용자가 단지 상세에서 직접 표시한 사실이고(채운 노랑), 메모 키워드는
**올린 사람이 그렇게 적었다**는 뜻이다(테두리만). '올수리' 는 우리가 확인한 것이
아니다. 같은 모양으로 두면 둘이 같은 무게로 읽힌다 — '추정을 사실처럼 보여 주지
않는다' 가 배지 모양에까지 적용되는 자리다.

호버에 **원문과 건수**를 같이 띄운다. 한 줄은 같은 층대 매물 여럿을 접은 것이라
태그도 합집합이고, 그래서 한 줄에 `즉시입주` 와 `입주협의` 가 같이 붙을 수 있다 —
서로 다른 매물의 말이다. 몇 건을 합친 것인지 모르면 그게 모순으로 보인다.

### 셋만 보이고 나머지는 접는다

재 봤다. **줄당** 태그는 중위 4개·최대 10개다(메모 하나당은 중위 2개인데, 한 줄이
매물 여럿을 접으므로 합집합이 커진다). 절반쯤 되는 줄이 `+N` 을 단다.

그래도 셋인 이유는 서버가 **가격에 걸리는 순서**로 돌려주기 때문이다. 10개가 붙은
줄의 앞 셋은 `세안고`·`분양권P`·`조정가능` 이었고 접힌 일곱은 설비·전망 얘기였다.
늘려 봐야 중요한 것이 더 보이지 않고 비고 입력칸만 밀려난다.

### 배지는 접힌다(wrap)

배지는 `flex: none` + `nowrap` 이라, 안 접으면 칸의 **최소 너비**가 배지 수만큼
늘어나 다른 열을 민다. 넣고 나니 1000px 안팎에서 단지명이 한 글자씩 세로로
쪼개졌다. `flex-wrap: wrap` + 입력칸 `min-width: 72px` 로 고쳤고, 재 보니 단지 열
너비가 배지 유무로 3px 밖에 안 달라진다(48px ↔ 51px).

## 매물 분석 → 매물 관리, 그리고 메모 사전

붙여넣어 읽기만 하던 탭에 **설정**이 들어오면서 하는 일이 분석보다 관리에 가까워졌다.
탭 이름을 바꾸고 메모 사전을 그 안에 뒀다.

### 사전은 화면에서 못 고친다 — 표시 설정만 고친다

규칙(정규식)은 `services/memo_tags.py` 의 `RULES` 에 있고 **코드다.** 화면에서 고칠
수 있게 하면 '실제 메모에 재 보고 적중 수를 주석에 남긴다' 는 고리가 끊긴다 —
아무 데서나 고칠 수 있으면 아무도 재지 않는다.

반면 **무엇을 띄울지**는 취향이고 때마다 다르다. 실측에서 제일 많이 걸린 것이
`시스템에어컨`(22/50)인데 가격 판단에는 거의 쓸모가 없다. 그런 것을 끄는 자리가
`memo_tag_prefs` 다.

### 없는 행은 켜진 것으로 본다

규칙을 새로 더했을 때 행이 없다고 꺼져 있으면, 더해 놓고 왜 안 보이는지 한참 찾게
된다. 기본은 **켬**이고 끈 것만 행으로 남는다.

### 끄는 것은 '안 보여 주기' 지 '안 읽기' 가 아니다

꺼도 `Quote.memo` 원문은 그대로 저장되고 호버에서 보인다. 비고 배지에서만 빠진다.
다시 켜면 그 자리에서 되살아난다 — 그래서 끄는 데 망설일 이유가 없다.

### 동 버튼과 같은 모양을 쓴다

하는 일이 같다. 목록을 한눈에 보고 눌러서 켜고 끈다. 새 모양을 만들면 같은 동작을
두 가지로 배우게 된다. 다만 켜진 **색**은 다르다 — 민간임대는 노랑(사용자가 표시한
사실), 메모 키워드는 파랑(중개사의 말)이고, 이것은 비고 배지에서 쓰는 구분과 같다.

끈 칩은 숨기지 않고 흐리게 둔다. 뭘 꺼 뒀는지 보여야 다시 켤 수 있다.

### 횟수를 같이 보여 준다

0회인 태그는 **지울 규칙이거나 패턴이 실제 표기와 어긋난 것**이다. 숫자가 없으면 그
구분이 안 되고, 안 걸리는 규칙이 영원히 남는다. 그래서 0회는 빨간 숫자로 띄운다.

횟수는 저장하지 않고 **볼 때마다 다시 센다.** 저장해 두면 사전을 고쳤을 때 옛 숫자가
남고, 그 숫자를 보고 사전을 또 고치게 된다.

같은 글이 여러 매물에 붙어 있으면 **한 번만 센다**. 같은 중개사가 같은 문구를 여러
매물에 돌려 쓰면 그 말 하나가 사전 통계를 통째로 왜곡한다.

### 사전에 없는 말도 같이 보여 준다

접어 둔 자리에 '아직 아무 규칙에도 안 걸리는 낱말(2번 이상)' 과 '어느 키워드에도 안
걸린 메모' 를 띄운다. 규칙을 늘릴 거리가 거기 있다. 다만 **늘리는 것은 코드에서**
하고, 늘린 뒤 `python -m scripts.memo_report` 로 다시 재서 적중 수를 주석에 남긴다.
화면은 '무엇을 늘릴지' 까지만 알려 준다.

## 선택한 기준의 열만 보여 준다

예전에는 실거래·요인 적정가를 둘 다 깔고 선택한 쪽만 굵게 했다. '기준을 바꿨는데
적정가가 그대로면 고장난 것처럼 보인다' 가 이유였는데, **열이 통째로 바뀌면 그
문제는 더 분명하게 풀린다** — 바뀐 것이 색이 아니라 표 모양이라 못 알아볼 수가 없다.
대신 열이 둘 줄어 단지명·비고가 숨 쉴 자리가 생긴다.

### 안 보이는 쪽 값은 버리지 않는다

표는 호버(`title`), 카드는 한 줄로 다른 기준의 적정가와 대비를 같이 적는다. 두
기준이 어긋나는 것 **자체가 정보**이기 때문이다 — 광교 84㎡ 가 실거래 기준 1위인데
요인 기준 4위로 내려간 적이 있다.

### 판정도 기준을 따라간다

`verdict` 는 늘 실거래 기준이었다. 열을 숨기니 요인 기준 화면에 **대비 -12% 인데
판정이 '적정'** 인 줄이 생길 수 있게 됐다 — 다른 기준의 답이 남은 것이다. 서버가
`verdict_factor` 를 따로 주고 화면이 기준에 맞춰 고른다. 요인 적정가가 없는 줄은
빈 칸이다 — 실거래 판정을 대신 보여 주면 보고 있는 숫자와 다른 것을 말하게 된다.

### 값이 한 줄도 없으면 그렇게 말한다

적합이 캐시에 없으면 요인 적정가가 안 나온다. 예전에는 실거래 열이 옆에 있어 표가
비어 보이지 않았는데, 이제는 `—` 만 가득한 표가 될 수 있다. 그건 고장처럼 보이고
왜 그런지도 안 적혀 있다. 그래서 '분석 탭을 한 번 열면 계산된다' 고 적는다.

### 규칙은 한 군데에 둔다

`components/rankBasis.js`. 표와 좁은 화면 카드가 각자 고르면 **같은 매물이 창 폭에
따라 다른 판정을 달게 된다** — 화면을 줄였더니 '적정' 이 '저평가' 로 바뀌는 식이다.
(한쪽에 두고 다른 쪽에서 가져오면 순환 import 가 된다. RankTable 이 RankCards 를 쓴다.)

## 붙여넣기 결과는 '새로 들어온 것' 만 보여 준다

북마클릿은 누를 때마다 **지금까지 담은 전부**를 클립보드에 넣는다. 여러 단지를 돌고
마지막에 한 번만 붙여넣게 하려고 일부러 그렇게 만든 것인데, 그 대가로 두 번째
붙여넣기부터는 결과에 이미 본 매물이 섞인다. "이전에 붙여넣은 매물도 다 같이 보인다"
는 말이 나온 자리다.

`quotes.record()` 가 이미 `created` / `seen` 을 가린다. 그 값을 버리지 않고 줄에
`is_new` 로 붙이면 화면에서 새 것만 추릴 수 있다. 기본은 **새 것만**이다 — 붙여넣은
직후에 궁금한 것은 '이번에 뭐가 늘었나' 이고, 전체 목록은 매물 순위 탭에 늘 있다.

**숨긴 건수는 적는다**(`이미 읽은 N건 숨김`). 안 적으면 몇 건이 어디로 갔는지 몰라
읽다 만 줄 알게 된다.

`is_new` 가 없는 줄(저장이 실패했거나 옛 백엔드)은 **숨기지 않는다.** 모르는 것을
'이미 읽은 것' 으로 치면 읽은 매물이 조용히 사라진다.

### 북마클릿도 비울 때를 알려 준다

비우는 길이 '매물이 안 보일 때 눌러서 확인' 하나뿐이라, 쓰는 사람은 자기가 뭘 얼마나
이고 다니는지 몰랐다. 20건을 넘기면서 **새로 담은 것이 없을 때만** 비울지 묻는다 —
담는 중에 끼어들면 돌아다니는 흐름을 끊고, 묻기 좋은 때는 '더 담을 게 없는' 순간이다.

## 못 찾은 단지를 후보에서 고른다

같은 이름이 여럿이면 자동으로 고르지 않는다. 잘못 붙이면 남의 거래가 섞여 시세가
통째로 망가지기 때문이다. 그런데 **고를 길도 없으면 그 매물은 그냥 사라진다** —
실제 붙여넣기 82건 중 '현대' 20건·'동산' 9건이 그렇게 버려졌다.

### 먼저 동 번호로 좁힌다

`_resolve_by_dong` 은 원래 시공사 합동 단지('신성,신안,쌍용,진흥')에만 썼다. 조각이
하나뿐이면 그만뒀는데, '쌍용' 같은 흔한 이름을 DB 전체에서 찾으면 엉뚱한 단지가
걸리기 때문이었다.

그런데 **이미 추려 둔 후보 안에서만** 찾으면 그 위험이 없다. '현대 104동' 의 후보는
이름이 정확히 '현대' 인 곳들뿐이고, 그중 104동 거래가 있는 곳이 하나면 그게 답이다.

재 봤다. 같은 붙여넣기 82건에서 읽히는 줄이 **8 → 48**로 늘었다.

```
동으로 유일하게 결정  41건   성원 -> 수원 권선 세류동 성원
                            신나무실5단지주공 -> 신나무실휴먼시아5단지(영통동)
동으로도 여럿        24건   (현대 — 101~103동이 여러 현대에 다 있다)
그 동의 거래 없음      9건   (동산)
```

추정이라는 것은 경고로 밝힌다 — 그 동의 거래가 우연히 한 단지에만 있었을 수도 있다.

### 남은 것은 **이름 단위**로 고른다

줄이 아니라 이름이다. 못 고른 이유가 '이 이름이 여러 곳' 이므로 한 번 고르면 그
이름의 매물이 전부 풀린다. 줄마다 고르게 하면 '현대' 하나에 스무 번을 눌러야 한다.

고른 것은 `name_map`(붙여넣은 단지명 → 단지 id)으로 서버에 보내고, 서버는 그것을
**이름 매칭보다 우선**으로 쓴다. 사람이 가린 것을 파서가 다시 뒤집으면 안 된다.

세 번 눌러 82건 중 81건이 읽혔다(1건은 중복으로 합쳐졌다). **8 → 81건.**

### 고를 수 있을 만큼 보여 준다

시군구만으로는 못 고른다 — '현대' 는 수원 장안구에만 세 곳이다(천천동·파장동·정자동).
법정동·지번·준공·세대수와 **등록된 동 번호**를 같이 띄운다. 동 번호가 결정적이다:
붙여넣은 매물이 101~104동이면 그 동이 있는 곳이 답이다.

거래 건수도 보여 주고, 많은 쪽을 위에 둔다. 0건인 단지를 고르면 적정가를 못 내는데,
고른 뒤 "비교 실거래 없음" 만 뜨면 왜인지 알 수 없다.

칩이 아니라 카드인 이유가 이것이다. 한 줄에 안 들어간다.

### 고르면 '전부' 로 바뀐다

`is_new` 는 '이번 붙여넣기에서 처음' 이 아니라 '이번 **요청**에서 처음' 이다. 후보를
고를 때마다 같은 목록을 다시 보내므로, 앞 선택으로 풀린 매물은 다음 요청에서 이미
저장된 것(seen)이 되어 숨는다. 실측으로 봤다 — 현대·동산·성원을 차례로 고르자 7건이
다 풀렸는데 표에는 **마지막 1건만** 남았다. 고른 직후에 보고 싶은 것은 '방금 뭐가
풀렸나' 이므로 전부를 보여 준다.

## 매물 순위 — 메모 키워드로 빼기

상단 칩을 누르면 그 키워드가 붙은 매물이 순위에서 **빠진다.**

### 고르는 게 아니라 빼는 것이다

'세안고 매물만 보기' 보다 '세안고는 빼고 보기' 가 실제로 하는 일이다. 매물을 고를 때
쓰는 문장이 "전세 낀 건 못 들어가니까 빼고" 쪽이기 때문이다. 포함 필터로 만들면
**키워드가 아예 없는 매물**(메모가 없는 것)이 통째로 사라지는데, 그게 거의 절반이다.

그래서 켜진 모양이 아니라 **지워진 모양**(취소선)을 쓴다. 칩이 밝아지면 '이것만 보기'
로 읽히는데 하는 일은 정반대다.

### 서버에 묻지 않는다

`note_tags` 는 이미 응답에 들어 있어서 왕복할 이유가 없고, 무엇보다 매물 순위는
**정적 사이트에도 실리는데** 거기는 서버가 없다. 거르는 일은 가볍다 — 수백 줄짜리
배열 필터다. 사전 순서도 서버에 묻지 않고 건수 많은 것부터 늘어놓는다.

### 번호를 다시 매기고, 원래 순위는 호버에 남긴다

그대로 두면 1·4·7 처럼 구멍이 난다. 구멍이 '걸렀다' 는 것을 말해 주긴 하지만,
필터를 건 뒤에 보고 싶은 것은 '내가 살 만한 것들 중 몇 번째냐' 다. 그래서 다시
매기되 `rank_all` 을 호버에 남긴다 — **다시 매긴 번호를 전체 순위로 읽으면 안 된다.**
순서 자체는 바뀌지 않는다.

### 숫자는 두 군데서 말하지 않는다

칩의 숫자는 **거르기 전 전체** 기준이다. 보이는 목록 기준으로 세면 누를 때마다 다른
칩이 같이 흔들리고 이미 뺀 칩은 0이 된다.

대신 칩 숫자를 더해도 숨김 건수와 안 맞는다 — 한 매물에 키워드가 여럿 붙기 때문이다
(실측: 세안고 12 + 올수리 21 + 전망 15 = 48 인데 실제로 숨은 것은 39건). 그래서 칩은
'이 키워드가 붙은 매물 수' 라고만 말하고, **실제로 몇 건이 숨었는지는 한 곳에서만**
적는다(`39건 숨김 · 전부 되돌리기`). 두 군데서 다른 숫자를 말하면 어느 쪽이 맞는지
알 수 없다.

### 민간임대도 같은 줄에서 뺀다

빼고 싶은 것이 중개사 메모 키워드만은 아니다. **민간임대**는 사용자가 단지 상세에서
직접 표시한 것(`note_auto`)이고, 분양 물건과 성격이 달라 아예 빼고 보고 싶은 경우가
많다. 쓰임이 같은데 두 군데서 따로 빼게 하면 하나를 빠뜨린다.

다만 **근거가 다르다.** 민간임대는 사용자가 확인해 표시한 사실이고, 메모 키워드는
올린 사람이 그렇게 적었다는 뜻이다. 비고 배지에서 쓰는 구분(채운 노랑 ↔ 테두리)을
칩에도 그대로 쓴다 — 두 화면이 같은 말을 해야 한다. 사실 쪽을 맨 앞에 둔다.

### Ctrl+클릭으로 한 단지만 본다

단지명을 그냥 누르면 **단지 상세**로 가고, Ctrl(맥은 ⌘)을 누른 채 누르면 **그 단지만**
남는다.

한 버튼에 둘을 둔 이유: 순위표를 보다가 "이 단지 것만 모아 보자" 가 되는 순간은 거의
항상 그 단지 이름을 보고 있을 때다. 필터를 따로 두면 이름을 기억해 다른 곳에 다시
입력해야 한다. 브라우저의 Ctrl+클릭('다르게 열기')과 같은 결이라 설명 없이도 손이
간다. 그래도 모르는 사람이 있으니 버튼 호버에 적는다.

규칙은 `components/rankSelect.js` 한 군데에 둔다. 표와 카드가 각자 쓰면 창 폭에 따라
동작이 달라진다 — `rankBasis.js` 와 같은 이유다.

### 좁히기와 빼기는 단계로 나눈다

`scoped`(단지까지 좁힌 것) → `shown`(거기서 키워드까지 뺀 것).

나눠 두는 이유는 **숫자** 때문이다. 'N건 숨김' 은 키워드로 숨긴 수여야 하는데 전체에서
빼면 단지로 좁힌 것까지 더해진다. 실제로 한 단지(25건)로 좁힌 뒤 민간임대를 빼니
**"247건 숨김"** 이 떴다. 맞는 값은 12다.

키워드 칩의 건수도 `scoped` 로 센다. 좁혀 놓고 보는 중이면 그 단지 안에서 몇 건인지가
궁금한 것이지 전체에서 몇 건인지가 아니다.

### 메모 사전과 이어져 있다

칩에 뜨는 키워드는 `note_tags` 이고, 그것은 **메모 사전에서 켜 둔 것만**이다. 사전에서
끈 키워드는 비고에도 안 뜨고 여기 칩에도 안 나온다. 한 군데서 끄면 양쪽이 같이 꺼지는
쪽이, 두 군데를 따로 관리하는 것보다 낫다.

## 순위표 — 좁히기와 정렬

### Ctrl+클릭으로 좁힌다 (단지 · 동 · 면적)

| 누르는 곳 | 좁혀지는 범위 |
|---|---|
| 단지명 | 그 단지 |
| 동 | 그 단지의 그 동 |
| 전용 | 그 단지의 그 면적 |

순위표를 보다가 "이것만 모아 보자" 가 되는 순간은 거의 항상 **그 값을 보고 있을
때**다. 필터를 따로 두면 단지명·동·면적을 기억해 다른 곳에 다시 입력해야 한다.
수식키 없는 클릭은 원래 하던 일(단지명은 상세로 가기)을 그대로 한다.

**좁히기는 덮어쓴다.** 쌓이게 하면 "지금 뭐가 걸려 있지" 를 화면에서 읽을 수 없고,
되돌리려면 누른 순서를 기억해야 한다. 한 번 누르면 한 가지로 좁혀지는 쪽이 예측된다.

면적은 **반올림 ㎡**(`area_key`)로 묶는다. 같은 평형인데 84.78 과 84.99 로 적히는 일이
흔하고, 그것들을 따로 보면 '같은 평형만 모아 보기' 가 안 된다.

Ctrl+클릭으로만 동작하는 값에는 **평소 밑줄을 긋지 않는다.** 늘 밑줄이 있으면 그냥
눌러도 되는 줄 안다. 호버에서만 알린다.

### 머리말을 눌러 정렬한다

오름차순 → 내림차순 → **기본(순위)**. 세 번째 누름을 둔 이유: 안 두면 한 번 정렬한
뒤 원래 순서로 돌아갈 길이 없어 새로고침을 하게 된다. `#` 머리말을 누르면 바로
기본으로 간다.

기본은 서버가 괴리율로 매긴 순서다 — 지금까지와 같다.

**화살표는 지금 정렬 중인 열에만** 띄운다. 모든 머리말에 흐린 화살표를 깔면 표가
온통 화살표가 되고 정작 어디로 정렬됐는지가 안 보인다. 점선 밑줄로 '누를 수 있다'
만 알린다.

값이 없는 줄은 **방향과 상관없이 뒤로** 보낸다. 오름차순 맨 위에 '—' 가 줄줄이 오면
정렬이 깨진 것처럼 보인다.

`#` 열의 번호는 **정렬해도 그대로**다. 그것은 순위이지 줄 번호가 아니다.

정렬은 `RankTable` 안에 둔다 — 매물 순위와 붙여넣기 결과가 같은 표를 쓰므로 양쪽이
공짜로 같은 동작을 얻는다. 거르기(어떤 줄을 볼까)는 바깥에, 정렬(어떤 순서로 볼까)은
표에 있다. 카드(좁은 화면)에도 같은 순서를 먹인다 — 표에서 정렬해 두고 창을 줄였을 때
순서가 뒤바뀌면 같은 화면이 아닌 것처럼 보인다.

## 향 — 버리지 않고 열로 보여 준다

매물에 `아파트107㎡ (전용84.78)11/12층동향` 처럼 적혀 있는데 지금까지 버리고 있었다.
같은 단지·같은 평형이라도 남향과 북향은 값이 다르다.

**'층' 바로 뒤만** 본다. 메모에도 '정남향' 같은 말이 흔한데 그것은 중개사의 말이지
매물 정보가 아니다. 둘을 섞으면 어느 쪽이 근거인지 알 수 없다.

실제 붙여넣기 150건을 세어 보니 다섯 가지뿐이었다(남향 63·남서향 42·남동향 35·
동향 8·서향 2). 북향 계열은 광고에 거의 안 적히지만 규칙에는 넣어 뒀다 — 안 나온다고
빼 두면 나왔을 때 조용히 버린다.

### 모델에는 넣지 않는다

국토부 실거래에 향이 없어 **계수를 추정할 길이 없다.** 추정할 수 없는 것을 요인으로
넣으면 다른 계수가 그 자리를 대신 먹는다. 보여 주기만 한다.

### 한 줄에 향이 여럿이면 그렇게 적는다

순위표의 한 줄은 같은 층대 매물 여럿을 접은 것이라 서로 다른 향일 수 있다(같은
층대의 다른 라인). 그때는 대표 것만 쓰지 않고 `동향·남동향` 처럼 **여럿임을 밝힌다** —
하나를 찍으면 나머지 매물의 향이 조용히 사라진다. 실측 81건에서 3줄이 그랬다.

### 향으로도 좁힌다 — 네 무리로 묶어서

쓰는 사람이 찾는 것은 '남서향 매물' 보다 **'서쪽으로 난 집'** 이다. 다섯 가지를 따로
두면 같은 성격인데 칸이 갈린다. 그래서 **동·서·남·북** 네 무리로 묶는다.

#### 두 글자면 **나쁜 쪽**을 남긴다

향에는 좋고 나쁨의 순서가 있다.

```
남 > 동 > 서 > 북        (왼쪽이 좋다)
```

그런데 매물을 올리는 쪽은 조금이라도 걸치면 **좋은 쪽을 함께 적는 경향**이 있다.
'남서향' 은 대개 서향에 남쪽이 조금 걸친 집이고, '북동향' 은 북향에 동쪽이 조금
걸친 집이다. 그래서 좋은 쪽을 떼고 **나쁜 쪽**을 그 집의 무리로 본다.

```
남서 -> 서      남동 -> 동
북서 -> 북      북동 -> 북
```

처음에는 '뒤 글자' 를 쓰려 했다. 남서·남동은 맞지만 **북서가 서향, 북동이 동향**이
된다 — 북향 집을 서향·동향으로 올려 주는 셈이라 반대로 틀린다. 순서를 명시해 고쳤다.

북 계열은 광고에 거의 안 적힌다. **바로 그래서** 규칙에 둬야 한다 — 안 나온다고 빼면
나왔을 때 조용히 좋은 쪽으로 올라간다.

정렬도 이 순서를 쓴다. 가나다순이면 남·동·북·서가 되어 북향이 서향보다 앞에 온다.

### 향은 **더해지고**, 동과 면적은 서로를 지운다

쓰는 사람이 원하는 끝 모양은 **단지 and (동 or 면적) and 향** 이다.

| 누르는 곳 | 하는 일 |
|---|---|
| 단지명 | 전부 푼다 — 제일 넓은 범위로 돌아가는 것이 그 버튼의 뜻이다 |
| 동 | 동을 걸고 **면적을 지운다**. 향은 둔다 |
| 전용 | 면적을 걸고 **동을 지운다**. 향은 둔다 |
| 향 | 향을 **더한다**. 동·면적은 둔다 |

동과 면적을 둘 다 걸면 '130동의 84㎡' 가 되는데 그건 대개 한 줄이라 좁히는 뜻이 없다.
반면 '130동 중에 남향만' 은 실제로 찾는 모양이다.

다른 단지의 값을 누르면 그 단지로 **갈아탄다** — 이전 단지의 동·면적을 들고 가면
아무것도 안 남는다.

실측:

```
동 클릭          성원 · 102동              3건
+ 남서향 클릭     성원 · 102동 · 서향       2건   ← 향이 더해지고 남서 -> 서
전용 클릭        성원 · 전용 135㎡ · 서향   2건   ← 동은 빠지고 향은 남음
단지명 클릭      성원                     10건   ← 전부 풀림
```

### 접힌 줄은 조각을 따로 누른다

`동향·남동향` 처럼 접힌 줄을 통째로 누르게 하면 어느 무리로 거는지 알 수 없다.
조각마다 따로 누를 수 있게 한다. 거를 때는 그 줄의 향 중 **하나라도** 맞으면 남긴다 —
다 맞아야 한다고 하면 `남향·동향` 으로 접힌 줄이 어느 쪽으로 걸러도 사라진다.

### 덮어쓰지 않는다

같은 집을 두 번 붙여넣었는데 한 번은 향이 안 적혀 있으면, 덮어쓰기로 두면 있던 값이
지워진다. **비어 있을 때만** 채운다.

## 동 위치 카드를 뺐다

이 표본에서는 검출되지 않는다(τ=0.0%, 검출 한계 약 1.2%). 단지 안에서만 비교하면
2.5%가 나오지만 그건 **평형 교란**이었다 — 40㎡가 두 동에만 있는 단지에서는 면적
곡선의 오차가 그 동들의 '동 효과' 로 둔갑한다. 평형을 통제하면 사라진다.

그래서 카드가 늘 "검출되지 않았습니다" 만 적고 있었다. 한 번 읽으면 그만인 말이 요인
격자에서 자리를 계속 차지한다. 동이 가격에 미치는 영향 중 이 표본에서 잡히는 경로는
**역까지 도보거리**뿐이고, 그건 그 카드에 이미 있다.

쟀던 값은 `fit["dong_premium"]` 에 그대로 남아 있다. **지우는 것은 화면이지 측정이
아니다** — 지역이나 기간이 바뀌어 검출되기 시작하면 다시 꺼내 쓸 수 있다.

## 향에 따른 가격 — 호가로 재고, 칸 안에서만 비교한다

### 보정계수와 따로 둔다

요인별 보정계수는 전부 **실거래**에서 추정한 값이다. 국토교통부 실거래에는 **향이
없어** 그 격자에 끼울 수 없다. 같은 격자에 넣으면 근거가 다른 숫자가 같은 무게로
읽힌다. 카드를 따로 두고 제목 옆에 `호가 기준` 이라고 적는다.

### 단지를 넘어서 비교하면 뒤집힌다 — 재 보고 알았다

처음에는 향 무리별 괴리율 중위를 그냥 냈다.

```
남향 -4.7%p    동향 +6.3%p    서향 +14.3%p    (전체 중위 대비)
```

'서향이 제일 비싸다' 는 말이 되는데 향의 좋고 나쁨과 정반대다. 들여다보니 **서향
25건 중 18건(72%)이 한 단지**(신나무실휴먼시아)였다. 그 단지의 호가가 적정가보다
높게 붙어 있었고, 그게 '서향 프리미엄' 으로 둔갑했다.

같은 **(단지·평형)** 칸 안에서만 비교하니 방향이 뒤집혔다.

```
남향 +0.70%p   동향 +0.60%p   서향 -0.75%p
```

**동 위치 카드를 뺀 것과 같은 함정이다.** 적정가가 단지·평형·층·시점을 통제한다고
해도, 그건 '그 칸의 실거래 대비' 일 뿐 **칸마다 호가가 얼마나 공격적인지**까지는 빼
주지 않는다.

### 어떻게 재나

1. 호가마다 적정가 대비 괴리율을 낸다 — **순위표와 같은 함수**로. 여기서 따로
   계산하면 두 화면이 언젠가 다른 말을 한다.
2. `(단지, 반올림 평형)` 으로 칸을 만든다.
3. 향이 **둘 이상 섞인 칸만** 쓴다. 한 가지뿐인 칸은 비교할 상대가 없다.
4. 칸 안에서 '그 칸의 중위' 를 뺀다. 칸마다의 호가 성향이 여기서 사라진다.
5. 무리별로 그 값들의 중위를 낸다.

### 충분한지는 **내가 아니라 구간이** 정한다

처음에는 '칸 20개' 라는 문턱을 내가 정했다. 그건 근거가 없다 — 20개가 왜 충분한지
말할 수 없었다. **칸을 통째로 복원추출하는 부트스트랩**으로 95% 구간을 내고, 구간이
0 을 건너지 않으면 '잡혔다' 로 본다.

칸 단위로 뽑는 이유: 한 칸 안의 매물들은 서로 독립이 아니다(같은 단지·같은 평형,
중개사도 겹친다). 매물 단위로 뽑으면 표본이 실제보다 많은 척하게 되고 구간이 거짓으로
좁아진다.

난수는 고정한다. 같은 데이터에 같은 구간이 나와야 '어제보다 좁아졌다' 가 데이터가
늘어서인지 주사위 탓인지 가려진다.

### 막대는 잡혔을 때만, 숫자는 늘 보여 준다

0 근처 막대 셋을 그리면 '향은 가격과 무관' 으로 읽히는데 실제로는 '이 표본으로는 잴
수 없다' 다. 그래서 막대는 잡혔을 때만 그리고, **지금 값과 구간은 표로 늘 보여 준다** —
숨기지는 않는다. 동 위치 카드를 뺀 이유와 같은 자리다.

### "얼마나 더 모아야 하나" 에 숫자로 답한다

구간 폭은 칸 수의 제곱근에 반비례한다. 검출 한계를 ±1%p 까지 좁히려면 칸이
`(지금 한계 / 1)²` 배 필요하다.

그런데 **매물 수가 아니라 단지 수**가 관건이다. 재 봤다 — 매물 81건·단지 6곳에서
향이 섞인 칸은 6개, 즉 **단지당 1개꼴**이었다. 같은 단지에서 더 담아도 칸은 거의 안
는다(그 단지의 평형 수가 상한이고, 한 평형에 향이 하나뿐인 곳도 많다).

```
지금    칸 6개 · 검출 한계 ±2.67%p · 단지 4곳
목표    ±1%p  ->  칸 약 42개  ->  단지 약 28곳
```

그래서 화면이 "같은 단지에서 더 담는 것보다 **단지를 더 도는 쪽**이 빠릅니다" 라고
적는다. 쓰는 사람이 할 일을 바꾸는 안내다.

### 무리 규칙은 양쪽에 같이 둔다

`services/aspect.py` 의 `ORDER` 와 프론트 `rankSelect.js` 의 `ASPECT_ORDER` 가 같은
순서여야 한다. 두 곳이 다르면 같은 매물이 화면마다 다른 무리에 들어간다.

## 향 카드도 접고, 자세한 것은 창으로

매크로 탭에서 쓰던 카드 모양을 `components/PanelCard.jsx` 로 꺼내 공용으로 뒀다.
한 화면에서 '누르면 커지는 카드' 가 두 가지 모양이면 어느 쪽이 눌리는지 매번 확인하게
된다.

카드가 답할 질문은 **'어느 쪽이 비싼가'** 하나다. 표·경고·구간은 창에 있다. 처음에는
전부 카드에 늘어놨더니 정작 그림이 안 보였다.

### 축소판은 색과 글자로만 말한다

300px 안에 눈금 원·수염·다각형을 다 그렸더니 선이 너무 많아 "뭘 보라는 거지" 가 됐다.
네 칸을 **십자로** 놓고 색 진하기로 크기를, 글자로 값을 말한다. 색 기준은 1%p —
그보다 큰 차이는 실무에서 쓸 만하고 그 안쪽은 흥정 범위다(`TARGET_FLOOR` 와 같은 값).

가운데 칸은 '보통 호가' 라고만 적는다. 기준이 무엇인지 모르면 +0.67%p 가 무엇에 대한
것인지 알 수 없다.

## 향을 나침반으로 보여 준다

막대 넷을 세로로 쌓으면 '남·동·서·북' 이 그냥 네 칸이 된다. 이 값이 말하는 것은
**방향**이라, 방향대로 놓으면 읽는 데 번역이 필요 없다. 북이 위 — 지도와 같다.

### 0 원과 수염이 핵심이다

가운데 점선 원이 **칸 중위**(그 단지·평형의 보통 호가)다. 바깥으로 뻗으면 더 비싸게,
안으로 들어가면 싸게 부른다는 뜻이다.

각 방향의 **수염은 95% 구간**이고, 그 선이 0 원을 **가로지르면 아직 못 가른다.**
숫자만 보면 '남향 +0.67%p' 가 사실처럼 읽히는데, 수염이 원을 넘나드는 것을 보면
단정할 수 없다는 게 한눈에 들어온다. 이 그림이 하는 일의 절반이 그것이다.

### 자료가 적은 방향은 점을 찍지 않는다

북향은 광고에 거의 안 적혀 칸이 세 개뿐이다. 그 값(+5.4%p)을 찍으면 북쪽으로 가시가
솟아 그림을 지배한다 — **매물 세 건이 그림 전체를 끌고 가는 셈**이다. 축만 흐리게
그리고 '자료 부족 (3칸)' 이라고 적는다.

### 라벨을 viewBox 안에 담는다

이름·값이 원 바깥에 붙으므로 `overflow: visible` 로 비어져 나오게 뒀더니 아래 범례
글과 겹쳤다(재 봤다: 남향 30px, 동향 32px 넘침). 넘치게 두면 폭에 따라 겹치는 자리가
달라져 어디서 깨지는지 알 수 없다. viewBox 를 넓혀 담으면 그림이 통째로 줄어들 뿐이다.

### 나침반이 못 답하는 것은 표로

나침반은 각 방향을 **칸 중위와** 견준 그림이라 두 방향끼리는 못 견준다. '남향이
서향보다 비싼가' 에는 **짝 비교**가 답한다 — 두 향이 **같은 칸에 함께 있을 때만**
골라 뺀 값이다. 칸 중위를 거치지 않으므로 사이에 낀 다른 무리의 영향이 섞이지 않는다.

짝도 3칸 미만이면 구간을 내지 않는다. 북향 1칸이 `[+5.40, +5.40]` 으로 '유의' 가 났던
것과 같은 함정이다 — **구간이 좁은 것이 확실하다는 뜻이 아니라, 퍼질 거리가 없다는
뜻**이었다.

## 합쳤다가 다시 나눴다 — 미시 분석 · 거시 분석

시장 분석과 매크로를 한 탭의 두 섹션으로 합쳤다가, 좌우 2단으로 바꿨다가, **결국
탭을 다시 나눴다.** 그 과정에서 배운 것을 적어 둔다.

합친 이유는 분명했다 — 둘은 같은 질문의 두 축이고, '모델과 어긋나는 곳' 은 두 쪽의
값을 겹쳐야 뜻이 생긴다. 그런데 **각자 카드가 예닐곱 장이다.** 세로로 쌓으면 스크롤로
오가야 하고(합친 보람이 없다), 좌우로 쪼개면 단마다 862px 밖에 안 돼 카드가 얇아진다.

겹쳐 봐야 하는 것은 결국 **한 장**이고, 그건 거시 쪽 카드에 이미 들어 있다. 한 장
때문에 열다섯 장을 한 화면에 밀어 넣을 이유가 없었다.

남은 것: `PanelCard`(매크로 카드 모양을 공용으로 뺀 것)와 아래 격자 폭 측정.

### 격자 폭은 폭이 바뀔 때마다 다시 재야 한다

같은 `minmax` 값이 배치에 따라 전혀 다른 결과를 낸다. 2단일 때 맞춘 260px 을 한 단으로
돌아오며 그대로 뒀더니 **여섯 칸·269px** 이 되어 카드가 종잇장이 됐다.

```
1,720px 한 단 기준
  260px -> 6칸(269)   280~320px -> 5칸(325)   340px -> 4칸(410)
```

300px 이면 다섯 칸·325px 이고 미시 카드 일곱 장이 5+2, 거시 여덟 장이 5+3 으로
떨어진다. 폭을 바꿀 때는 **격자도 같이 재는 것**이 규칙이다.

## (지난 기록) 분석 탭을 좌우 2단으로 — 좌 거시, 우 미시

두 섹션을 세로로 쌓아 두니 '무엇이 가격을 움직이나'(미시)와 '지역이 서로 어떻게
다른가'(거시)를 보려면 여전히 스크롤로 오가야 했다. 둘을 **나란히** 놓으면 눈만
옮겨 견줄 수 있다 — 두 탭을 오가며 머릿속에서 이어 붙이던 것이 원래 문제였다.

### 폭을 고정 상한에서 화면 따라가기로

1240 → 1560 → 지금. 한쪽 단이 격자를 품어야 하는데 1560px 에서는 단마다 760px 밖에
안 돼 카드가 두 칸 들어가고 양옆은 여전히 비었다. `min(100%, 2200px)` 로 화면을
따라가게 두되 2,200px 에서 멈춘다 — 그 너머는 글줄이 아니라 **눈이 좌우로 너무 멀리
간다.**

### 격자 최소폭 300 → 260px (재 보고)

단마다 862px 인데 `minmax(300px)` 로는 **두 칸**밖에 안 들어가 칸폭이 402px 로 벌어지고
오른쪽이 비었다. 재 보니 260px 부터 세 칸이 되고 칸폭은 262px 다.

```
단 862px 기준
  300px -> 2칸 (칸폭 402)    260px -> 3칸 (칸폭 262)
  280px -> 2칸 (칸폭 402)    240px -> 3칸 (칸폭 262)
```

카드 축소판은 원래 축 눈금도 이름표도 없이 구름·분포 모양만 보여 주므로 262px 에서
버틴다.

### DOM 순서는 미시가 먼저, 자리만 order 로 바꾼다

좁은 화면에서는 단이 하나라 위에서부터 읽는데, 그때 먼저 와야 할 것은 이 서비스가
직접 낸 값(미시)이다. 넓을 때만 `order` 로 거시를 왼쪽에 놓는다 — 마크업을 건드리지
않고 배치만 바뀐다.

1280px 미만에서는 한 단으로 떨어지고 건너뛰기 네비게이션이 다시 나온다. 둘 다 보일
때는 건너뛸 데가 없으므로 넓은 화면에서는 숨긴다.

## 향 카드는 뺐다

그림이 설득력 있게 나오지 않았다. **측정은 남긴다** — `services/aspect.py` 와
`/api/analysis/aspect` 는 그대로다. 향도 계속 저장되고 매물 순위의 향 열·Ctrl+클릭
좁히기도 그대로다. 화면에서 뺀 것은 미시 분석의 카드 하나다.

동 위치 카드를 뺄 때와 같은 기준이다 — **지우는 것은 화면이지 측정이 아니다.**
정적 내보내기에서는 뺐다(안 쓰는 응답을 2,151개 파일에 섞어 둘 이유가 없다).

## 거시 탭 — 지표를 고르지 않고 전부 깐다

지표 칩으로 하나를 골라 보게 했는데, **일곱 개뿐이고 카드 축소판은 한 장이 작다.**
고르는 수고를 시키느니 전부 깔고 눈으로 훑게 하는 쪽이 빠르다. 선택식일 때는
'전세가율이 어떻더라' 를 보려면 칩을 누르고 기다려야 했다.

카드 13장이 된다(인사이트 6 + 지표 7). 필터에는 **기간만** 남는다.

### 오는 대로 그린다

지표마다 따로 받고 도착하는 대로 카드를 채운다. `Promise.all` 로 묶으면 제일 느린
하나가 전부를 잡는데, 정적 사이트에서는 파일 일곱 개라 그럴 이유가 없다.

하나가 실패해도 나머지는 그린다 — 실패를 모아 오류 화면으로 올리지 않고 그 카드만
비운다. 지표 하나가 안 와서 탭 전체가 막히는 것이 더 나쁘다.

### '지표 추이' 와 '최신값' 을 합쳤다

둘 다 같은 지표를 보는 것이라 카드를 나눌 이유가 없었다. 지표 창 하나에 추이·범례·
최신값 표를 같이 둔다.

### 지운 것

`MetricChips`, `MetricNote`, `MiniTable`. 지표 설명(`what`/`read`)은 서버가 여전히
내려보내고 지표 창의 `note` 로 보인다 — 칩 호버에만 있던 것이 창으로 옮겨 간 셈이다.
